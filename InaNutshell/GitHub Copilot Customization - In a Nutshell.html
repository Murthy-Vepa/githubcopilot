    📖 Overview

    intro overview

    GitHub Copilot Customization lets you tailor how Copilot behaves in your projects — shaping agents, skills, instructions, prompts, hooks, tools, and integrations so Copilot works the way your team does.

    💡 Customizations can be scoped per-workspace (shared with your team via source control) or per-user (personal preferences that follow you across projects).

    Why Customize Copilot?

    • Consistency — encode team conventions once, so every suggestion and chat response follows the same standards.
    • Context — give Copilot domain knowledge it can't infer from code alone (architecture, business rules, tooling).
    • Reusability — package common workflows as prompts and skills instead of re-explaining them each session.
    • Automation — trigger actions automatically with hooks when files are saved, tasks run, or events occur.
    • Extensibility — connect external tools and data sources through MCP servers and plugins.

    The Building Blocks

    Building BlockPurpose
    🤖 AgentsCustom personas with specialized instructions and scoped tool access for specific tasks.
    💡 SkillsReusable, domain-specific knowledge and workflows that Copilot can discover and invoke.
    📘 InstructionsAlways-on guidance that steers AI behavior across a workspace or user profile.
    🔖 PromptsReusable, parameterized prompt templates for repeatable tasks.
    ⚡ HooksAutomated actions triggered by events such as saving a file or running a task.
    🔌 MCP ServersExternal tool servers that extend Copilot with custom tools and data sources.
    🧩 PluginsInstallable extensions that add tools, skills, and integrations to Copilot.

    Where Customizations Live

    Most customizations are Markdown files with YAML frontmatter, stored either in your workspace (e.g. .github/) for team-shared behavior, or in your user profile for personal defaults that apply across all projects.

    🤖 Agents

    agents personas

    A custom agent is a specialized Copilot persona with its own instructions, tool access, and mode of operation. Instead of relying on the default assistant, you can define agents purpose-built for a role — a code reviewer, a security auditor, a deployment planner, a database migration expert — each with the exact knowledge and permissions it needs.

    🎯 Agents are ideal when a task needs a consistent persona across many invocations — e.g. "always review PRs the same way" or "always plan Azure deployments with the same checklist."

    Why Use Custom Agents?

    • Specialization — a narrow, well-defined persona produces more focused and predictable output than a general-purpose assistant.
    • Safety — scoping tool access limits blast radius; a docs agent can't accidentally run destructive terminal commands.
    • Repeatability — the same review checklist, deployment steps, or migration process runs identically every time it's invoked.
    • Discoverability — agents show up in the chat agent picker with a name and description, so teammates can find and reuse them.
    • Composability — agents can call subagents for parallelizable or isolated work, building multi-agent workflows.

    What Makes Up an Agent

    • Name & description — identifies the agent and when it should be used (shown in the agent picker).
    • Instructions — the persona's behavior, tone, responsibilities, and step-by-step process.
    • Tool access — the specific tools/functions the agent is allowed to call.
    • Argument hint — guidance shown to the user on what input the agent expects.
    • Model preference (optional) — some platforms let an agent request a specific model tier for its workload.

    Common Agent Archetypes

    ArchetypeTypical Responsibility
    🔍 ReviewerReviews PRs/diffs for style, security, and correctness against team standards.
    🧪 TesterWrites and runs unit/integration tests, reports coverage gaps.
    🚀 DeployerPlans and executes infrastructure/deployment changes with guardrails.
    📚 DocumenterGenerates or updates docs, READMEs, and changelogs from code changes.
    🛡️ Security AuditorScans for vulnerabilities and OWASP Top 10 issues, suggests fixes.
    🧭 ExplorerRead-only research and codebase Q&A, safe to call in parallel.

    Agent Definition

    Custom agents are defined in .agent.md files with YAML frontmatter followed by Markdown instructions — similar to instructions files, but scoped to a single persona.

    ---
name: code-reviewer
description: Reviews pull requests for style, security, and correctness.
tools: ['codebase', 'search', 'runTests']
argument-hint: Paste a diff or PR link to review
---

You are a meticulous code reviewer. For every change:
1. Check for security issues (OWASP Top 10).
2. Verify tests cover the new behavior.
3. Flag style inconsistencies with project conventions.
4. Summarize findings as a short bullet list, ordered by severity.

    Common Frontmatter Fields

    FieldPurpose
    nameUnique identifier used to invoke the agent.
    descriptionShown in the agent picker; helps users and orchestrators pick the right agent.
    toolsAllow-list of tools/functions the agent may call.
    argument-hintPlaceholder text guiding what input to supply.
    Body (Markdown)The system instructions defining persona, process, and constraints.

    Where Agent Files Live

    • Workspace-scoped — .github/agents/*.agent.md, committed to source control and shared with the team.
    • User-scoped — stored in the user profile, following you across every project you open.

    Invoking an Agent in Chat

    Once an .agent.md file is in scope, the agent appears in the chat participant picker. Reference it with the @ prefix followed by its name field:

    # In the Copilot Chat input:
@code-reviewer Please review the changes in src/auth/

# With the optional argument-hint text filled in:
@code-reviewer https://github.com/org/repo/pull/42

    You can also type @ in the chat input to open the agent picker and browse all available agents.

    Model Selection

    By default, agents use whatever model is active in the Copilot Chat session. You can optionally pin a specific model in the frontmatter — useful when a task consistently needs a reasoning-capable model vs. a fast one:

    ---
name: security-auditor
description: Deep-dives into code for security vulnerabilities — OWASP Top 10 and CWE.
model: gpt-4o          # Pin to a specific model for this agent
tools: ['codebase', 'search']
---

    Check your Copilot subscription plan — some models (e.g. o3, Claude Sonnet) are only available on Copilot Enterprise or Business plans.

    📝 Keep agent instructions focused on one responsibility. If an agent's instructions try to cover too many concerns, split it into multiple agents that can be composed together.

    Tool Access & Permissions

    Each agent declares the tools it's allowed to use via the tools frontmatter field. This scopes the agent's capabilities — a documentation agent might only get read/search tools, while a deployment agent might get terminal and cloud provider tools.

    🔒 Least-privilege by default: an agent can only call the tools explicitly listed. This prevents an agent designed for one purpose from taking unintended actions.

    Tool Categories

    CategoryExamplesRisk Level
    Read-onlyFile search, semantic search, reading files, listing directories🟢 Low
    WriteFile edits, creating files, renaming symbols🟡 Medium
    ExecutionTerminal commands, running tests/builds🟠 Medium-High
    IntegrationMCP servers, cloud provider tools (Azure, GitHub), databases🔴 High

    Design Guidance

    • Start with the smallest tool set that lets the agent complete its job, then expand only if needed.
    • Separate read-only "explorer" agents from write-capable "implementer" agents so research never accidentally mutates code.
    • For destructive or hard-to-reverse actions (deletes, force-pushes, infra teardown), require explicit user confirmation even if the tool is technically available.
    • Review an agent's tool list periodically as your toolset grows — unused permissions should be removed.

    Built-in vs Custom Agents

    AspectBuilt-in AgentCustom Agent
    SourceShipped with Copilot (e.g. default chat agent, Explore)Defined by the user/team in .agent.md
    BehaviorGeneral-purpose, broad knowledgeTailored to a specific task or domain
    Tool accessFull default toolsetExplicitly scoped subset
    PortabilityAlways available, no setupShared via source control or user profile
    MaintenanceMaintained by the platform vendorMaintained by your team; can go stale if not reviewed
    Best forEveryday coding assistance, ad-hoc questionsRepeatable workflows with guardrails (review, deploy, migrate)

    Choosing Between Them

    • Use the default/built-in agent for general coding help, exploratory questions, and one-off tasks.
    • Reach for a custom agent when a task recurs often enough to justify codifying the process, or when you need to restrict what actions are possible.
    • Combine both: a custom orchestrator agent can delegate research to a built-in explorer subagent, then hand off implementation to a specialized coder agent.

    Use built-in agents for everyday coding assistance, and reach for custom agents when you need repeatable, specialized workflows with guardrails on tool access.

    💡 Skills

    skills knowledge agentskills.io

    Agent Skills are a lightweight, open format for extending an AI agent's capabilities with specialized, reusable knowledge and workflows. A skill is simply a folder containing a SKILL.md file with metadata and instructions — optionally bundled with scripts, reference docs, and templates the agent can pull in as needed.

    🎯 Skills package procedural knowledge — company, team, or domain-specific know-how — into portable, version-controlled folders that any skills-compatible agent can load on demand.

    Why Skills Exist

    Agents are increasingly capable, but they often lack the specific context needed to do real work reliably. Skills solve this by turning tribal knowledge into structured, reusable instructions:

    • Domain expertise — capture specialized knowledge (legal review, data pipelines, deployment runbooks) as instructions and resources instead of re-explaining it every session.
    • Repeatable workflows — turn multi-step tasks into consistent, auditable procedures anyone on the team can trigger.
    • Cross-product reuse — Agent Skills is an open standard; build a skill once and use it across any compatible client (GitHub Copilot, Claude, Cursor, Gemini CLI, and dozens more).
    • Small context footprint — unlike stuffing everything into one instructions file, skills load lazily so an agent can keep hundreds on hand without bloating every prompt.

    Skills vs Agents vs Instructions

    MechanismAnswersLoaded
    Instructions"How should all code in this repo be written?"Always, for matching files
    Agent"Who is doing the work, and what can they touch?"When that persona is invoked
    Skill"How do I perform this specific task?"On demand, only when relevant

    Any agent — built-in or custom — can invoke a matching skill mid-task. Skills are the reusable "how-to" library that agents draw from.

    Example Skill Categories

    CategoryExample Skills
    Document processingPDF extraction/merging, spreadsheet generation, slide-deck formatting
    Cloud & DevOpsProvisioning checklists, deployment runbooks, IaC scaffolding conventions
    Data & analyticsETL pipeline patterns, SQL query guidelines, dashboard build steps
    Compliance & reviewLegal contract review, security audit checklists, accessibility review
    Team conventionsCompany style guides, commit message formats, release-note templates

    Skills vs MCP Servers

    Skills and MCP servers solve different problems and are often used together:

    • MCP servers expose live capabilities — new tools/functions the agent can call (query a database, hit an API).
    • Skills package knowledge about how to use those capabilities correctly — which query patterns to prefer, what edge cases to check, how to format the result.
    • A skill's allowed-tools field can reference MCP-provided tools directly, tying the "how" to the "what."
    🧩 Think of MCP servers as adding new hands to the agent, and skills as the training manual for using those hands well.

    SKILL Structure

    Every skill lives in its own directory, matching its name, with a required SKILL.md at the root:

    pdf-processing/
├── SKILL.md          # Required: metadata + instructions
├── scripts/          # Optional: executable code (Python, Bash, JS...)
├── references/       # Optional: detailed docs loaded on demand
├── assets/           # Optional: templates, images, data files
└── ...               # Any additional files or directories

    SKILL.md Frontmatter

    FieldRequiredConstraints
    nameYes1–64 chars; lowercase letters, digits, hyphens only; no leading/trailing/double hyphens; must match the folder name.
    descriptionYes1–1024 chars; states what the skill does and when to use it — this is what agents match against.
    licenseNoLicense name or reference to a bundled license file.
    compatibilityNoMax 500 chars; environment requirements (e.g. "Requires git, docker, jq").
    metadataNoFree-form string key/value map for client-specific extensions (e.g. author, version).
    allowed-toolsNoSpace-separated, pre-approved tools (experimental; e.g. Bash(git:*) Read).
     
    ---
name: pdf-processing
description: Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs. Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction.
license: Apache-2.0
metadata:
  author: example-org
  version: "1.0"
---

## Instructions
1. Identify the requested operation (extract, fill, merge).
2. Run the matching script in scripts/ with the input file path.
3. Report the output file location and a summary of what changed.
    ✍️ Write a specific description with concrete keywords ("PDFs, forms, document extraction"), not a vague one like "Helps with PDFs." Vague descriptions make skills harder for agents to match correctly.

    Optional Directories

    • scripts/ — self-contained executable code the agent can run; should include clear error messages and handle edge cases.
    • references/ — deeper documentation (e.g. REFERENCE.md, FORMS.md) loaded only when the task needs that level of detail.
    • assets/ — templates, images, schemas, or other static resources the skill's instructions point to.
    📏 Keep SKILL.md under ~500 lines (ideally <5,000 tokens). Move deep detail into references/ files linked with relative paths, one level deep, so context stays small until it's actually needed.

    Naming Rules — Valid vs Invalid

    ExampleValid?Reason
    pdf-processing✅Lowercase, hyphen-separated, matches folder name.
    data-analysis✅Simple, descriptive, no special characters.
    PDF-Processing❌Uppercase letters are not allowed.
    -pdf❌Cannot start with a hyphen.
    pdf--processing❌Consecutive hyphens are not allowed.

    File References

    When a skill's instructions need to point at bundled files, use relative paths and keep the reference chain shallow:

    See [the reference guide](references/REFERENCE.md) for details.

Run the extraction script:
scripts/extract.py

    Avoid deeply nested reference chains (a reference file pointing to another reference file pointing to another) — keep everything one hop from SKILL.md so the agent doesn't have to chase a trail of links.

    Writing Effective Instructions

    • Lead with step-by-step instructions written as an ordered list — agents follow procedures more reliably than prose.
    • Include examples of inputs and outputs so the agent can pattern-match expected results.
    • Call out common edge cases and how to handle them (missing files, malformed input, empty results).
    • Prefer concrete, imperative language ("Run X, then check Y") over abstract advice ("Be careful with X").

    Skill Discovery & Invocation

    Skills load through progressive disclosure — agents only pull in as much detail as a task actually requires, in three stages:

    1. Discovery — at startup, the agent loads only each skill's name and description (~100 tokens each), just enough to know when it might be relevant.
    2. Activation — when a task matches a skill's description, the agent reads the full SKILL.md body into context.
    3. Execution — the agent follows the instructions, optionally running bundled scripts or loading referenced files as needed.
    💡 This is why the description field matters so much: it's the only thing evaluated against every incoming task before a skill is activated. A precise description with the right trigger keywords is the difference between a skill being found and being ignored.

    Where Skills Live

    • Workspace-scoped — bundled with a repository so the whole team gets the same skill automatically.
    • User-scoped — installed in a personal profile/toolbox, following the user across projects.
    • Shared/marketplace — since the format is open, skills can be published and pulled into any compatible client without modification.

    Ecosystem

    Agent Skills was originally developed by Anthropic and released as an open standard; it's now supported by a wide range of agentic tools — GitHub Copilot, VS Code, Claude Code, Cursor, Gemini CLI, OpenAI Codex, Goose, OpenCode, and many more — so a skill written once can be reused across whichever client a team member prefers.

    🔧 Validate a skill before sharing it with the skills-ref reference tool: skills-ref validate ./my-skill — it checks frontmatter validity and naming conventions.

    How Matching Works in Practice

    • The agent compares the user's request against every available skill's description — not its name or body — to decide relevance.
    • Multiple skills can match; a well-behaved agent picks the most specific one, or asks for clarification if the choice is ambiguous.
    • If no skill's description is a good match, the agent falls back to general reasoning instead of forcing a poor fit.
    • Skills don't need to be manually invoked by name — good descriptions make them trigger naturally from everyday phrasing.

    Testing a New Skill

    1. Run skills-ref validate to confirm frontmatter and folder naming are correct.
    2. Ask the agent a realistic question that should trigger the skill, using the same words a real user would.
    3. Confirm the full SKILL.md was loaded (not just the metadata) and the agent followed the documented steps.
    4. Try a near-miss request that should not trigger the skill, to check the description isn't too broad.

    Common Pitfalls

    • Vague descriptions — "Helps with data" matches almost everything or nothing; be specific about scope and trigger keywords.
    • Overloaded skills — one skill trying to cover too many unrelated tasks; split into focused, single-purpose skills instead.
    • Bloated SKILL.md — burying instructions in a huge file wastes context; move detail into references/.
    • Undocumented scripts — bundled scripts with no usage notes force the agent to guess arguments; document expected inputs/outputs.

    📘 Instructions

    instructions guidance

    Instructions are standing guidance that Copilot automatically applies to every relevant request — repo-wide conventions, coding standards, and house rules that shouldn't need to be repeated in every prompt. Unlike agents (a persona) or skills (a task-specific how-to), instructions are always-on context that shapes every response for matching files.

    🎯 Use instructions for things you'd otherwise say in every single chat message — "use tabs not spaces," "always add null checks," "never use any in TypeScript." Say it once, apply it everywhere.

    Two Flavors of Instructions

    FileScopeWhen It Applies
    .github/copilot-instructions.mdWhole repositoryAlways, for every Copilot request in this workspace
    *.instructions.mdTargeted file patternsOnly when the active/edited file matches its applyTo glob

    Instructions vs Agents vs Skills

    • Instructions — passive, always-considered background rules ("how code should look").
    • Agents — active personas you invoke for a role ("who is doing the work").
    • Skills — on-demand how-to knowledge for a specific task ("how to do this one thing").

    They compose together: an agent can be bound by repo-wide instructions while also pulling in a skill mid-task.

    copilot-instructions.md

    Placed at .github/copilot-instructions.md, this file is the single most impactful customization for a repo — its content is automatically included as context for every chat request and inline suggestion in that workspace, with no applyTo matching required.

    # Copilot Instructions

This is a .NET 8 Web API with a React frontend.

## Conventions
- Use dependency injection; no static service locators.
- Controllers stay thin — business logic lives in services.
- All new endpoints require an integration test in `tests/`.

## Style
- C#: prefer expression-bodied members for simple properties.
- React: functional components with hooks only, no class components.

## Do Not
- Do not commit secrets or connection strings — use Key Vault references.
- Do not add new NuGet packages without checking `Directory.Packages.props`.

    What Belongs Here

    • Project context — stack, architecture style, folder layout, where things live.
    • Global conventions — naming, formatting, error handling, testing expectations that apply everywhere.
    • Guardrails — things Copilot must never do (commit secrets, bypass auth, use deprecated APIs).
    • Pointers — references to other instructions/skills files for more specific guidance, so this file doesn't become a dumping ground.
    ⚠️ Keep this file lean and high-signal. Since it loads on every request regardless of what file is open, bloating it with narrow, file-specific rules wastes context on requests where those rules don't even apply — use .instructions.md with applyTo for that instead.

    .instructions.md & applyTo

    For guidance that should only apply to certain files or folders, use a *.instructions.md file under .github/instructions/. Its YAML frontmatter applyTo field is a glob pattern — Copilot only loads the file's content when the currently active or edited file matches that pattern.

    ---
applyTo: "**/*.test.ts"
---

Use Jest with `describe`/`it` blocks. Mock external HTTP calls with `nock`.
Every test file must cover at least one failure-path scenario.
Prefer `screen.getByRole` over `getByTestId` in React Testing Library tests.

    Common applyTo Patterns

    PatternMatches
    **Every file (equivalent scope to copilot-instructions.md, but composable/optional)
    **/*.ts,**/*.tsxAll TypeScript and TSX files anywhere in the repo
    src/api/**Everything under the src/api folder
    **/*.bicepAll Bicep infrastructure files
    **/*.test.*,**/*.spec.*Test files regardless of extension/language

    Why Split Instructions by applyTo

    • Relevance — frontend rules don't clutter context when editing backend code, and vice versa.
    • Ownership — different teams can own different instructions files without merge conflicts in one giant file.
    • Composability — multiple .instructions.md files can match the same file simultaneously; all matching ones are applied together.
    • Discoverability — a file per concern (testing, security, database access) is easier to review and update than one monolith.

    Instruction Stacking & Precedence

    When several instruction files match the active file, Copilot applies all of them simultaneously — there is no overriding or last-wins behaviour. Rules from multiple files are combined into the context:

    • No conflict resolution — if two files give contradictory guidance for the same pattern (e.g. one says "use tabs", another says "use 2-space indent"), the model must reconcile them itself. Avoid overlapping rules for the same concern.
    • Specificity is not ranked — a pattern like src/auth/** does not automatically take priority over **/*.ts; both instructions are injected with equal weight.
    • copilot-instructions.md is always loaded for every request, in addition to any matching .instructions.md files — so it forms the base layer.
    • Audit overlap periodically — use a glob visualiser or run git ls-files | grep -E "test|spec" to check which files would match multiple patterns.
    📁 A typical layout: .github/instructions/testing.instructions.md, security.instructions.md, frontend.instructions.md, infra.instructions.md — each scoped with its own applyTo.

    Best Practices

    Writing Effective Instructions

    • Be specific and actionable — "use dependency injection, not static service locators" beats "write clean code."
    • State the "don't"s explicitly — models follow explicit negative constraints ("never log PII") better than implied ones.
    • Prefer short, scannable bullets over long prose paragraphs; instructions are re-read on every request, so density matters.
    • Give examples for non-obvious conventions (a snippet showing the exact error-handling pattern beats a description of it).
    • Version-control instructions files alongside the code so they evolve with the codebase and are reviewed in PRs like any other change.

    Common Pitfalls

    • Overloading copilot-instructions.md — cramming every rule into the global file wastes context on requests where most rules are irrelevant; split with applyTo instead.
    • Conflicting instructions — two files giving contradictory guidance for the same files confuses the model; review overlapping applyTo patterns periodically.
    • Stale guidance — instructions describing a migrated-away framework or deprecated pattern actively mislead; treat them as living documentation.
    • Too vague to act on — "follow best practices" gives the model nothing concrete to check against; always tie guidance to a specific, verifiable rule.

    A Layered Approach

    1. Start with a lean copilot-instructions.md covering project context and the handful of rules that truly apply everywhere.
    2. Add scoped .instructions.md files as specific pain points emerge (a recurring review comment is a sign an instruction is missing).
    3. Periodically prune: remove instructions that no longer reflect the codebase, and merge near-duplicate files.
    4. Pair instructions with skills for anything that needs multi-step procedural guidance rather than a standing rule.
    💡 A good test: if you find yourself repeating the same correction across multiple PR reviews or chat sessions, that correction belongs in an instructions file, not in your memory.

    🔖 Prompts

    prompts reusable

    Prompt files are reusable, parameterized chat starters stored as .prompt.md files. Instead of typing the same detailed request from scratch every session, you write it once in a file, attach relevant context, wire in variables, and invoke it by name from the chat. Think of them as saved macros for complex, frequently repeated Copilot interactions.

    🔖 Prompts are for repeatable interactions — "generate a REST API spec from this schema," "write a post-incident report for this alert," "draft a PR description from the diff." Write once, reuse forever, share with the team.

    Prompts vs Instructions vs Skills

    MechanismTriggered byBest for
    InstructionsAutomatically, on every matching requestStanding rules and conventions
    SkillsAutomatically, when task matches descriptionProcedural how-to knowledge
    PromptsExplicitly, by the user selecting the promptComplex tasks the user wants to kick off on demand

    When to Use Prompts

    • Repeatable tasks with rich context — tasks that need several sentences of setup (e.g. "review this diff using our security checklist") benefit most from being saved rather than retyped.
    • Team workflows — commit a prompt to .github/prompts/ so everyone runs the same task the same way (PR descriptions, sprint retrospective notes, API documentation drafts).
    • Teaching new team members — a well-named prompt with clear variables is self-documenting; a new hire can invoke "generate-unit-tests" without understanding all the underlying conventions yet.
    • Multi-step scaffolding — chain instructions together in a single prompt body to walk Copilot through a multi-step generation task.

    .prompt.md Files

    A prompt file is a .prompt.md file with optional YAML frontmatter, stored in .github/prompts/ (shared with the team) or in your user profile (personal prompts). The filename becomes the prompt's display name in the chat slash-command picker.

    ---
description: Generates a unit test file for a given source file.
tools: ['codebase', 'search']
---

You are a test-writing assistant for a TypeScript project using Jest.

Given the file `${file}`, generate a comprehensive unit test file that:
1. Imports the subject under test and any required mocks.
2. Uses `describe`/`it` blocks with descriptive names.
3. Covers the happy path, at least one error path, and edge cases for each exported function.
4. Mocks all external HTTP calls with `nock`.

Place the output in a file named `${file.base}.test.ts` alongside the source file.

    Frontmatter Fields

    FieldPurpose
    descriptionShown in the prompt picker so users know what it does before invoking it.
    toolsRestricts which tools the prompt's session can use — same syntax as agent tool lists.
    modeOptional. Can pin the prompt to a specific agent mode (e.g. agent for agentic, chat for plain chat).

    Using the mode Field

    The mode field controls the execution environment for the prompt:

    ---
description: Scaffolds a new React component with tests and a Storybook story.
tools: ['codebase', 'search', 'createFile']
mode: agent        # Runs in agentic mode — Copilot can create files autonomously
---

Create a new React functional component named `${input:Component name}`.
Generate:
1. The component file at `src/components/${input:Component name}/${input:Component name}.tsx`
2. A Jest unit test at `src/components/${input:Component name}/${input:Component name}.test.tsx`
3. A Storybook story at `src/components/${input:Component name}/${input:Component name}.stories.tsx`
    • mode: agent — Copilot operates autonomously, can call tools, create/edit files, and run multi-step tasks.
    • mode: chat — Plain conversational mode; tools listed in the tools field are still available but Copilot won't take autonomous file-system actions.
    • Omitting mode inherits the current session mode.

    Prompt Execution Context

    When a prompt runs, Copilot has access to the following context automatically:

    • Active editor file — available via ${file} and related variables; the full file content is included if small enough to fit in the context window.
    • Current selection — available via ${selection}; only present if text was highlighted before invoking the prompt.
    • Workspace root — available via ${workspaceFolder}; useful for constructing absolute paths.
    • Tools allowed by tools field — e.g. listing codebase lets Copilot semantically search the workspace during prompt execution.
    • Active instructions files — any .instructions.md files matching the active file continue to apply during a prompt session.

    Prompts do not automatically receive the full repository content. If the prompt needs to read a specific file that isn't the active one, reference it explicitly in the prompt body or use a codebase tool call.

    Prompt Body

    The Markdown body after the frontmatter is the full prompt text sent to Copilot when the user invokes it. It can be as long and structured as needed — headings, numbered lists, code blocks, and variable placeholders all work as-is.

    Where Prompt Files Live

    • .github/prompts/*.prompt.md — workspace-level, checked in to source control, available to every teammate who opens the repo.
    • User profile — personal prompts that follow you across all projects, not visible to teammates.

    Invoking a Prompt

    1. Open the Copilot Chat input.
    2. Type / to open the slash-command picker — all .prompt.md files in scope appear by their filename.
    3. Select the prompt; Copilot pre-fills the chat with the prompt body and resolves any variables before sending.
    📁 A clean naming convention helps: use verb-noun format — generate-unit-tests.prompt.md, review-security.prompt.md, draft-pr-description.prompt.md — so the picker list reads like an action menu.

    Prompt Variables

    Variables make prompts generic and reusable. They are written as ${variableName} placeholders in the prompt body and are resolved at invocation time — either automatically from VS Code's current editor context or by prompting the user for input.

    Built-in Context Variables

    VariableResolves to
    ${file}The currently active file path.
    ${file.base}The filename without extension (e.g. userService from userService.ts).
    ${file.ext}The file extension (e.g. .ts).
    ${selection}The currently selected text in the editor.
    ${input}Free-text value — Copilot prompts the user to type something before sending.
    ${workspaceFolder}The absolute path to the workspace root.

    Using Variables Effectively

    • Combine variables to build dynamic paths: ${workspaceFolder}/tests/${file.base}.test.ts.
    • Use ${selection} for "act on what I've highlighted" prompts — code review, explanation, refactoring.
    • Use ${input} for open-ended parameters (ticket number, feature name, target API version) that can't be inferred from context.
    • Keep variables minimal — a prompt that requires the user to fill in five ${input} values is just as tedious as typing the prompt from scratch; parameterize only what genuinely varies.

    Example — PR Description Generator

    ---
description: Drafts a pull request description from the current diff.
tools: ['codebase', 'search']
---

Write a pull request description for the changes in the current branch.
Ticket reference: ${input:Ticket number (e.g. JIRA-1234)}

Structure the description as:
## Summary
One paragraph explaining *what* changed and *why*.

## Changes
Bullet list of the key changes.

## Testing
What was tested and how to verify.

## Notes
Any breaking changes, migration steps, or follow-up items.
    💡 The ${input:label} syntax lets you add a descriptive label to the user-facing input dialog, making prompts self-documenting: ${input:Ticket number (e.g. JIRA-1234)} is far clearer than a bare ${input}.

    Prompt Composition Tips

    • Reference workspace files inline with a relative path so Copilot knows exactly where to write generated output.
    • Chain prompts by having one prompt's output become the input file for a follow-up prompt (e.g. "generate spec" → "generate tests from spec").
    • Version prompts alongside code — when a convention changes, update the prompt and commit the change so history is preserved.

    📊 Skills vs Instructions vs Prompts

    comparison reference

    Skills, Instructions, and Prompts are the three knowledge-injection mechanisms in Copilot customization. They are often confused because they all involve Markdown files — but they serve completely different purposes, fire at different times, and live in different locations.

    🗝 Simple rule of thumb: Instructions = always-on rules; Skills = on-demand playbooks; Prompts = reusable task templates.

    Scope Repository-wide (or file-pattern scoped via applyTo) User-global or repo-local depending on install location Repository-wide; can also be in user settings for personal templates

    Content Authoring Guidelines

    GuidelineInstructionsSkillsPrompts
    Ideal length Short to medium — under 500 words per file; split into multiple files if needed As long as the playbook requires — 1–5 pages is normal for complex domains Short — the template itself is a single focused request, not a guide

    Decision Tree: Which Should I Use?

    • "I want Copilot to always follow a rule without me asking" → Instructions file
    • "I want Copilot to know how our team does X when it's working in that area" → Skill
    • "I want a shortcut to run a specific task repeatedly" → Prompt file
    • "I want a task to run automatically when I commit code" → Prompt file + Hook
    • "I want to give Copilot a persona for a specific type of work" → Agent (which can use all three)
    • "I want Copilot to call a live API or read a database" → MCP server

    ⚡ Hooks

    hooks automation

    Hooks let you attach automated Copilot actions to specific events in your development workflow — things like opening a file, saving a change, running a test, or committing code. Rather than manually asking Copilot to do something every time an event occurs, a hook fires automatically and runs a configured action or prompt in the background.

    ⚡ Hooks turn Copilot from a reactive assistant (answer when asked) into a proactive partner (do the right thing at the right moment without being asked).

    Why Use Hooks

    • Eliminate repetitive requests — if you always ask Copilot to explain a test failure or check coverage after every test run, a hook can fire that request automatically.
    • Enforce team practices — a pre-commit hook can automatically run a security review prompt on staged changes before they leave the developer's machine.
    • Reduce context switching — inline suggestions and ambient analysis that appear at the right moment mean fewer interruptions to fetch information manually.
    • Consistent quality gates — every save, every commit, every PR can trigger the same quality check, making the process repeatable rather than dependent on individual discipline.

    Hooks vs Prompts vs Instructions

    MechanismTriggered byRequires user action?
    InstructionsCopilot matching context automaticallyNo
    PromptsUser selecting from the slash-command pickerYes (explicit invoke)
    HooksA workspace or editor event (save, test run, commit…)No — fires automatically

    Hook Execution Model

    Understanding how hooks execute helps you write reliable, non-disruptive configurations:

    • Non-blocking by default — most hooks fire asynchronously so they do not delay your save, commit, or build. The only exception is a onGitCommit (pre) hook with a block: true condition, which can hold a commit until the action completes.
    • Timeout protection — hooks have a configurable timeout (default: 30 s). If the Copilot action does not complete within the timeout, the hook is silently cancelled to avoid hanging your workflow.
    • No queue buildup — rapid events (e.g. multiple saves in a second) are debounced; only the most recent event in the burst triggers the hook.
    • Failure isolation — if a hook's action fails (e.g. the prompt errors out, the network is unavailable), it logs the failure silently and does not surface a blocking error unless you set block: true.

    Knowing if a Hook Fired

    • Open VS Code Output panel → select GitHub Copilot (Hooks) channel to see a real-time log of hook events, conditions evaluated, and actions dispatched.
    • In Copilot Chat, a hook-triggered response is annotated with "Auto-triggered by <event>" so you can distinguish it from a user-initiated request.
    • Add a brief action.text that starts with "Hook fired:" during initial setup so hook responses are visually distinctive while you tune conditions.

    Hook Events

    Each hook is bound to a specific event — the trigger that causes it to fire. Events span the full development lifecycle, from editing through to deployment.

    Editor & File Events

    EventFires when…Common use
    onFileOpenA file is opened in the editorSurface relevant context, known issues, or recent changes for that file
    onFileSaveA file is savedTrigger inline lint feedback, auto-format reminders, or doc-sync checks
    onFileCloseA file is closedPrompt to add a test if the file changed but no test file was modified
    onDiagnosticChangeA new compiler error or warning appearsAutomatically explain the error and suggest a fix without the user asking

    Source Control Events

    EventFires when…Common use
    onGitStageFiles are staged for a commitRun a security scan or compliance check on the staged diff
    onGitCommit (pre)Just before a commit is finalisedValidate commit message format; block or warn on policy violations
    onGitCommit (post)After a commit completesGenerate a changelog entry or update a DEVLOG
    onBranchChangeThe active branch switchesSummarise what the new branch is about using recent commit history
    onPullRequestOpenA PR is opened or updatedAuto-draft PR description, request review checklist, run impact analysis

    Build & Test Events

    EventFires when…Common use
    onTestRun (post)A test run completesSummarise failures, suggest fixes, flag coverage regressions
    onBuildFailA build step failsParse the build output and surface the root-cause error with a suggested fix
    onBuildSuccessA build step succeedsRemind to update docs or run integration tests if only unit tests were run
    🔍 Not all hook events are available in every Copilot client. Check your client's documentation for the exact supported event list — VS Code exposes the richest set, including editor, SCM, and task events.

    Hook Configuration

    Hooks are configured in a .github/copilot-hooks.yml (or equivalent client-specific config file). Each hook entry names the event, optionally adds a condition, and specifies either an inline prompt or a reference to a .prompt.md file to run.

    # .github/copilot-hooks.yml
hooks:
  - event: onTestRun
    trigger: post
    condition: "failure"            # only fires when tests fail
    action:
      type: prompt
      text: |
        The test run just failed. Review the output, identify the root cause
        of each failing test, and suggest minimal fixes without changing
        unrelated code.

  - event: onGitCommit
    trigger: pre
    condition: "stagedFiles contains '*.ts'"
    action:
      type: prompt-file
      path: .github/prompts/pre-commit-security.prompt.md

  - event: onFileSave
    condition: "file matches 'src/api/**/*.ts'"
    action:
      type: prompt
      text: |
        Check the saved file for any new public endpoints that are missing
        authentication middleware. Report any issues as inline comments.

    Configuration Fields

    FieldRequiredDescription
    eventYesThe lifecycle event that triggers this hook (see Hook Events section).
    triggerNopre or post for events that have before/after phases (e.g. commit). Defaults to post.
    conditionNoA boolean expression that gates the hook — it only fires when the condition evaluates to true. Keeps noisy hooks quiet.
    action.typeYesprompt (inline text) or prompt-file (path to a .prompt.md).
    action.textIf type=promptThe inline prompt text sent to Copilot when the hook fires.
    action.pathIf type=prompt-fileRelative path to the .prompt.md file to use as the action.

    Conditions

    Conditions prevent hook fatigue by limiting when a hook fires. They support simple expressions over event context:

    • "failure" — only fire on a failed outcome (tests, builds).
    • "success" — only fire on a successful outcome.
    • "stagedFiles contains '*.sql'" — fire when the staged diff includes SQL files.
    • "file matches 'src/security/**'" — fire only when the active file is in a specific folder.
    • "testCount > 0" — fire only when at least one test was executed.

    Design Guidance

    • Start narrow — add conditions to every hook from day one; unconditioned hooks on frequent events (every save) quickly become noise.
    • Prefer prompt-file over inline text for anything longer than a sentence — it keeps the config readable and lets you iterate on the prompt without touching the hook config.
    • Use pre-commit hooks sparingly — they block the commit workflow; reserve them for critical checks (secrets detection, compliance) and keep them fast.
    • Test hooks in a branch first — an overly eager hook that fires on every keystroke will frustrate the team; validate scope and conditions before committing to main.
    • Document each hook's purpose in the YAML comments so teammates understand why it exists without reading the prompt body.
    🚦 A well-designed hook set feels invisible — it quietly surfaces the right information at the right moment without interrupting flow. If developers start dismissing hook output habitually, the hook is either too noisy or its output isn't actionable enough.

    🔌 MCP Servers

    mcp tools

    The Model Context Protocol (MCP) is an open standard that lets AI assistants like Copilot communicate with external tools, data sources, and services through a lightweight server/client architecture. An MCP server exposes a set of tools — named functions the model can call — and Copilot discovers and invokes them as needed during a chat session.

    🔌 MCP turns Copilot into a connected agent. Instead of answering from training data alone, it can query live databases, call REST APIs, read file systems, interact with CI/CD pipelines, and much more — all within the same conversation.

    Why MCP Matters

    • Live data access — Copilot can query real-time information rather than relying on stale training data or copy-pasted context.
    • Standardised integration — any service that implements the MCP spec can be connected to any compatible AI assistant, not just Copilot.
    • Composable tool sets — combine multiple MCP servers in a single session; Copilot picks the right tool for each subtask automatically.
    • Security boundary — each MCP server runs in its own process with its own credentials; Copilot sends structured requests and receives structured responses without direct access to underlying systems.
    • No context window stuffing — instead of pasting large files or API responses into chat, Copilot calls a tool that returns only the relevant slice of data.

    MCP vs Skills vs Built-in Tools

    MechanismLives inInvoked byBest for
    Built-in toolsCopilot clientModel automaticallyFile reads, terminal runs, web search — bundled actions
    Skills (SKILL.md)Workspace / user folderSemantic keyword matchDomain knowledge, team playbooks, long prompts loaded on demand
    MCP serversExternal process or remote URLModel calls a named toolLive data, authenticated APIs, stateful operations, cross-app actions

    Architecture Overview

    • MCP Host — the Copilot client (VS Code, GitHub.com, CLI). It manages MCP server connections and proxies tool calls from the model.
    • MCP Server — a local or remote process that advertises tools via the MCP spec. Each tool has a name, description, and JSON Schema for its parameters.
    • Transport — communication between host and server uses either stdio (local subprocess) or SSE / HTTP (remote service).
    • Tool call flow — model decides a tool is relevant → host sends a JSON-RPC tools/call request → server executes → host returns result to model → model incorporates into its response.

    Configuring MCP Servers

    MCP servers are declared in a JSON configuration file that the Copilot host reads on startup. VS Code uses .vscode/mcp.json (workspace-scoped) or the user settings.json (global). GitHub.com and the CLI use their own config locations but follow the same schema.

    VS Code — Workspace Config (.vscode/mcp.json)

    {
  "servers": {
    "github": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${env:GITHUB_PAT}"
      }
    },
    "postgres": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres",
               "postgresql://localhost/mydb"]
    },
    "azure-devops": {
      "type": "sse",
      "url": "https://my-mcp-proxy.example.com/azure-devops/sse",
      "headers": {
        "Authorization": "Bearer ${env:ADO_TOKEN}"
      }
    }
  }
}

    VS Code — User Settings (settings.json)

    {
  "github.copilot.chat.mcp.servers": {
    "filesystem": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem",
               "/Users/me/projects"]
    }
  }
}

    Configuration Fields

    FieldRequiredDescription
    typeYesstdio (local subprocess) or sse (remote HTTP/SSE endpoint).
    commandIf stdioExecutable to launch (e.g. node, npx, python, a compiled binary).
    argsIf stdioArray of command-line arguments passed to the executable.
    urlIf sseFull URL of the remote SSE endpoint.
    envNoEnvironment variables injected into the subprocess. Use ${env:VAR} to reference host environment variables rather than hardcoding secrets.
    headersIf sseHTTP headers sent with every request to the remote server (e.g. auth tokens).

    Stdio vs SSE — When to Use Which

    TransportUse when…Trade-offs
    stdioServer runs locally (Node, Python, Go binary)Zero network latency; server starts/stops with the IDE; easiest to develop and debug
    sseServer is a shared remote service or needs centralised authAccessible from any machine; requires network; manage availability and TLS yourself

    Security Best Practices

    • Never hardcode credentials — always use ${env:VAR} references and store secrets in your OS keychain, a .env file (gitignored), or a vault.
    • Least-privilege tokens — create dedicated tokens with only the scopes the MCP server actually needs (e.g. read-only GitHub token for a search server).
    • Validate server provenance — only install MCP servers from trusted publishers; review the package code before running unknown packages with npx -y.
    • Workspace vs user scope — put team-shared servers in .vscode/mcp.json (committed); put personal or credential-bearing servers in user settings (never committed).
    • Remote server TLS — SSE endpoints must use HTTPS in non-local environments; avoid plain HTTP over untrusted networks.
    🔑 The most common MCP misconfiguration is checking a token directly into .vscode/mcp.json. Always use ${env:MY_TOKEN} and set the variable in your shell profile or CI secret store.

    Tool Discovery

    Once an MCP server is configured and running, Copilot automatically queries it for its available tools via the tools/list RPC call. The server responds with a manifest of each tool — name, description, and parameter schema — which Copilot uses to decide when and how to call it.

    How Copilot Selects a Tool

    1. User sends a message — e.g. "Show me the open PRs on the main branch".
    2. Model scans the tool manifest — it evaluates each tool's name and description against the user's intent.
    3. Model constructs a tool call — it generates a JSON payload matching the tool's parameter schema.
    4. Host executes the call — the MCP host routes the request to the appropriate server and returns the JSON response.
    5. Model synthesises the answer — the tool result is injected as context and the model formulates its final response.

    Writing Effective Tool Descriptions

    The model cannot see your server's source code — it only sees the tool name and description. A well-written description dramatically improves how reliably Copilot picks the right tool.

    PrinciplePoor exampleBetter example
    State the action verbPR dataList open pull requests for a repository
    Name key parametersGet issuesSearch GitHub issues by label, assignee, or state
    Describe the return valueRun a queryExecute a SQL query and return rows as JSON
    Distinguish from similar toolsRead fileRead a file from the local filesystem (use for source code, config, logs)
    Include domain keywordsGet dataFetch Azure DevOps work items by sprint or area path

    Inspecting the Tool Manifest

    You can inspect what tools an MCP server advertises directly from VS Code:

    1. Open the Command Palette (Ctrl/Cmd+Shift+P) → MCP: List Servers.
    2. Select the server → Show Tools to see the full manifest including each tool's parameter schema.
    3. Use MCP: Restart Server after modifying a server's tool list to force a re-discovery.

    Tool Namespacing and Conflicts

    • When multiple MCP servers expose a tool with the same name, Copilot qualifies calls with the server name (e.g. github.search_issues vs jira.search_issues).
    • Give each server a descriptive key in the config (e.g. "github-readonly", "postgres-analytics") — this becomes the namespace prefix and affects how the model references tools.
    • Avoid generic tool names like get, search, run — they clash across servers and confuse selection.

    Debugging Tool Calls

    • VS Code Output panel → select GitHub Copilot (MCP) channel to see raw tool call requests and responses in real time.
    • Tool call transparency — Copilot shows which tool it called and the arguments used in the chat response (look for the collapsed "Used tool" disclosure).
    • Server logs — for stdio servers, add console logging to your server code; output appears in the MCP output channel.
    • Schema validation errors — if the model generates a malformed call, the host returns a structured error; check the output channel for INVALID_PARAMS messages and tighten your parameter schema descriptions.

    Error Handling & Fallback Behaviour

    MCP tool calls can fail in several ways — knowing how Copilot responds prevents silent issues:

    Failure TypeWhat Copilot DoesHow to Resolve
    Tool returns an error JSONInjects the error message into context; may attempt a different tool or ask the user for clarificationImprove error messages in your server code — make them actionable (e.g. "Permission denied: token needs repo:read scope")
    Tool call times outReports timeout to the user; does not automatically retryAdd a timeout parameter to your tool and return a partial result rather than hanging
    Server is unreachableShows a "Server unavailable" warning; skips the tool and proceeds without itCheck MCP: List Servers status; use MCP: Restart Server to reconnect
    INVALID_PARAMS from schema mismatchLogs the error in the MCP output channel; the model may retry with adjusted argumentsInspect the Output panel for the exact schema violation; tighten descriptions of optional vs. required parameters
    Server crashes mid-sessionMarks the server as stopped; tool calls to that server fail until restartConfigure "autoRestart": true in the server config (stdio servers only) so VS Code restarts the process automatically
    💡 MCP tool failures are non-fatal — Copilot will try to answer using whatever context it has, noting what it couldn't retrieve. Build tool descriptions and error messages to guide recovery: tell the model (and the user) why a call failed and what action would fix it.
    🛠 If Copilot isn't calling your MCP tool when you expect it to, the description is almost always the culprit. Rewrite it to explicitly match the user phrasing you expect — treat it like writing a search-engine meta description, not an API comment.

    🧩 Plugins

    • Per workspace — right-click → Disable (Workspace) to suppress it only in the current project without affecting other workspaces.

    Updating Plugins

    • VS Code auto-updates extensions by default. To control update behaviour: Settings → Extensions → Auto Update.
    • To update a specific plugin manually: Extensions view → filter by Outdated → click Update next to the plugin.
    • To pin a plugin at a specific version: right-click → Install Another Version → select the version → then disable auto-update for that extension.

    In enterprise environments, track which Copilot plugins are installed across the team to manage security and licensing:

    • Extensions view → filter "Installed" — manually review the list; look for the Copilot chat participant icon to identify Copilot-contributing plugins.
    • .vscode/extensions.json unwantedRecommendations — list extension IDs here to suppress VS Code prompts to install them in this workspace.

    TermDefinitionWhere used
    Agent A named AI persona defined in a .agent.md file. Agents combine a system prompt, tool permissions, model selection, and optional skills into a reusable workflow mode invoked via @agent-name in chat. Agents section
    applyTo A glob pattern in an instruction file's YAML frontmatter that controls which files trigger automatic inclusion of that instruction. E.g. applyTo: "**/*.ts" applies the instruction whenever a TypeScript file is in context. Instructions section
    Chat Participant A named @handle in Copilot Chat backed by a VS Code extension or GitHub App. Chat participants can receive user messages and respond with structured output, code, or UI actions. Plugins section
    Context Provider A plugin capability that automatically injects structured data (e.g. open tickets, sprint board, live metrics) into Copilot's context without the user needing to attach files manually. Plugins section
    copilot-instructions.md The repository-level instruction file at .github/copilot-instructions.md. Always included in Copilot's context for any request made in that repository — the highest-priority persistent instruction file. Instructions section
    Frontmatter YAML metadata block at the top of a .md file enclosed by --- delimiters. Used in .agent.md, .prompt.md, and .instructions.md files to declare metadata like name, description, applyTo, and mode. All customization files
    Hook An event-driven trigger that automatically runs a .prompt.md or agent workflow when a specific IDE event fires — such as saving a file, creating a commit, or completing a build. Configured in .github/copilot/hooks.yml. Hooks section
    Inline Suggestion The ghost-text completion Copilot offers as you type in the editor (not in chat). Accepts with Tab. Influenced by open files, instructions, and cursor context but not by skills or agents. General Copilot concepts
    Instructions file (.instructions.md) A Markdown file with optional applyTo frontmatter that injects persistent rules, conventions, or constraints into Copilot's system prompt. Stored in .github/instructions/ or .copilot/instructions/. Instructions section
    MCP (Model Context Protocol) An open standard that lets Copilot call external tools via a structured JSON-RPC protocol over stdio or SSE. MCP servers expose tools Copilot can invoke to read/write data or trigger actions in external systems. MCP section
    MCP Server A standalone process (any language) that implements the MCP protocol. Configured in .vscode/mcp.json or user settings. Copilot discovers its available tools automatically at session start. MCP section
    Mode The interaction model for an agent: ask (read-only conversation), edit (can modify files), or agent (full agentic loop with tool use and multi-step planning). Set in .agent.md frontmatter. Agents section
    Plugin A VS Code extension or GitHub App that extends Copilot's UI surface — adding chat participants (@name), slash commands (/command), context providers, or Code Lens actions. Installed through the VS Code Marketplace or GitHub Marketplace. Plugins section
    Prompt file (.prompt.md) A reusable prompt template stored in .github/prompts/ or .copilot/prompts/. Can be invoked by name in chat (/prompt-name), by a hook, or by another agent. Supports ${{ variable }} interpolation. Prompts section
    Skill A domain knowledge package consisting of a SKILL.md file and optional supporting assets, stored in a named folder. Loaded on demand when Copilot's routing logic matches the user's request to the skill's description. Skills section
    Slash Command A /keyword shortcut in Copilot Chat that triggers a specific behaviour. Built-in commands include /explain, /fix, /tests. Plugins can register additional slash commands. Plugins section
    stdio transport An MCP connection method where VS Code spawns the MCP server as a child process and communicates via standard input/output streams. Simpler and more secure than SSE — preferred for local tools. MCP section
    SSE transport Server-Sent Events — an MCP connection method where VS Code connects to an already-running HTTP server via a URL. Used for remote or shared MCP servers accessible over a network. MCP section
    System Prompt The hidden instructions Copilot receives before every conversation. Includes VS Code's base instructions plus any applicable instruction files, agent definitions, and skill content. Not directly visible to users. Instructions, Agents sections
    Tool Call When Copilot invokes an MCP tool or built-in capability (file read, terminal command, etc.) during an agentic session to gather information or perform an action, rather than answering from its training data alone. MCP, Agents sections
    Variable interpolation The substitution of ${{ variableName }} placeholders in prompt files with actual values at runtime — for example ${{ workspaceFolder }}, ${{ file }}, or custom parameters defined in the prompt's frontmatter. Prompts section
    Composability The ability to combine multiple customization files — instructions, skills, prompts, MCP servers — independently and in layers. Multiple .instructions.md files matching the same file are all applied simultaneously; MCP servers from different providers coexist in the same session. Instructions, MCP, Skills sections
    Persona The role or character that a custom agent or prompt adopts — defined in the Markdown body of an .agent.md file. E.g. "You are a meticulous security reviewer." The persona shapes tone, priorities, and constraints for that agent's responses. Agents section
    Routing The process by which Copilot (or the underlying model) decides which skill, MCP tool, or agent to invoke for a given user message. Routing is driven by matching the user's intent against each option's description field. Skills, MCP sections
    Scoped vs. global Global customizations (e.g. copilot-instructions.md with applyTo: **) apply to every request in the workspace. Scoped customizations (e.g. an .instructions.md with a narrow applyTo pattern) apply only when the active file matches that scope. Instructions section
    JSON-RPC The lightweight remote-procedure-call protocol used by the Model Context Protocol. MCP clients and servers exchange JSON-RPC 2.0 messages (tool/list, tools/call, resources/list, etc.) over either stdio or SSE transports. MCP section
