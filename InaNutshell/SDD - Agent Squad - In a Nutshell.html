    🤖 What is SDD - Agent Squad?

    intro overview

    The SDD - Agent Squad is a set of 10 specialist AI agents that each own a distinct phase of the software delivery pipeline. The Orchestrator coordinates them, humans approve at two critical gates, and all agents read constitution.md before acting.

    Core Principle
    You describe a feature in plain English. The squad writes the spec, designs the UI, implements the code, tests it, reviews it, secures it, makes it observable, documents it, and opens the PR — automatically.

    Why Use the Agent Squad?

    • ⚡ Speed: Parallelise independent work across specialist agents
    • ✅ Quality: Each agent is an expert — no generalist compromises
    • 🔒 Security: Dedicated security review on every change
    • 📊 Observability: SRE review built into the pipeline
    • 📝 Traceability: Every task linked to REQ-XXX requirements
    • 🔁 Rework loops: Failures automatically route back for correction

    Human Approval Gates

    • 🟡 Gate 1: Spec approval — human reviews spec.md before any code is written
    • 🟡 Gate 2: PR approval — human reviews the final PR before merge

    🎭 Agent 1: Orchestrator

    orchestrator pipeline conductor

    The Orchestrator is the pipeline conductor. It sequences all other agents, manages quality gates, handles rework loops, maintains the status manifest, and surfaces the final PR. The Orchestrator never writes code itself.

    Responsibilities

    • Reads tasks.json and builds the execution plan
    • Dispatches agents in dependency order
    • Monitors each agent's output for gate pass/fail
    • Routes back to the appropriate agent on failures
    • Opens the PR when all gates pass

    Key Behaviours

    • 🔀 Parallelises tasks with no dependencies on each other
    • ⏸️ Stops and waits at human approval gates (spec approval, PR approval)
    • 🔁 Rework loops: re-invokes any agent up to 5 iterations with additional context
    • 🆘 Escalates to the human after 5 failed rework iterations — with full context of what was tried

    Invocation

    Plain English:
    @orchestrator "Add export to CSV feature to the Todo App"

    From tasks file:
    @orchestrator execute tasks.json at .github/specs/my-feature/tasks.json

    Quality Gates Enforced

    • Gate 3: Validates tasks.json before dispatching (acyclic deps, all IDs valid)
    • Gate 4: Validates all tasks complete before opening PR

    📝 Agents 2–3: Planner & Designer

    planner designer spec

    Agent 2: Planner

    Transforms an ambiguous requirement into a complete, unambiguous specification. The Planner never writes code — it writes documents that enable code to be written correctly.

    What It Produces

    • spec.md — requirements (REQ-XXX) with acceptance criteria
    • plan.md — implementation steps linked to REQ-XXX
    • tasks.json — machine-readable task list with dependencies

    Key Behaviours

    • Always asks at least 3 clarifying questions before writing spec.md
    • Writes acceptance criteria that are independently testable
    • Flags open questions rather than resolving them silently
    • Refuses to proceed with unresolved mandatory decisions

    Interaction Pattern

    @planner "Add CSV export to the Todo list"

    Planner asks:
    "1. What columns should the CSV include?"
    "2. Should the filename include the current date?"
    "3. Is there a row limit for exports?"

    You answer → Planner writes spec.md

    Agent 3: Designer

    Provides UI/UX guidance for features that include a user-facing component. The Designer does not write final code — it guides the Coder.

    What It Produces

    • Component recommendations (MLDC for public-facing, Bootstrap for internal)
    • Wireframe-level descriptions of each new UI element
    • WCAG 2.0 AA accessibility requirements
    • UX concern flags if the spec has usability issues
    Note: The Orchestrator invokes the Designer only when the spec has UI-related REQ-XXX items. Skip for pure backend features.

    💻 Agents 4–5: Coder & Tester

    coder tester implementation

    Agent 4: Coder

    Implements code changes based on the approved spec, plan, and designer guidance. Produces working code that builds, follows the constitution, and references all REQ-XXX IDs.

    Key Behaviours

    • Reads constitution.md before writing any code
    • Implements each assigned task from tasks.json
    • Confirms build passes after each task
    • Tags code with // REQ-XXX comments where non-obvious
    • Does not refactor beyond what the task requires
    • Does not add unrequested features ("gold plating")

    Agent 5: Tester

    Ensures test coverage exceeds the threshold and validates that behaviour matches the spec. Generates tests that trace back to REQ-XXX requirements.

    Coverage Requirements

    • Default threshold: 85% on changed files
    • Every REQ-XXX must have at least one test validating its acceptance criterion
    • Happy path + at least one failure path per method

    Test Naming Convention

    MethodName_StateUnderTest_ExpectedBehavior

    Example:
    ExportToCsv_EmptyList_ReturnsHeaderRowOnly
    ExportToCsv_ValidItems_ContainsAllColumns

    Test Types

    • Unit: mock IRepository<T>, test service implementations
    • Integration: use TestServerFixture for HTTP-level tests
    • E2E (optional): use PlaywrightFixture for browser-level flows

    🔍 Agents 6–7: Reviewer & Security

    reviewer security OWASP

    Agent 6: Reviewer

    Reviews all code changes for defects, standards compliance, and correctness against the spec. The Reviewer does NOT fix issues — it reports them to the Orchestrator for Coder rework.

    Review Checklist

    • ☑ Follows naming conventions from constitution.md
    • ☑ Repository pattern used (no direct DbContext in services)
    • ☑ Async/await correct
    • ☑ No magic strings
    • ☑ Error handling present on all public methods
    • ☑ Logging at appropriate levels
    • ☑ All REQ-XXX requirements are implemented

    Output

    • PASS — code approved, Orchestrator proceeds
    • FAIL — specific line-level findings sent to Coder for rework

    Agent 7: Security Review

    Identifies security vulnerabilities in code changes. Blocks the PR if any CRITICAL findings remain unresolved.

    What It Checks

    • OWASP Top 10 against all changed files
    • Injection vulnerabilities (SQL, command, LDAP)
    • Authentication and authorisation checks
    • Secrets/PII in code and logs
    • XSS/CSRF for any HTML-rendering code

    Severity Levels

    LevelAction
    🔴 CRITICALOrchestrator blocks PR, routes to Coder for immediate fix
    🟠 HIGHMust be fixed before merge; Orchestrator holds PR
    🟡 MEDIUMNoted in PR, team decides fix timeline
    🟢 LOWAdvisory only — listed in PR description

    📊 Agents 8–9: SRE & Document Writer

    sre observability documentation

    Agent 8: SRE / Observability

    Ensures the code change is production-ready: logging, health checks, error handling, and monitoring are in place.

    Checks Performed

    • ☑ ILogger<T> used (not Console.Write)
    • ☑ Structured log messages (not string interpolation)
    • ☑ No PII in logs
    • ☑ Exceptions logged with the exception object
    • ☑ Health check endpoint reachable at /health
    • ☑ New dependencies (DB, external APIs) have timeouts configured

    What It Produces

    A runbook.md snippet attached to the PR describing:

    • What the new feature does operationally
    • What to look for in logs when it fails
    • How to recover

    Agent 9: Document Writer

    Produces user-facing documentation, API references, and changelog entries from implementation artifacts.

    What It Updates

    • docs/API_REFERENCE.md — new/changed endpoints
    • docs/USER_GUIDE.md — relevant sections
    • docs/CHANGELOG.md — entry from user's perspective
    • docs/README.md — if feature changes the setup process

    Quality Bar

    • CHANGELOG entries written from user's perspective (not technical jargon)
    • API docs include: endpoint URL, method, request/response schema, error codes

    🏛️ Agent 10: Constitution Generator

    constitution conventions architecture

    The Constitution Generator scans a repository and generates a populated constitution.md capturing the project's architecture, conventions, and patterns. All other agents read constitution.md before acting.

    Invocation

    @constitution-generator scan this repository and generate constitution.md

    What It Captures

    • Technology stack — runtime, framework, database, test tools
    • Folder structure — what goes where
    • Naming conventions — files, classes, methods, databases
    • Architectural patterns — DI, repository, unit of work
    • Code patterns — how services, repositories, controllers are written
    • Test conventions — test project structure, naming, fixtures
    • Key decisions — why this approach was chosen

    Why It Matters

    constitution.md is the team's "law of the land".
    Without it, agents make inconsistent choices about naming, patterns, and structure. With it, every agent produces code that looks like a human expert on your team wrote it.

    When to Regenerate

    • At the start of a new project (run first before any agent work)
    • After major refactoring changes the patterns
    • When onboarding a new service/module with different conventions

    🔄 The Orchestrated Workflow

    workflow process pipeline

    The Agent Squad follows a structured pipeline with 4 quality gates and 2 human approval checkpoints.

    Pipeline Overview

    PhaseAgentOutputGate
    1. DiscoveryConstitution Generator (if new)constitution.md—
    2. SpecificationPlannerspec.md, plan.md, tasks.json🟡 Gate 1: Human spec approval
    3. Design (UI only)Designerdesign-notes.md—
    4. ValidationOrchestratorValidated tasks.json🚦 Gate 3: Automated
    5. ImplementationCoderCode + build ✓—
    6. TestingTesterTests + coverage ≥ 85%—
    7. ReviewReviewerPASS / FAIL—
    8. SecuritySecurity ReviewNo CRITICAL findings—
    9. ObservabilitySRERunbook snippet—
    10. DocumentationDocument WriterDocs updated—
    11. PR OpeningOrchestratorPR opened🟡 Gate 4: Human PR approval

    Rework Loops

    • If Reviewer FAILS → routes back to Coder with findings
    • If Security finds CRITICAL → routes back to Coder for immediate fix
    • If Tester finds coverage gap → routes back to Coder and Tester
    • Maximum 5 rework iterations before human escalation

    Parallelisation

    The Orchestrator parallelises tasks with no dependencies.
    Example: Security Review and SRE run in parallel after Tester passes. Document Writer runs in parallel with PR prep.

    🚦 Quality Gates

    gates quality approval

    The pipeline has 4 quality gates — 2 automated and 2 human.

    GateTypeCheckBlocks?
    🟡 Gate 1 Human Spec approval — human reviews spec.md, plan.md, tasks.json Yes — Planner reworks until approved
    🟡 Gate 2 Automated Plan coverage — every REQ-XXX has at least one plan step Yes — Planner adds missing plan steps
    🚦 Gate 3 Automated tasks.json validity — acyclic deps, all IDs valid, all REQ-XXX referenced Yes — Orchestrator fixes and re-validates
    🟡 Gate 4 Human PR approval — human reviews the final pull request Yes — Coder reworks based on PR comments

    What Happens on Gate Failure

    • Gate 1 fail: Planner revises spec.md based on human feedback, re-submits for approval
    • Gate 2 fail: Planner adds missing plan steps and regenerates tasks.json
    • Gate 3 fail: Orchestrator fixes the specific issue (adds missing REQ-XXX refs, resolves circular deps)
    • Gate 4 fail: Orchestrator dispatches Coder to address PR comments, then loops back through Reviewer and Security
    Never bypass a gate.
    Quality gates are not optional. The Orchestrator will not proceed past a failed gate without either fixing the issue or escalating to the human after 5 failed rework attempts.

    🚀 Getting Started

    setup quickstart

    Prerequisites

    • GitHub Copilot Business or Enterprise licence
    • VS Code with GitHub Copilot Chat extension
    • Access to Claude Sonnet 4.6 and GPT-5.4 models in Copilot

    Step 1: Generate constitution.md

    @constitution-generator scan this repository and generate constitution.md

    Save the output to .github/memory/constitution.md

    Step 2: Install Agent Files

    Copy the agent files from the squad repository into your project:

    • .github/agents/orchestrator.agent.md
    • .github/agents/planner.agent.md
    • .github/agents/designer.agent.md
    • .github/agents/coder.agent.md
    • .github/agents/tester.agent.md
    • .github/agents/reviewer.agent.md
    • .github/agents/security-review.agent.md
    • .github/agents/sre-observability.agent.md
    • .github/agents/document-writer.agent.md
    • .github/agents/constitution-generator.agent.md

    Step 3: Run Your First Feature

    @orchestrator "Add a dark mode toggle to the application settings page"

    What Happens Next

    1. Orchestrator invokes Planner with your request
    2. Planner asks 3 clarifying questions
    3. You answer → spec.md is generated
    4. You approve the spec (Gate 1)
    5. Orchestrator dispatches Designer (if UI), then Coder, Tester, Reviewer, Security, SRE, Document Writer — all with rework loops
    6. You approve the PR (Gate 4)
    7. Merge and ship 🚀
