    🧠 Introduction to Context Engineering

    intro overview definition

    What is Context Engineering?

    Context Engineering is the discipline of deliberately designing, assembling, and managing the information made available to an AI model at inference time — so it can reason accurately, act reliably, and stay grounded in what matters most.

    One-line definition: Context Engineering is the art and science of giving AI the right information, in the right format, at the right moment.

    The term was coined to distinguish prompt engineering (writing clever instructions) from the broader systems challenge of what goes into the context window — including instructions, memory, retrieved knowledge, conversation history, tool outputs, and structured data.

    Why Context Engineering Matters

    🎯 Accuracy & Grounding

    Models hallucinate less when the right facts are within the context window.

    ⚡ Performance & Cost

    Sending fewer, more relevant tokens reduces latency and API cost.

    🤖 Agentic Reliability

    Agents that manage context well make fewer mistakes across long task horizons.

    🔒 Safety & Compliance

    What's in — and out of — context determines what the model can and cannot say.

    🔁 Consistency

    Structured context templates produce predictable, repeatable model behaviour.

    📈 Scalability

    Well-engineered context pipelines scale across users, tasks, and models.

    Context Engineering vs. Prompt Engineering

    Dimension Prompt Engineering Context Engineering
    Scope Crafting the instruction text Designing the entire information payload
    Focus Wording, tone, phrasing What data, memory, and tools to include

    Core Principles

    • 🎯 Relevance over volume. Include only what the model needs for the current task. Noise in context degrades performance.
    • 🏗️ Structure beats prose. Well-structured context (headings, sections, JSON) is easier for models to parse than long narrative paragraphs.
    • 🔄 Dynamic assembly. Context should be built at request time from live sources — not hardcoded into a static prompt.
    • ✂️ Budget consciously. Every token costs money and latency. Prioritise, compress, and prune ruthlessly.
    • 🔍 Observe and iterate. Treat context as a first-class engineering artefact — log it, evaluate it, and improve it over time.

    🏗️ Context Architecture

    architecture design structure

    What is Context Architecture?

    Context Architecture is the structural design of how information is organised, layered, and delivered to an AI model. It answers the question: "How should all the pieces of context be arranged so the model can use them effectively?"

    Good context architecture is like good software architecture — it separates concerns, defines clear interfaces between layers, and makes the system predictable and maintainable.

    The Four Pillars of Context Architecture

    🧩 Separation of Concerns

    Keep instructions, memory, retrieved data, and user input in distinct, clearly labelled slots.

    📐 Explicit Structure

    Use headings, delimiters, or XML tags so the model can reliably locate each block of information.

    ⚖️ Priority Ordering

    Place the most task-critical information near the start or end — models attend more strongly to those positions.

    🔄 Dynamic Composition

    Assemble context at request time from modular slots, not from a monolithic, hard-coded string.

    Slot-Based Architecture Pattern

    The most widely adopted pattern is the slot-based context — each context component occupies a named slot with a defined purpose, ordering rule, and token budget:

    SlotPurposePositionToken Budget
    📋 SystemRole, rules, output formatFirst5–15%
    💾 MemoryPersistent user facts, preferencesAfter system10–20%
    🔍 RetrievedRAG documents, grounding factsMiddle30–50%
    🔧 Tool OutputsAPI results, code outputMiddle–late10–20%
    🗣️ HistoryPrior conversation turnsLate10–20%
    ❓ User InputCurrent query or taskLast5–10%
    Primacy & Recency Effect: LLMs attend most strongly to content at the very beginning (system slot) and the very end (user input) of the context. Critical instructions should appear in at least one of these positions.

    🧩 Context Types & Layers

    types layers taxonomy

    Why Classify Context?

    Different types of information have different volatility, scope, and trust levels. Classifying them helps you decide how to retrieve, cache, and prioritise each kind.

    The Six Core Context Types

    📋
    System Context

    The AI's persona, capabilities, constraints, and output format rules. Stable — changes per deployment, not per request.

    Role instructions · Safety guardrails · Output format · Persona
    👤
    User Context

    Who the user is — profile, preferences, history, entitlements. Semi-stable — updated per session or interaction.

    Name · Preferences · Role · Past interactions · Subscriptions
    🎯
    Task Context

    What the user is trying to accomplish right now. Volatile — specific to the current request.

    Current goal · Constraints · Acceptance criteria · Examples
    🔍
    Retrieved / Knowledge Context

    External facts pulled in at runtime via RAG, search, or databases. Dynamic — retrieved per query.

    Documents · FAQs · Product data · Policy text · Code snippets
    🕐
    Temporal Context

    Time-sensitive information the model would not know from training. Always include current date/time for time-aware tasks.

    Current date · Time zone · Recent events · Deadlines
    🔧
    Tool / Environment Context

    Outputs from function calls, code execution, or API responses injected back into the context. Ephemeral — valid for the current turn only.

    API results · Code output · Search results · Database rows

    📐 Context Schema Design

    schema structure format

    What is a Context Schema?

    A context schema is a formal or semi-formal specification that defines the shape, ordering, and constraints of a context payload sent to an LLM. It functions like a contract between your application and the model.

    Think of a context schema the way you'd think of an API contract — it makes context predictable, testable, and easy to evolve without breaking downstream behaviour.

    Schema Design Dimensions

    🏷️ Naming

    Give each slot a clear, machine-readable name. Models respond better to labelled sections than unlabelled prose blocks.

    📏 Ordering

    Define a canonical slot order and stick to it. Consistency helps the model build positional expectations.

    💰 Budgets

    Assign max-token limits to each slot. Enforce them in your assembler to prevent any one slot from crowding out others.

    🔒 Constraints

    Specify which slots are required vs. optional, and define fallback content for missing slots.

    📄 Format

    Choose the right serialisation format for each slot: Markdown, XML tags, JSON, or plain text — matched to how the model best parses that content.

    🔢 Version

    Version your schema. Track which schema version produced which model outputs so you can isolate regressions during evaluation.

    Serialisation Format Comparison

    FormatBest ForProsCons
    Markdown Instructions, lists, structured prose Human-readable; models trained heavily on it Ambiguous nesting; fragile parsing
    XML Tags Slot delimiters, multi-document wrapping Unambiguous boundaries; widely used in system prompts Verbose; adds tokens
    JSON Structured data, tool outputs, configs Machine-parseable; typed; compact with minification Harder for models to generate long prose inside
    Plain Text Simple instructions, user messages Minimal token overhead No structure; ambiguous at scale

    🔗 Context Hierarchies

    hierarchy nesting inheritance

    What are Context Hierarchies?

    A context hierarchy is a parent–child relationship between context definitions, where child contexts inherit from parent contexts and can override or extend them. This mirrors how object-oriented inheritance works, applied to AI context payloads.

    Hierarchies let you define a base context once and specialise it for different products, user roles, or tasks — without duplicating shared instructions.

    Inheritance Rules

    📥 Inherit

    Child context automatically receives all slots from its parent unless explicitly overridden.

    ✏️ Override

    A child can replace a parent slot entirely — e.g., a product-specific system prompt replaces the generic org-level one.

    ➕ Extend

    A child can append additional content to a parent slot — e.g., adding product-specific rules after org-level compliance rules.

    🚫 Restrict

    A child can suppress or nullify a parent slot — e.g., a read-only role suppresses the "create record" tool context.

    What is Context Creation?

    Context Creation is the process of gathering, formatting, and assembling all the information that will be placed in the context window before calling the LLM. It is the first — and most critical — stage of the lifecycle.

    The quality of what goes into the context window determines the quality of what comes out. Garbage in, garbage out applies more forcefully to LLMs than to almost any other system.

    Creation Strategies

    📝 Template-Based

    Define a prompt template with named placeholders ({{user_name}}, {{retrieved_docs}}) filled at runtime. Simple, predictable, easy to version.

    🧩 Slot Assembly

    Each context type is a separate module. An assembler combines slots in a defined order. Highly composable and testable in isolation.

    ⚡ Streaming Assembly

    Build context incrementally — start sending to LLM while still fetching retrieval results. Reduces time-to-first-token in streaming applications.

    🤖 LLM-Guided Selection

    Use a fast, cheap model to determine which context slots are relevant for this specific request before assembling the full payload.

    Key Creation Principles

    🎯 Relevance First

    Only include context that is genuinely relevant to the current task. Each irrelevant token competes for attention with useful ones.

    🏷️ Always Label Slots

    Delimit every context block with a clear header or XML tag. Models perform better when they can identify the source and role of each block.

    ⏱️ Measure Creation Latency

    Context creation (especially RAG retrieval) is often the biggest contributor to end-to-end latency. Parallelise independent fetches where possible.

    🔄 Prefer Dynamic Over Static

    Avoid hard-coding context into prompts. Fetch it from live sources so it stays accurate without code changes.

    ✅ Validate Before Sending

    Check total token count, required slot presence, and schema conformance before submitting to the LLM API.

    📦 Cache Stable Slots

    Use prompt prefix caching for system prompts and stable user profiles. Dramatically reduces cost and latency for high-volume applications.

    🔧 Context Management

    management state updates

    What is Context Management?

    Context Management covers everything that happens to context over time — across turns, sessions, and deployments. It addresses how context is stored, updated, versioned, expired, and kept consistent as the conversation evolves.

    Without deliberate context management, AI systems accumulate stale information, exceed token budgets, and produce increasingly inconsistent responses over long conversations.

    The Four Management Concerns

    🗓️ Freshness

    Ensuring context reflects the current state of the world. Stale context is one of the leading causes of incorrect AI responses.

    📏 Scope

    Controlling how far back in history the model can see — by turn count, token limit, or time window.

    🔒 Consistency

    Preventing conflicting information across context slots — e.g., a user's name in memory differing from their name in the system prompt.

    💾 Persistence

    Deciding what gets written to long-term memory after each turn — facts, preferences, summaries, or entire conversation turns.

    TTL & Expiry Policies

    ⏰ Time-to-Live (TTL)

    Set explicit expiry on cached context slots. Temporal context (current date, live prices) should have a TTL of seconds to minutes.

    🔢 Turn-Based Expiry

    Tool outputs are typically valid only for the current turn. Mark them ephemeral and never persist them to long-term memory.

    🎯 Event-Based Invalidation

    Invalidate context when an underlying event occurs — e.g., a user changes their plan tier, invalidating cached entitlement context.

    📦 Prefix Cache Alignment

    Keep stable slots (system prompt, org rules) at the head of the context to maximise KV-cache hits. Never change their position between calls.

    ✂️ Context Pruning & Compression

    pruning compression summarisation

    Why Prune Context?

    Every model has a finite context window measured in tokens. Exceeding it causes errors; approaching it increases cost and latency. But token limits are not the only reason to prune — noisy or irrelevant context actively degrades model performance, even when there is budget available.

    Research consistently shows that LLMs struggle to find relevant information buried in large context windows — a phenomenon called the "lost in the middle" problem. Pruning improves both accuracy and cost simultaneously.

    Pruning vs. Compression

    ✂️ Pruning

    Removing entire context chunks that are irrelevant, outdated, or redundant. Hard cuts — the content is discarded entirely.


    Example: dropping conversation turns older than 10 turns

    🗜️ Compression

    Condensing context to fewer tokens while preserving key information. Soft reduction — semantics are retained, verbosity is reduced.


    Example: summarising 10 turns into a 3-sentence summary

    Pruning Techniques

    🪟 Sliding Window

    Keep only the most recent N turns or K tokens of history. Simple and predictable.

    📊 Relevance Scoring

    Score each context chunk against the current query using embedding similarity. Drop low-scoring chunks first.

    🏷️ Slot Priority Ordering

    Assign each slot a priority rank. When budget is exceeded, drop lowest-priority slots first.

    🔁 Deduplication

    Remove chunks that are near-duplicate of each other or of existing memory. Common in multi-document RAG.

    ⏰ TTL-Based Expiry

    Automatically prune context slots that have exceeded their time-to-live threshold.

    🎯 Query-Focused Selection

    Re-rank retrieved chunks against the specific current question rather than a generic embedding of the conversation.

    Compression Techniques

    TechniqueDescriptionToken ReductionQuality Loss
    Extractive Summary Select the most important sentences verbatim 40–70% Low
    Abstractive Summary LLM rewrites content in fewer words 60–90% Medium
    Entity Extraction Distil to key facts: names, dates, decisions 70–95% High (loses narrative)
    Structured Distillation Convert prose to a compact structured format (JSON, bullet list) 30–60% Low–Medium

    Anti-Patterns to Avoid

    🚫 Context Stuffing

    Dumping all available data into the context window hoping the model finds what it needs. Degrades accuracy and explodes cost.

    🚫 Hard-Coded Instructions

    Embedding business rules directly in prompts as static text. Impossible to update without redeployment; drifts from source of truth.

    🚫 Unlabelled Blocks

    Concatenating context blocks without headers or delimiters. Models cannot distinguish between instructions, data, and examples.

    🚫 Single Monolithic Prompt

    One giant prompt string concatenated at runtime. Cannot be tested, versioned, or optimised slot-by-slot.

    🚫 Instruction Repetition

    Repeating the same instruction in multiple places "for emphasis." Consumes tokens without benefit and may confuse models.

    🚫 Ignoring Token Costs

    Treating context as free. In high-throughput systems, every unnecessary token in the prompt multiplies into significant cost.

    💡 Prompting Patterns

    prompting few-shot chain-of-thought zero-shot

    What Are Prompting Patterns?

    Prompting Patterns are techniques for structuring the instructional and exemplar portions of context to guide LLM behaviour. They are the most directly impactful category of context engineering — small changes in how instructions are framed can dramatically change output quality.

    The Core Prompting Patterns

    🎯 Zero-Shot

    Instruct the model to perform a task with no examples. Relies entirely on pre-trained knowledge. Fast and cheap; works best with simple, well-defined tasks.

    "Classify this email as spam or not spam."

    📋 Few-Shot

    Provide 2–8 input/output examples before the task. The model learns the expected format, tone, and reasoning style from examples. Most reliable for structured outputs.

    "Input: 'I love it!' → Output: positive\nInput: [new] → Output: ?"

    🧠 Chain-of-Thought (CoT)

    Ask the model to reason step-by-step before giving a final answer. Dramatically improves accuracy on multi-step reasoning, math, and logic tasks.

    "Think step by step..." or show a CoT example

    🎭 Role Prompting

    Assign the model an expert persona. "You are a senior insurance underwriter..." Primes the model to activate domain-specific knowledge and adopt appropriate vocabulary.

    📝 Scratchpad

    Instruct the model to use a <scratchpad> or <thinking> block for intermediate reasoning before producing the final answer. Separates reasoning from output.

    🔁 Self-Consistency

    Generate multiple independent reasoning paths (multiple completions), then take a majority vote on the final answer. Reduces variance on ambiguous tasks.

    🌲 Tree-of-Thought (ToT)

    Explore multiple reasoning branches in parallel, evaluate each branch, and select the most promising path to continue. Best for planning and search problems.

    🔄 ReAct

    Reason + Act. Interleave reasoning steps with tool-use actions. The model reasons about what to do, acts (calls a tool), observes the result, and reasons again.

    Few-Shot Example Selection

    The quality of few-shot examples is as important as the pattern itself. Follow these principles:

    🎯 Diversity

    Cover edge cases and varied inputs, not just happy-path examples. Models learn failure modes from diverse examples.

    📏 Consistency

    All examples must follow the exact same input/output format. Inconsistency confuses the model about the expected structure.

    🔢 Count

    2–5 examples is usually sufficient. More examples help for complex tasks but have diminishing returns above 8–10.

    📐 Relevance

    For dynamic few-shot, retrieve examples semantically similar to the current input at runtime rather than using static examples.

    🔗 Chaining & Composition

    chaining composition pipelines

    What is Context Chaining?

    Context Chaining is the pattern of passing the output of one LLM call as input context to the next. Instead of one massive prompt, the task is decomposed into a pipeline of focused steps — each with its own tightly scoped context window.

    Chaining trades latency for quality and scalability. A chain of small, focused LLM calls typically produces more accurate, auditable, and controllable results than a single monolithic call.

    Core Chain Architectures

    ➡️ Sequential Chain

    Each step takes the prior step's output as its input. The simplest and most common pattern. Useful for multi-stage transformations: extract → transform → format.

    🗺️ Map-Reduce Chain

    Process multiple chunks in parallel (map), then combine the results in a final step (reduce). Essential for summarising or analysing documents larger than one context window.

    🔀 Router Chain

    A classifier LLM call selects which downstream chain or specialist model to invoke based on the input. Enables dynamic routing without hard-coded if/else logic.

    🌳 Branching Pipeline

    Multiple parallel chains execute simultaneously. Results are merged by a final step. Useful when independent sub-questions can be answered concurrently.

    Chain Design Principles

    • ✅ Each step in the chain should have a single, clear responsibility
    • ✅ Validate and type-check the output of each step before passing it forward
    • ✅ Log each step's input and output for debugging and evaluation
    • ✅ Parallelise independent steps — do not serialise what can run concurrently
    • ✅ Define retry and fallback behaviour for each step independently
    • ✅ Use cheaper/faster models for routing and classification steps; reserve expensive models for generation

    What Are Memory Patterns?

    Memory Patterns define how information is persisted beyond a single context window and selectively recalled into future context. They are what give AI systems the ability to "remember" users, facts, and prior interactions across sessions.

    LLMs have no built-in persistent memory — they process only what is in their current context window. All memory must be engineered externally and injected back into context at the appropriate time.

    Memory Write Patterns

    💾 Append-Only Log

    Every turn is written verbatim to an append-only log. Complete fidelity; grows without bound. Requires aggressive pruning on read.

    📝 Summarise-on-Write

    After N turns, a background process summarises old turns. The summary replaces verbatim turns. Keeps memory bounded; loses fine-grained detail.

    🎯 Entity Extraction

    After each turn, extract key entities and facts via a fast LLM call and write them to a structured store. Highly compressed; best for long-running assistants.

    🔄 Reflection Loop

    Periodically ask the model to reflect on recent interactions: "What have you learned about the user?" Write the reflection as a consolidated memory entry.

    Memory Read (Recall) Patterns

    🕐 Recency-Based

    Always load the N most recent turns. Simple; assumes recent context is most relevant. Breaks down in long sessions.

    🔍 Semantic Search

    Embed the current query and retrieve the most semantically similar past turns. Finds relevant older memories even across long sessions.

    🏷️ Tag-Based

    Each memory entry is tagged (topic, entity, sentiment). Load memories that match the tags inferred from the current query.

    🧮 Hybrid Scoring

    Combine recency, semantic relevance, and importance score into a single ranking function. More complex but produces the highest-quality recall.

    Agents vs. Chatbots: A Context Perspective

    AI agents differ from chatbots in one fundamental way: they take actions in the world — calling tools, writing files, navigating UIs, spawning sub-agents — and must track the state of those actions across many steps. This creates far richer and more complex context requirements than simple conversational systems.

    In agentic systems, context is not just conversational history — it is an operating environment. The agent's context window is its working memory, containing its goal, its plan, its past actions, their results, and the tools available to it.

    The most widely used agentic context pattern is ReAct — each step appends a Thought, an Action, and an Observation to the context:

    Unique Context Challenges in Agents

    📈 Context Growth

    Each action adds a Thought + Action + Observation triple to context. Long-running agents rapidly exhaust even large context windows without active pruning.

    🔄 State Tracking

    The agent must track which sub-tasks are complete, in-progress, or pending. Context is both the plan and the execution log simultaneously.

    🔀 Error Recovery

    When a tool call fails, the error must be in context so the agent can reason about it. Error observations must be concise but informative.

    🛡️ Injection Risk

    Tool outputs and web content injected into agent context may contain adversarial instructions. Always sanitise and delimit external content before including it.

    🤝 Multi-Agent Context

    What is Multi-Agent Context?

    In multi-agent systems, multiple LLM-powered agents collaborate on a task — each with its own context window, role, and toolset. The key engineering challenge is ensuring agents share the right information at the right time without overloading any single agent's context.

    In multi-agent systems, context engineering is a distributed problem. You must design not just what each agent knows, but how information flows between agents, who maintains the shared state, and how conflicts are resolved.

    Multi-Agent Orchestration Patterns

    🎼 Orchestrator–Worker

    A central orchestrator agent decomposes the task and delegates sub-tasks to specialist workers. Orchestrator maintains the shared plan; workers see only their assigned sub-task.

    🔗 Sequential Handoff

    Agent A completes a step and passes a structured handoff object to Agent B. Each agent sees only the handoff context relevant to its role, not the full prior history.

    🪩 Blackboard

    Agents read from and write to a shared structured state object (the "blackboard"). Each agent's context includes only the blackboard fields relevant to its task.

    🌊 Swarm

    Agents communicate peer-to-peer by passing messages. No central orchestrator. Context propagates through message-passing; each agent maintains its own local state.

    What is Tool Use Context?

    Tool Use Context covers how tool definitions are loaded into context, how tool call results are handled, and how to manage the token costs of tool-heavy agents. Tools are the bridge between the LLM's reasoning and the external world.

    Tool Definition in Context

    Modern LLM APIs accept tool schemas as a dedicated section of the context. Each tool definition includes a name, description, and parameter schema. The model decides whether and how to call them:

    // Tool schema in OpenAI function-calling format
{

    📐 Context Windows & Token Budgeting

    tokens limits budgeting window size

    What is a Context Window?

    The context window is the maximum number of tokens an LLM can process in a single inference call — encompassing both the input (prompt) and the output (completion). Everything the model knows about the current task must fit within this limit. Tokens are roughly ¾ of a word in English, so 128K tokens ≈ ~96,000 words ≈ a short novel.

    A larger context window does not mean you should fill it. Research shows that LLM accuracy degrades as context grows, especially for information placed in the middle of very long contexts. Budget ruthlessly — even when you have room to spare.

    The "Lost in the Middle" Problem

    Studies show that LLMs retrieve information most reliably from the beginning (primacy) and end (recency) of the context window. Information buried in the middle is frequently ignored — even when highly relevant.

    What Is a Token?

    🔤 English Text

    ~1 token per ¾ word. Common words are 1 token; rare or long words split into 2–4 tokens. 1,000 tokens ≈ 750 words.

    💻 Code

    More tokens per character than prose. Indentation, brackets, and keywords each tokenise differently. Minified code uses fewer tokens.

    🌍 Non-English

    Non-Latin scripts (Chinese, Arabic, etc.) typically use 2–5× more tokens per word than English. Budget accordingly for multilingual systems.

    📊 JSON / XML

    Structural characters ({}, [], quotes, colons) each consume tokens. Compact JSON uses ~20–30% fewer tokens than pretty-printed.

    Prompt Caching

    Prompt prefix caching (supported by Anthropic, OpenAI, and Google) allows the LLM provider to cache the KV (key-value) state of a stable context prefix, dramatically reducing cost and latency for repeated calls:

    💡 How It Works

    The provider detects that the first N tokens of the context are identical to a recent call and reuses the cached computation. You pay a reduced cache-read price instead of the full input price.

    💰 Cost Savings

    Cache hits typically cost 10–25% of normal input token prices. For a 128K system prompt used in 1,000 calls/day, caching can reduce costs by 60–80%.

    📌 Design Rule

    Place stable content (system prompt, user profile, document corpus) at the very start of context. Never insert dynamic content before stable content — it invalidates the cache.

    ⚠️ Cache Invalidation

    Any change to the prefix (including whitespace) invalidates the cache. Version-control your system prompts and avoid programmatic modifications to stable slots.

    Key Token Budgeting Principles

    • ✅ Always reserve output tokens before assembling input slots — never let input crowd out the response
    • ✅ Measure token counts programmatically using the model's tokeniser (e.g., tiktoken for OpenAI) — estimates are unreliable
    • ✅ Set a hard cap per slot and enforce it in the assembler — never rely on the API to truncate gracefully
    • ✅ Align stable content to the start of context for maximum prompt cache utilisation
    • ✅ Track actual token usage per call in production — usage patterns drift over time as content grows
    • ✅ Use compact serialisation formats (JSON without extra whitespace, plain text over XML) where context is tight

    🔍 Retrieval-Augmented Context

    rag retrieval augmentation

    What is RAG?

    Retrieval-Augmented Generation (RAG) is the pattern of fetching relevant documents from an external knowledge store at inference time and injecting them into the LLM's context window. It solves two fundamental LLM limitations: the knowledge cutoff date and the inability to access private or proprietary information without fine-tuning.

    RAG does not change the model — it changes the context. The LLM remains frozen; all knowledge freshness and domain specificity comes from what you retrieve and inject. This makes RAG fundamentally a context engineering problem.

    RAG vs. Alternatives

    ApproachHow It WorksStrengthsWeaknesses
    🔍 RAG Retrieve docs at runtime; inject into context Fresh data; no retraining; auditable sources; cheap to update Retrieval quality is a bottleneck; adds latency
    🎓 Fine-Tuning Train model weights on domain data Deep knowledge integration; no retrieval latency Expensive; data becomes stale; hard to update
    📄 Long Context Stuffing Load entire document corpus into context No retrieval step; simpler architecture Expensive; "lost in middle" accuracy degradation
    🛠️ Tool Calling LLM calls a search/lookup tool on demand On-demand precision; structured results Requires agent loop; higher latency per query

    RAG Architecture Variants

    📌 Naive RAG

    Embed query → search vector store → inject top-K chunks → generate. Simple, fast, but quality limited by raw chunk retrieval accuracy.

    🔧 Advanced RAG

    Adds pre-retrieval (query rewriting, HyDE) and post-retrieval (re-ranking, redundancy removal) steps. Substantially higher quality.

    🔄 Modular RAG

    Each component (indexing, routing, retrieval, re-ranking, generation) is a swappable module. Most flexible; used in production-grade systems.

    🤖 Agentic RAG

    The LLM decides when and how to retrieve, may issue multiple retrieval queries, and iterates until it has sufficient evidence. Highest quality; highest latency.

    📚 RAG Fundamentals

    rag embeddings vector database chunking

    Step 1 — Chunking

    Chunking is the process of splitting source documents into smaller pieces for indexing. Chunk size is one of the highest-impact RAG parameters — too small loses context; too large reduces retrieval precision.

    📏 Fixed-Size Chunks

    Split at a fixed token count (e.g., 512 tokens) with a sliding overlap window (e.g., 50 tokens). Simple, predictable, universally applicable.

    📑 Semantic Chunking

    Split at natural semantic boundaries — sentences, paragraphs, section headings. Preserves meaning; produces variable-size chunks.

    📂 Document Structure

    Respect the document's inherent structure: split on headings (Markdown), tags (HTML), or object boundaries (JSON). Best for structured content.

    🌿 Hierarchical Chunks

    Create parent (large) and child (small) chunks. Retrieve on child chunks for precision; inject the parent chunk for full context.

    Chunking Parameter Guidelines

    Use CaseRecommended Chunk SizeOverlapReasoning
    Q&A over dense technical docs256–512 tokens10–15%Precise answer location matters
    Conversational / general knowledge512–1024 tokens10%Broader context improves fluency
    Long-form summarisation1024–2048 tokens5%Larger chunks preserve narrative flow
    Code retrievalFunction / class boundary0–5%Natural semantic unit; splitting code mid-function is harmful
    Tabular / structured dataRow or section boundary0%Row integrity must be preserved

    Step 2 — Embedding

    Each chunk is converted to a dense vector (embedding) using an embedding model. The embedding captures the semantic meaning of the text as a point in high-dimensional space.

    🏢 OpenAI text-embedding-3

    1536–3072 dimensions. Strong English performance; multilingual support. Most widely deployed commercial option.

    🤗 sentence-transformers

    Open-source family (all-MiniLM, BAAI/bge, etc.). Run locally; no API cost. Wide variety of sizes and specialisations.

    🌐 Cohere Embed v3

    Supports 100+ languages and a search/classification task type parameter. Strong multilingual RAG performance.

    ⚡ Azure AI Search

    Integrated embedding + vector search + keyword search + re-ranking in a managed service. Reduces operational complexity.

    Beyond Keyword Search

    Semantic retrieval finds documents based on meaning rather than exact word match. A query for "car insurance premium" will retrieve documents containing "vehicle coverage cost" — because their embeddings are close in vector space, even though no words match.

    Retrieval Strategy Comparison

    StrategyHow It WorksStrengthsWeaknesses

    🔢 Dense Vector (ANN) Cosine similarity in embedding space Semantic understanding; synonym-aware Poor exact-match recall; black-box
    🔀 Hybrid Search Combine BM25 + vector scores (RRF or weighted) Best of both; highest overall recall More complex; needs score normalisation
    🌿 HyDE Generate a hypothetical answer; embed and search with it Bridges query–document gap; improves recall Extra LLM call; hallucinated answers may hurt

    Advanced Retrieval Techniques

    ✍️ Query Rewriting

    Use an LLM to rewrite the user query into a form that better matches how information is stored in the index. Especially useful when user queries are colloquial.

    💡 HyDE

    Hypothetical Document Embedding: Ask the LLM "what would a document answering this question look like?" then embed that hypothetical answer as the search query.

    🔁 Multi-Query

    Generate 3–5 rephrasings of the user query. Retrieve for each and take the union. Dramatically improves recall for ambiguous queries.

    ⚖️ Cross-Encoder Re-ranking

    After retrieving top-50 candidates, pass each (query + chunk) pair through a cross-encoder model to re-score for true relevance. Keep only top-5 for context injection.

    🌿 Parent-Child Retrieval

    Index small child chunks (high precision retrieval) but inject their larger parent chunk into context (full context, better coherence).

    🧠 Contextual Retrieval

    (Anthropic, 2024) Prepend a document-level summary to each chunk before embedding. Dramatically improves chunk relevance by adding document context to each piece.

    What is Context Injection?

    Context Injection is the final step of RAG — taking retrieved documents and inserting them into the LLM's context window in a way that maximises how effectively the model can use them. How you inject is as important as what you retrieve.

    Why Evaluate Context Quality?

    LLM output quality is largely determined by context quality. Evaluating context systematically — not just final outputs — enables faster debugging, more targeted improvements, and earlier detection of regressions. Context evaluation answers: "Did we give the model the right information, in the right format, at the right time?"

    "Evaluation is the flywheel of context engineering." Measure context quality independently from generation quality so you can fix the right component when outputs degrade.

    Context Quality Dimensions

    ✅ Relevance

    Is every piece of context in the window actually relevant to the current task? Irrelevant context reduces model focus and wastes token budget.

    🎯 Completeness

    Does the context contain all the information the model needs to answer correctly? Missing context causes hallucination or refusal.

    📐 Conciseness

    Is the context as compact as possible while retaining necessary information? Verbose context degrades reasoning and inflates cost.

    🗓️ Freshness

    Is the context up-to-date? Stale facts produce wrong answers even when the context is otherwise well-formed.

    🔒 Consistency

    Do different context slots agree with each other? Conflicting signals confuse the model and produce inconsistent outputs.

    🏷️ Structure

    Is the context clearly labelled and delimited? Well-structured context is parsed more reliably than unstructured text dumps.

    Production Context Engineering

    Moving from prototype to production means treating context as a first-class operational concern. Context payloads must be logged, monitored, cached, versioned, and optimised — the same disciplines applied to any critical data pipeline.

    Every context payload sent to an LLM in production is an observable event. If you can't inspect it, measure it, and alert on it, you don't have a production system — you have a prototype with traffic.

    Production Readiness Checklist

    📋 Context Logging
    • Log every context payload with a unique trace ID
    • Store token counts per slot
    • Capture retrieval scores and chunk IDs
    • Link context log to the output and user feedback
    📈 Metrics & Alerting
    • Alert on average context token count exceeding budget
    • Track retrieval hit-rate and average similarity score
    • Monitor p95 context assembly latency
    • Alert on zero-retrieval rate (no chunks found)
    🔄 Prompt Versioning
    • Store system prompts in version control
    • Tag each prompt version with a semantic version
    • A/B test prompt changes with traffic splitting
    • Roll back to previous version on metric regression
    ⚡ Latency Optimisation
    • Parallelise all independent context fetches
    • Enable prompt prefix caching on stable slots
    • Pre-warm embedding cache for frequent queries
    • Set per-slot SLA budgets and enforce timeouts
    💰 Cost Control
    • Track cost per call and cost per user
    • Set token budget guardrails in the assembler
    • Maximise prompt cache hit rate
    • Route simple queries to cheaper/smaller models
    🛡️ Security & Safety
    • Sanitise all user and external content before injection
    • Enforce tool call allow-lists
    • Redact PII from context logs
    • Apply content safety checks on outputs

    📖 Glossary

    terms definitions
    A comprehensive glossary of Context Engineering terminology to help you understand the key concepts and practices across the field.
    🪟 Context Window

    The maximum number of tokens an LLM can process in a single inference call, including both input prompt and output completion.

    🧠 Context Engineering

    The discipline of systematically designing, assembling, managing, and optimising what goes into an LLM's context window to maximise output quality, reliability, and cost-efficiency.

    📋 System Prompt

    The developer-controlled instructions placed at the beginning of the context window that define the AI's persona, task scope, rules, and output constraints.

    🔢 Token

    The atomic unit of text processed by an LLM. Approximately ¾ of an English word. Both input prompt and output completion consume tokens counted against the context window.

    🔍 RAG (Retrieval-Augmented Generation)

    The pattern of fetching relevant documents from an external store at inference time and injecting them into context — enabling the model to answer questions about private or recent data without fine-tuning.

    🔢 Embedding

    A dense numerical vector representation of text that captures its semantic meaning. Similar texts have similar embeddings (small cosine distance). Used as the basis of semantic search in RAG.

    ✂️ Chunking

    The process of splitting source documents into smaller text segments for embedding and indexing. Chunk size and overlap are critical parameters affecting retrieval precision.

    ⚡ Prompt Prefix Caching

    A provider feature that reuses the KV-cache state of a stable context prefix across calls, reducing cost and latency for repeated prompts with the same beginning.

    🔄 ReAct

    A prompting pattern where an agent interleaves Reasoning steps (Thought) and Actions (tool calls), appending each Observation back to context before reasoning again.

    🌿 HyDE (Hypothetical Document Embedding)

    A retrieval technique where an LLM generates a hypothetical ideal answer, which is then embedded and used as the search query — bridging the semantic gap between questions and documents.

    ⚖️ Reciprocal Rank Fusion (RRF)

    A score combination technique that merges ranked lists from multiple retrieval methods (e.g., BM25 + vector search) into a single unified ranking without requiring score normalisation.

    🧠 Chain-of-Thought (CoT)

    A prompting technique that instructs the model to reason step-by-step before producing a final answer, dramatically improving performance on multi-step reasoning tasks.

    💾 Episodic Memory

    External storage of past conversation turns and events that can be selectively recalled into future context windows. One of the four agent memory types.

    🎯 Faithfulness

    A RAG evaluation metric measuring whether the generated answer is grounded in the provided context — i.e., all factual claims are supported by retrieved documents.

    💉 Prompt Injection

    An adversarial attack where malicious instructions are embedded in user input or external content that is injected into context — attempting to override system prompt instructions.

    🗺️ Map-Reduce Chain

    A chaining pattern that processes document chunks in parallel (map) then combines the results in a final aggregation step (reduce). Used for summarising large documents.

    🏢 Context Slot

    A named, typed section of the context window with a defined purpose and token budget — e.g., "system_prompt", "user_profile", "retrieved_documents".

    📏 Lost in the Middle

    The empirical finding that LLMs recall information most reliably from the beginning and end of long context windows, with accuracy degrading for content placed in the middle.

    Foundational Papers

    📄 RAG (Lewis et al., 2020)

    "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks" — the original RAG paper from Meta AI. Introduced the retrieve-then-generate paradigm.

    📄 Chain-of-Thought (Wei et al., 2022)

    "Chain-of-Thought Prompting Elicits Reasoning in Large Language Models" — Google Brain paper demonstrating the step-by-step reasoning pattern.

    📄 Lost in the Middle (Liu et al., 2023)

    "Lost in the Middle: How Language Models Use Long Contexts" — Stanford paper identifying primacy and recency effects in long-context LLM performance.

    📄 ReAct (Yao et al., 2023)

    "ReAct: Synergizing Reasoning and Acting in Language Models" — introduced the Thought→Action→Observation loop for agentic systems.

    📄 Contextual Retrieval (Anthropic, 2024)

    Anthropic's technique of prepending document-level context summaries to each chunk before embedding, significantly improving retrieval precision.

    📄 HyDE (Gao et al., 2022)

    "Precise Zero-Shot Dense Retrieval without Relevance Labels" — introduced Hypothetical Document Embedding as a query-expansion technique.

    Context Engineering in Practice — Key Takeaways

    • ✅ Context quality is the #1 determinant of LLM output quality — invest here before anything else
    • ✅ Treat every context slot as a named, typed, budgeted component — not raw string concatenation
    • ✅ Measure retrieval quality independently from generation quality — fix the right layer
    • ✅ Place the most critical information at the start (system prompt) and end (user query) of context
    • ✅ Log every context payload in production — it is your primary debugging and improvement tool
    • ✅ Evaluate continuously with automated metrics and a curated gold test set
    • ✅ Use prompt prefix caching on stable slots — the ROI is immediate and significant
    • ✅ Never inject unsanitised external content — always delimit with XML tags and apply grounding instructions
