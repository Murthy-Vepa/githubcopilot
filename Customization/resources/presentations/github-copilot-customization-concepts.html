GitHub Copilot | Concepts presentation

Shape the work.
Shape the context.

Customization is how teams make Copilot more relevant, more repeatable, and more accountable without turning every request into a giant prompt.

The goal is not maximum customization. It is the smallest boundary that reliably improves the work.Agents, skills, instructions, prompts, hooks, MCP, and packaging
01 / Mental model

Match the tool to the kind of control you need.

Always-on guidance→Reusable task→Specialist role→Bundled procedure→Deterministic action→External capability

Context

Instructions and prompts shape what Copilot knows and how it approaches a request.

Behavior

Agents and skills shape who does the work and which procedure is followed.

Capability

Hooks and MCP connect the workflow to deterministic actions and external systems.

02 / Shape the request

Instructions set expectations.
Prompts start focused work.

Instructions

Persistent guidance in a scope

Use for standards, conventions, architecture rules, accessibility expectations, or repository context that should apply automatically.

.github/copilot-instructions.md
.github/instructions/*.instructions.md

Prompt files

Reusable task templates

Use for repeatable tasks with a clear input, process, and output. Keep the request focused and invoke it when needed.

.github/prompts/*.prompt.md

Rule of thumb: if it should apply without asking, consider an instruction. If a person chooses when to run it, consider a prompt.Scope instructions with applyTo globs (e.g. backend/**/*.cs) so they only load for matching files — the same token-optimization pattern skills use.
03 / Shape the work

Agents define a role.
Skills package a procedure.

Custom agents

A deliberate specialist

An agent combines role-specific instructions, boundaries, tools, and a model field. Delegating to an agent spins up a subagent with a fresh context window — nothing from the main conversation carries over, a major token optimization. Set model: auto for a 10% premium-request discount when task complexity varies.

.github/agents/<name>.agent.md

Agent skills

A reusable capability bundle

A skill is a folder with a focused procedure, references, scripts, and samples. Only the frontmatter (~100 tokens) always loads; the body loads when the description matches. Search the community first with gh skill search / gh skill install (200+ skills in awesome-copilot) before writing one — or run /create-skill to build your own.

.github/skills/<skill-name>/SKILL.md

Design distinction: an agent answers “who should handle this?” A skill answers “what repeatable method should be used?”
04 / Extend the workflow

Hooks automate moments.
MCP opens systems.

Hooks

Deterministic lifecycle actions, zero tokens

Hooks run a script at a lifecycle event (e.g. sessionEnd) — no LLM call involved, making them the cheapest primitive. Use them for checks an agent should never be able to skip, like secret scanning before a commit.

.github/hooks/*.json

Model Context Protocol

Tools and data beyond the repository

MCP servers expose approved tools such as issue trackers, APIs, databases, or live docs. Pick a transport that matches distribution: local (stdio, launches a CLI/binary), http (hosted server), or legacy sse.

.vscode/mcp.json

.vscode/mcp.json — example: Context7 (http transport) { "servers": { "context7": { "type": "http", "url": "https://mcp.context7.com/mcp", "headers": { "Authorization": "Bearer ${input:context7-key}" } } } }
Security boundary: treat hooks and MCP as executable capability. Every configured MCP server's tool definitions load into context on every request — before you've asked anything server-related — so only add servers you'll actually use, and keep secrets in inputs, never hard-coded.
05 / Decision framework

Start with the smallest useful boundary.

What kind of change are you trying to make?

Choose the first answer that describes the behavior. Add another primitive only when the current boundary cannot express the need clearly.

Make every request follow a ruleUse an instruction.
Run a known task on demandUse a prompt file.
Give the work a specialist ownerUse a custom agent.
Teach a multi-step methodUse a skill.
Run a predictable command at a momentUse a hook.
Reach an external systemUse MCP.
06 / Composition

Good customizations compose without hiding responsibility.

Orchestrator→Planner (auto)→✋ checkpoint→Tester (haiku)→Reviewer (sonnet)

Make inputs visible

Name the assumptions, files, permissions, and data sources the workflow expects.

Make handoffs explicit

An agents: array declares exactly which sub-agents an orchestrator may delegate to — the boundary is enforced, not just documented.

Make approval points real

Stage gates (e.g. “✋ wait for user approval before implementation”) keep humans accountable between planning and execution.

A customization is production-ready when another developer can predict when it activates, what it can do, and how to verify its result. Example: a dev-flow orchestrator coordinating Planner → Tester → Reviewer sub-agents through a plan → code → test → review → ship pipeline.
07 / Packaging

Package the working system,
not just the files.

copilot-customizations/ plugin.json README.md agents/ instructions/ prompts/ skills/ hooks/ .vscode/ mcp.json
ManifestName, version, description, and the component inventory — plugin.json for a simple bundle, or apm.yml + apm.lock.yaml via the Agent Package Manager when you need version-locked, reproducible team installs.
DocumentationPurpose, installation, prerequisites, permissions, and verification steps.
Portable pathsUse relative references and include the files needed by each skill or agent.
Safe defaultsKeep secrets out of the package. Make MCP examples illustrative unless they are configured and approved. apm install/apm audit also scan for hidden Unicode tampering.

Distributing org-wide? Plugins and APM are pull (a user installs); an org's .github-private repo is a push model for sharing agents automatically across every repo.

08 / Quality and governance

Adoption starts with trust.

Every referenced path exists and is portable.
Frontmatter, JSON, and Markdown parse cleanly.
Trigger conditions are clear to a new user.
Tools, permissions, and network access are documented.
Secrets and private endpoints are excluded.
Examples distinguish facts from recommendations.
Failure paths and recovery steps are visible.
Browser, keyboard, and narrow-layout checks pass.
Definition of done: a teammate can install the package, understand what activates, run a bounded example, and explain what a human still needs to review.
09 / Takeaway

Customize with intent.
Package with evidence.

Instructions shape expectations. Prompts focus tasks. Agents assign roles. Skills carry procedures. Hooks automate moments. MCP connects systems. Packaging makes the whole system adoptable.

The strongest Copilot customization is understandable before it is powerful, bounded before it is broad, and verified before it is shared.
