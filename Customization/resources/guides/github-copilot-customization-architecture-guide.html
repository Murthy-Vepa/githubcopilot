Customization architecture guide

Design Copilot as a system of layers, not a pile of prompts.

Use the right customization mechanism for the right responsibility: instructions establish standards, Skills package expertise, custom agents define roles, hooks enforce deterministic controls, and the SDK assembles the runtime into an application.

01 · Architecture model

Five components, five distinct jobs

A maintainable Copilot implementation separates information that should always be available from expertise that should load only when needed, role behavior, runtime controls, and application-level orchestration.

YOUR APPLICATION | Copilot SDK / CLI | +----------------+-------+--------+----------------+ | | | | Instructions Skills Custom Agents Hooks foundation capability roles enforcement | | | | +----------------+-------+--------+----------------+ | MCP servers / tools | Files, APIs, repositories, systems
LayerMental modelActivationBest forPrimary risk
InstructionsCompany bylaws or team handbookAlways-on or path-matchedConventions, standards, technology preferencesContext bloat and contradictions
Agent SkillsSpecialist training manualOn demand through matching or explicit invocationDetailed workflows, scripts, examples, referencesWeak descriptions or unsafe third-party content
Custom AgentsDedicated teammate or roleUser selected or delegatedPersona, tools, model, handoffs, sub-agentsOver-permissioning and unclear boundaries
HooksSecurity checkpoint or automation triggerLifecycle eventValidation, permission checks, logging, notificationsUnsafe scripts and false positives
Copilot SDKProgrammatic remote controlApplication invocationCustom tools, agents, permissions, MCP, workflowsPrivilege escalation and uncontrolled tool access
Architectural principle: Instructions answer “what standards apply?”, Skills answer “how is this specialist task performed?”, Agents answer “which role performs it?”, Hooks answer “what must happen or be blocked at runtime?”, and the SDK answers “how does an application compose and invoke the system?”.

Foundation

Keep global instructions short, stable, and applicable to nearly every interaction.

Capability

Move task-specific depth, scripts, templates, and references into Skills that can be loaded progressively.

Role

Give a custom agent a mission, tools, model, and collaboration contract rather than a vague persona.

Control

Use hooks and permission handlers for deterministic behavior that must not depend on model compliance.

02 · Instructions

Layer context from broad to specific

Instructions are guidance injected into Copilot context. They are the right place for stable standards, not long procedures or agent orchestration.

Six instruction types

TypeTypical locationScope and loadingUse for
Repository-wide.github/copilot-instructions.mdAlways-on for repository interactionsStack, naming, testing, architecture principles
Path-specific.github/instructions/*.instructions.mdMatched by applyTo globLanguage, framework, directory, or file-type rules
Agent instructionsAGENTS.md in the repository treeOperational guidance when an autonomous coding agent worksBuild, test, deploy, and repository procedures
Model-specificCLAUDE.md, GEMINI.mdWhen the corresponding model is activeModel-specific conventions or compatibility notes
PersonalVS Code user settingsAcross a developer's workspacesIndividual preferences that should not be committed
OrganizationGitHub organization settingsOrganization-wide where supportedShared standards and governance expectations

Repository-wide instruction example

# Project standards - Use TypeScript strict mode for all .ts and .tsx files. - Prefer pnpm over npm for package management. - Add tests for every new public function. - Follow the repository's conventional commit format. - Never commit secrets, tokens, or local environment files. - Run the focused test before running the full suite.

Path-specific instruction example

--- applyTo: "**/*.py" excludeAgent: "code-review" --- - Use Python 3.12 or newer. - Add type hints to public functions. - Prefer pytest fixtures over test setup duplication. - Run `ruff check` and the focused pytest module for Python changes.

Precedence is composition, not a license for contradiction

Personal preferences highest local influence | Repository-wide copilot-instructions.md always-on standards | Path-specific *.instructions.md conditional rules | AGENTS.md autonomous operations | Skills matched expertise | Custom agent prompt selected role behavior

Applicable instructions are provided together. Treat the layers as complementary and remove conflicts instead of relying on a hidden precedence trick.

Keep it concise

Use roughly 5–15 core repository rules. A global file should usually fit in about 200–500 tokens.

Prefer durable rules

Write principles that remain true across features, contributors, and model versions.

Use applyTo deliberately

applyTo: "*" can target all files while remaining conditional on an active file context. It is not identical to a repository-wide instruction file.

Do not embed runbooks

Move lengthy procedures, code examples, and multi-step workflows to Skills or prompt files.

Common failure: putting “when X happens, invoke agent Y, then run Z and update W” in copilot-instructions.md. This wastes context on unrelated tasks and asks a probabilistic model to perform orchestration that belongs in an explicit workflow mechanism.
03 · Agent Skills

Package expertise with progressive disclosure

Agent Skills are reusable task capabilities. Their design goal is to make specialist knowledge available when relevant without placing every detailed procedure in every interaction.

Three-tier loading model

TierContentLoading behaviorDesign target
1. Metadataname and description in YAML frontmatterAvailable for skill discoveryAbout 50–100 tokens; describe both capability and trigger condition
2. BodySKILL.md instructionsLoaded when Copilot determines the Skill is relevant or the user invokes itConcise quick-start and decision flow; keep detailed reference content out of the body
3. ReferencesFiles under references/, scripts, assets, templatesLoaded only when the Skill directs Copilot to themSmall, focused files that answer one specialized question

Recommended directory structure

.github/skills/webapp-testing/ ├── SKILL.md # Required entry point ├── LICENSE.txt # Recommended for shared Skills ├── scripts/ │ ├── helper.py │ └── helper.ps1 ├── references/ │ ├── visual-testing.md │ └── debugging-guide.md ├── assets/ │ └── baseline.png └── templates/ └── scaffold.py

SKILL.md example

--- name: webapp-testing description: > Toolkit for testing local web applications with Playwright. Use when asked to verify frontend behavior, debug UI issues, capture screenshots, or check visual regressions. --- ## Quick start 1. Run `npx playwright install` when browsers are missing. 2. Start the application using the repository's documented command. 3. Run the focused test or use the browser workflow. ## Choose a workflow - For visual regression, read `references/visual-testing.md`. - For debugging, read `references/debugging-guide.md`. - Use scripts in `scripts/` instead of rewriting repeated setup steps.
Description quality controls discovery: state what the Skill does, when it should trigger, and what kinds of work it supports. A vague description creates both false positives and false negatives.

Skill design rules

  • Make the first screen useful: include a quick start and the first decision.
  • Use references for API details, edge cases, and long examples.
  • Keep scripts deterministic, documented, and safe to run in a clean workspace.
  • Do not assume an undocumented working directory, secret, or installed binary.
  • Include a verification step and tell the agent what success looks like.
  • Audit third-party Skills before adding them to a trusted organization repository.
04 · Custom Agents

Define roles and collaboration contracts

Custom Agents specialize Copilot for a role. Their configuration can restrict tools, select a model, expose handoffs, and allow a parent agent to delegate bounded sub-tasks.

Configuration fields

FieldResponsibilityExample
nameDisplay and invocation nameSecurity Reviewer
descriptionRole purpose and recommendation signalReviews code for security vulnerabilities
toolsAllowed tool whitelist['read', 'search']
modelModel selection or fallback list['Claude Sonnet', 'GPT']
handoffsUser-visible transitions to another rolePlanner to Implementer
agentsSub-agent names a parent may invoke['Researcher', 'Implementer']

Handoff: human-guided relay

A handoff is a visible transition. One agent completes its work, then the user clicks a button to move to the next role with a preset prompt and conversation context.

--- name: Planner description: Generate implementation plans from requirements tools: ['search', 'fetch'] handoffs: - label: Start Implementation agent: Implementer prompt: Implement the plan above. send: false --- You are a planning specialist. Research the repository, identify affected files, write a step-by-step plan, and list focused tests. Stop when the plan is ready for a human to review.
User selects Planner | v Planner researches and writes plan | v [Start Implementation] - human confirms Implementer receives plan and writes changes | v [Review Code] - human confirms Reviewer evaluates implementation

Sub-agent: autonomous delegation

A parent agent can invoke a whitelisted sub-agent as a bounded task. The sub-agent runs in an isolated context and returns a result to the parent. Include agent in the parent's tools and enumerate permitted agents.

--- name: Feature Builder description: Research and implement features with a quality review tools: ['agent', 'editFiles', 'search'] agents: ['Researcher', 'Implementer', 'CodeReviewer'] --- For each task: 1. Ask Researcher for relevant patterns and dependencies. 2. Ask Implementer to make the smallest change. 3. Ask CodeReviewer for security, quality, and test feedback. 4. Fix concrete findings and run the focused validation.
DimensionHandoffSub-agent
TriggerUser clicks a buttonParent agent invokes programmatically
ControlHuman-drivenAgent-autonomous
ContextShared conversation historyIsolated context with explicit handoff input
User experienceVisible agent switchUsually transparent to the user
Best suited forPlan, implement, review pipelines that need approvalResearch, parallel scans, automated review loops
DepthCan continue through user transitionsSingle-level delegation; sub-agents cannot recursively spawn more sub-agents

Choose the collaboration mode

  • Plan to implement to review: use handoffs when each stage needs human confirmation.
  • Research plus implementation: use a sub-agent when research is an auxiliary step.
  • Parallel independent scans: use multiple bounded sub-agents and aggregate their results.
  • Automated review loop: let a parent invoke a read-only reviewer, fix findings, and rerun validation.
  • Domain role with a visible decision: use a handoff so the user can inspect the output before proceeding.
Least privilege applies to roles: a planner usually needs search and fetch, not edit. A reviewer generally needs read and search, not shell or write access. A parent that can invoke agents should have a narrow whitelist.
05 · Hooks

Put deterministic controls at the runtime boundary

Hooks are code, not prompts. They run when a configured lifecycle event fires and can validate, block, record, or prepare an operation without spending model tokens.

Common hook events

EventWhen it runsUseful behavior
sessionStartSession beginsLoad environment context or validate prerequisites
userPromptSubmittedUser submits a promptRecord metadata, normalize context, or apply request policy
preToolUseBefore a tool invocationValidate parameters, approve safe commands, block protected paths
postToolUseAfter a tool invocationRun focused checks, record result, format generated files
sessionEndSession endsAggregate redacted logs or send a notification
onErrorWhen configured execution failsRetry safely, degrade gracefully, or surface a diagnostic

Hook versus instruction

QuestionUse an instruction when...Use a hook when...
What is the rule?The model should understand a convention or preference.The host must enforce a deterministic condition.
Can a model forget it?It is acceptable to provide guidance and let the model apply judgment.It is not acceptable to rely on model compliance.
Does it consume context?Yes, it is supplied to the model.No model tokens are required for the code-level check.
What does failure mean?The response may be less consistent.The operation should stop, warn, or enter a defined recovery path.

Example hook policy

{ "hooks": { "preToolUse": [ { "matcher": "shell", "command": "pwsh -File .github/hooks/check-command.ps1", "timeout": 5 } ] } } # check-command.ps1 param([Parameter(ValueFromPipeline = $true)] $Event) $command = $Event.toolInput.command if ($command -match 'git reset --hard|Remove-Item|DROP TABLE') { Write-Output '{"decision":"deny","reason":"Destructive operation requires approval."}' exit 0 } Write-Output '{"decision":"allow"}'
Review hook code as production security code: validate JSON, escape shell inputs, avoid secret logging, bound network calls, use least privilege, and test case, whitespace, encoding, and path variations.
06 · Placement

Put each workflow where it naturally belongs

The most common architecture mistake is placing every procedure in the always-on instruction file. Choose based on activation, human control, detail, and determinism.

Workflow needRecommended mechanismReason
Global coding standardscopilot-instructions.mdThe only content that should be broadly always-on.
Language or directory rules*.instructions.mdLoaded only for matching files.
Build, test, and deploy steps for an autonomous agentAGENTS.mdOperational guidance for coding-agent work.
Detailed task procedureSKILL.mdOn-demand expertise with scripts and references.
User-triggered repeatable command*.prompt.mdExplicit slash-command invocation.
Plan, implement, review with approvalCustom agent plus handoffsVisible, deterministic human gates.
Research, parallel scans, or automated review loopParent custom agent plus sub-agentsProgrammatic delegation with isolated context.
Permission, validation, or audit controlHook or SDK permission handlerDeterministic code-level boundary.
Reusable application workflowCopilot SDKProgrammatic composition with explicit permissions and tools.

Why workflows do not belong in global instructions

  1. Token waste: complex procedures occupy context even for unrelated questions.
  2. Separation of concerns: standards and orchestration change at different rates and have different owners.
  3. Unreliable execution: a model may skip or reinterpret a long procedural instruction.
  4. Poor discoverability: users cannot easily tell which operation is a standard, a Skill, a prompt, or an agent transition.
  5. Harder governance: a single global file becomes a conflict zone for every team.
Rule of thumb: if content is needed in nearly every interaction, use Instructions. If it is needed only for specific tasks, use a Skill or Prompt. If it involves inter-agent collaboration, use a Custom Agent and choose Handoff or Sub-agent based on human control. If it must happen regardless of model wording, use a Hook.
07 · Project structure

Make the architecture visible in the repository

A clear directory layout lets contributors discover the right customization mechanism and review changes at the correct boundary.

your-project/ ├── .github/ │ ├── copilot-instructions.md # Global standards │ ├── instructions/ │ │ ├── typescript.instructions.md # applyTo: **/*.ts │ │ ├── python.instructions.md # applyTo: **/*.py │ │ └── security.instructions.md # Security-sensitive paths │ ├── agents/ │ │ ├── planner.agent.md # Handoff -> Implementer │ │ ├── implementer.agent.md # Handoff -> Reviewer │ │ ├── reviewer.agent.md # Read-only review role │ │ └── feature-builder.agent.md # Parent with sub-agents │ ├── skills/ │ │ ├── ci-debugging/ │ │ │ ├── SKILL.md │ │ │ └── references/common-errors.md │ │ └── db-migration/ │ │ ├── SKILL.md │ │ └── scripts/generate-migration.sh │ ├── prompts/ │ │ ├── plan-feature.prompt.md │ │ └── generate-endpoint.prompt.md │ └── hooks/ │ ├── check-command.ps1 │ └── README.md ├── AGENTS.md # Agent operational procedures ├── CLAUDE.md # Model-specific guidance, if needed ├── src/ ├── tests/ └── docs/

Example ownership map

AssetSuggested ownerReview question

08 · Token strategy

Spend context where it creates capability

Token consumption is an architecture concern. Always-on content competes with the task, while on-demand content can remain deep without affecting unrelated interactions.

ComponentTypical loadingCost behaviorOptimization
Repository instructionsAlways-onConsumed on every relevant invocationKeep to stable rules and remove duplicate examples.
Path instructionsConditionalConsumed when file context matchesSplit by language or framework; keep globs narrow.
AGENTS.mdAgent operationConsumed when an autonomous agent worksKeep build/test commands concise and executable.
Skill metadataAvailable for discoverySmall persistent description footprintWrite precise trigger descriptions.
Skill bodyOn demandConsumed on matchMove long content to references and scripts.
Custom agent promptWhen selectedCan become large and role-specificState mission, decision process, output contract, and boundaries.
HooksEvent-triggeredCode-level execution; no model prompt tokensUse for deterministic checks instead of repeating instructions.
Sub-agentDelegation-triggeredIsolated context; does not accumulate parent historyPass a compact task packet and return structured findings.
Lower context cost Higher context cost Hooks -------- Path instructions -------- Repo instructions -------- Skills -------- Agent prompt 0 tokens conditional always-on on match selected role

Strategic principles

  • Never make always-on what can be loaded on demand.
  • Never use Instructions when a Hook can enforce the rule without model involvement.
  • Never put detailed procedures in Instructions when a Skill can provide them only for matching tasks.
  • Write Skill metadata for true-positive discovery and low false-positive loading.
  • Keep global Instructions stable so the repository context remains predictable.
  • Pass sub-agents only the context they need; do not copy the entire parent conversation into every delegation.
09 · Security

Treat customization as executable policy

Customization files influence what an agent sees, what it can invoke, and what it can change. Review them as part of the repository's security boundary.

SurfacePrimary threatControls
InstructionsPrompt injection or malicious repository guidanceVersion control, code review, ownership, short stable content.
SkillsUntrusted scripts, references, or package installationAudit source, pin dependencies, sandbox execution, test with least privilege.
Custom AgentsOverly broad tools or agent delegationExplicit tool whitelist, narrow agent whitelist, separate read and write roles.
HooksCommand injection, unsafe parsing, secret leakageValidate structured input, avoid shell interpolation, redact logs, bound timeouts.
SDKPrivilege escalation through tools or permission callbacksDefault deny, explicit permission handlers, isolated runtime, approved MCP servers.
MCP serversUntrusted external tool behavior or data exfiltrationApproved servers, narrow tools, documented data flow, network controls, audit logs.

Security design principles

  1. Default deny: an agent should not execute shell commands, read or write files, or fetch URLs unless the runtime explicitly approves them.
  2. Least privilege: grant only the tools and scopes required for the role or task.
  3. Isolation: use containers or Dev Containers for agents with shell, file, or dependency-installation access.
  4. Auditability: record tool invocations and permission outcomes without logging secrets.
  5. Human control: place high-impact transitions behind handoffs or interactive approval.
  6. Recovery: document how to disable a broken customization without removing all protections.
Prompt injection is an architecture concern: instructions and Skill content can be treated as data by an attacker if they are loaded from an untrusted source. Review third-party content, avoid blindly executing repository-provided scripts, and keep privileged operations behind code-level permission checks.
10 · Copilot SDK

Assemble the layers inside an application

The Copilot SDK gives an application programmatic control over sessions, custom agents, Skills, MCP servers, and permission handling. It is the composition layer rather than another replacement for repository customization.

Runtime architecture

Your application | v SDK client ---- JSON-RPC ----> Copilot CLI server mode | | |-- custom tools |-- built-in fs / git / shell |-- custom agents |-- MCP servers |-- permission handler |-- auto-discovered instructions |-- Skill directories |-- AGENTS.md and repository context

Session-level instruction injection

const session = await client.createSession({ model: "claude-sonnet-4.5", instructions: `You are a code analysis specialist. Follow these rules: - Focus on security, performance, and maintainability. - Rate each finding from 1 to 5. - Provide evidence and an actionable next step.`, });

Filesystem auto-discovery

# The CLI scans the working directory for project guidance: # .github/copilot-instructions.md # AGENTS.md # .github/instructions/*.instructions.md # CLAUDE.md or GEMINI.md when the matching model is active const session = await client.createSession({ model: "claude-sonnet-4.5", workingDirectory: "/path/to/repository" });

Dynamic Skill selection

const skills = []; if (taskType === "code_review") { skills.push("./.copilot_skills/code-review/SKILL.md"); } else if (taskType === "migration") { skills.push("./.copilot_skills/migration/SKILL.md"); } const session = await client.createSession({ model: "claude-sonnet-4.5", skillDirectories: skills });

Custom agent registration

const session = await client.createSession({ customAgents: [{ name: "pr-reviewer", displayName: "PR Reviewer", description: "Reviews pull requests for security and maintainability", prompt: `You are an expert code reviewer. Focus on security vulnerabilities, performance, consistency, and test coverage gaps. Return evidence and severity.` }] });

Permission handler: read-only pattern

function readOnlyHandler(request, context) { if (["read", "search"].includes(request.kind)) { return { kind: "approved" }; } if (request.kind === "shell") { const command = context.command || ""; if (/^(git log|git diff|git show|git status)\b/.test(command)) { return { kind: "approved" }; } } return { kind: "denied" }; } const session = await client.createSession({ model: "claude-sonnet-4.5", onPermissionRequest: readOnlyHandler });

MCP server integration

const session = await client.createSession({ mcpServers: { filesystem: { type: "stdio", command: "npx", args: ["-y", "@modelcontextprotocol/server-filesystem", "."] }, github: { type: "http", url: "https://api.githubcopilot.com/mcp/" } } });

End-to-end PR analysis shape

from copilot import CopilotClient async def main(): client = CopilotClient() await client.start() session = await client.create_session({ "model": "claude-sonnet-4.5", "instructions": "Analyze PRs for security, performance, and quality.", "skill_directories": ["./.copilot_skills/pr-analyzer/SKILL.md"], "mcp_servers": { "github": { "type": "http", "url": "https://api.githubcopilot.com/mcp/" } }, "on_permission_request": read_only_handler }) result = await session.send_and_wait({ "prompt": "Analyze all PRs merged yesterday. Include a summary,\n" "security assessment, performance impact, and quality score." }) print(result.content) await client.stop()

SDK core principle: instructions provide foundational context, Skills provide on-demand knowledge, permission handlers enforce safety, MCP supplies external tools, and sub-agents enable divide-and-conquer. The SDK assembles these pieces inside a controlled application session.
11 · Readiness

Architecture review checklist

Use this checklist when introducing or reviewing Copilot customization in a team repository.

  • Global instructions contain only durable, broadly applicable standards
  • Path-specific rules use narrow, tested applyTo patterns
  • AGENTS.md contains operational steps, not a second global handbook
  • Skills have precise descriptions and progressive disclosure
  • Skill scripts and third-party content have been audited
  • Custom agents have explicit role, tools, model, and output boundaries
  • Handoffs are used for human-gated transitions
  • Sub-agents have a narrow whitelist and compact task packets
  • Hooks enforce deterministic rules with bounded timeouts
  • Hook inputs, outputs, and failure modes are tested
  • MCP servers and external tools have approved data flows
  • SDK permission handlers default to deny for risky operations
  • Secrets never appear in instructions, Skills, logs, or prompts
  • Owners, review dates, and recovery paths are documented
  • Focused validation runs before full repository validation
Definition of done: a new contributor can look at the repository and answer five questions: what is always-on, what loads on demand, which role owns the task, what is enforced in code, and how the application composes the runtime.
