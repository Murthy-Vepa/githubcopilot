GitHub Agentic Workflows bring AI reasoning into GitHub Actions. Define the intent in Markdown, compile it with gh-aw, and let the workflow respond to repository context within explicit permissions, network rules, and human review.

01 · The idea

Why use an agentic workflow?

Traditional automation is excellent when every branch is known in advance. Agentic workflows help when the input is rich, unstructured, or changing and a model needs to interpret context before choosing a response.

Traditional workflowAgentic workflowDesign implication
Fixed code decides every branch.The model interprets issues, pull requests, logs, or repository state.Write clear intent and acceptance criteria.
Configured actions write directly.Proposed changes pass through Safe Outputs.Separate reasoning from side effects.
Behavior changes through code edits.Behavior can be refined through reviewed Markdown.Version and review the source workflow.

Good fit

Daily summaries, issue triage, CI diagnosis, documentation maintenance, release notes, and other tasks where context changes but the outcome is bounded.

Use caution

High-impact decisions, unrestricted production changes, secrets handling, or workflows where a mistaken model action cannot be reviewed or rolled back.

Core principle: let the agent interpret and propose; let deterministic workflow code, permissions, Safe Outputs, and people control what becomes real.
02 · Setup

Install gh-aw and prepare the repository

The gh-aw extension converts Markdown workflow sources into GitHub Actions lock files. Development is easiest with a test repository and a manual trigger.

gh extension install github/gh-aw # Confirm the extension is available gh aw --help # Compile a workflow source gh aw compile .github/workflows/daily-report.md # Run a local or dispatched workflow as supported by your setup gh aw run .github/workflows/daily-report.md
  1. Create a workflow source in .github/workflows/<name>.md.
  2. Choose a narrow trigger, preferably workflow_dispatch while developing.
  3. Declare only the permissions, tools, and network access the task requires.
  4. Compile the source and inspect the generated .lock.yml.
  5. Commit both the Markdown source and the compiled lock file.
Source versus artifact: the .md file is the human-editable contract. The .lock.yml file is the compiled workflow executed by Actions. Frontmatter changes require recompilation; body-only changes may not, but recompiling is a useful consistency check.
03 · Authoring

Understand the workflow anatomy

A workflow combines YAML frontmatter for machine configuration with Markdown instructions for the agent. Keep both explicit enough for review.

--- name: daily-repository-report on: workflow_dispatch: permissions: contents: read issues: read safe-outputs: create-issue: max: 1 network: allowed: - github.com --- # Daily repository report Review the repository activity for the requested period. Summarize meaningful changes, open risks, and follow-up work. Cite the issues, pull requests, and commits that support each conclusion. Do not invent activity. If evidence is missing, say so. ## Expected output - A concise report for maintainers - Links to supporting GitHub artifacts - A proposed issue only when a follow-up is clearly needed

Frontmatter

Defines triggers, permissions, engines, tools, network allowlists, Safe Outputs, and other compilation settings.

Instructions

Explains the task, scope, evidence standard, output format, and stop conditions in human-readable Markdown.

Tools

Use GitHub context, shell commands, MCP servers, or other supported tools only when they are needed and explicitly allowed.

Outputs

Prefer comments, issues, labels, and pull requests through Safe Outputs rather than granting the model direct write authority.

04 · Guardrails

Make the safe path the default

Agentic workflows execute in a CI environment and may read untrusted repository content. Security belongs in the workflow configuration as well as the prompt.

Least privilege

Start with read-only permissions. Add a permission only when the task and the resulting evidence justify it.

Safe Outputs

Use bounded output declarations to validate and release external effects such as issues, comments, labels, or pull requests.

Network allowlists

Permit only the hosts required by the workflow. Treat broad internet access as a design exception that needs review.

Threat detection

Use strict compilation and the available threat detection controls to catch suspicious instructions, unsafe tools, and excessive authority.

--- permissions: contents: read pull-requests: read network: allowed: - api.github.com - github.com safe-outputs: add-comment: max: 2 create-issue: max: 1 ---
Never grant direct write permissions to the model just to make a demo work. Use a Safe Output with a small maximum, clear content rules, and a reviewable artifact. Keep secrets out of prompts, logs, issues, and model context.
05 · Examples

Three useful starting workflows

These examples show the shape of common workflows. Adapt the instructions and frontmatter to the current gh-aw schema, repository policy, and risk level.

Daily status report

Gather recent commits, pull requests, and issues, then produce a concise report for maintainers. The workflow should cite evidence and avoid creating output when there is nothing actionable.

# Daily status report Review activity from the last reporting period. Group findings into: 1. Delivered work 2. Active work 3. Risks or blocked work 4. Suggested follow-up Use links to GitHub artifacts as evidence. Do not infer status from file names alone. If the repository has no meaningful change, report that fact and do not create an issue.

Issue triage

Classify new issues by area, urgency, and missing information. Use a bounded label or comment output only after checking the issue body and repository guidance.

# Issue triage For each eligible issue, inspect the title, body, labels, and related issues. Recommend a category and priority only when the evidence supports it. Do not close issues, remove labels, or change milestones. When information is missing, add one concise request for clarification. Do not repeat an existing maintainer comment.

CI Doctor

Inspect a failed check, identify the most likely cause, and suggest a repair. Keep the workflow diagnostic unless a separate reviewed workflow owns the change.

# CI Doctor Inspect the failed workflow run, relevant logs, recent changes, and the repository's troubleshooting guidance. State: - failing job and first meaningful error - likely root cause and confidence - evidence used - smallest recommended next step Do not rerun jobs repeatedly, edit workflow files, or claim a fix was made.
06 · Patterns

Compose context, decisions, and outputs

Reliable workflows make the model's decision surface small. Give it the right context, define what good looks like, and constrain the possible side effects.

PatternUse it whenImplementation note
Evidence-first reportPeople need a summary of changing repository state.Require links and distinguish observed facts from interpretation.
Classifier plus Safe OutputA request needs a label, comment, or bounded issue.Set a maximum and prevent duplicate or destructive actions.
Diagnostic advisorA human owns the repair decision.Return confidence, evidence, and a smallest next step.
Scheduled maintainerA recurring review can reduce toil.Keep the schedule modest and make no-change runs cheap.
Human-in-the-loop proposalPotential changes need review.Produce a patch, issue, or pull request for approval rather than applying it directly.
Context engineering matters: provide focused files, issue history, logs, and repository instructions. More context is not automatically better; irrelevant or untrusted content increases both cost and risk.
07 · Validation

Compile, test, and debug in small loops

Test the workflow as both a GitHub Actions artifact and a model-guided behavior. Capture the generated lock file, run logs, model response, tool calls, and Safe Output decisions.

# Compile with strict checks before sharing gh aw compile .github/workflows/daily-report.md --strict # Inspect generated workflows and repository status git diff -- .github/workflows/daily-report.md .github/workflows/daily-report.lock.yml # Run the manual workflow from GitHub Actions during development gh aw run .github/workflows/daily-report.md
  • Markdown source compiles successfully
  • Generated lock file is committed and reviewable
  • Manual trigger works in a test repository
  • Read-only permissions are sufficient
  • Untrusted issue or log content cannot override instructions
  • Missing evidence produces a qualified response
  • Safe Outputs stay within their configured maximum
  • Duplicate comments or issues are prevented
  • Failure logs identify the first meaningful error
  • Cost, duration, and model behavior are acceptable
Debug the compiled artifact too: a correct Markdown instruction can still produce an unsafe or broken Actions workflow if frontmatter, permissions, tool wiring, or generated configuration is wrong.
08 · Build

Create your own workflow

Start with one recurring pain point and make the first version deliberately narrow. Expand only after the workflow produces useful evidence without surprising side effects.

  1. Name the job. Describe the user or maintainer outcome, not the model technology.
  2. Choose the trigger. Use workflow_dispatch while developing, then add issue, pull request, schedule, or check-run triggers deliberately.
  3. Define the evidence. List the files, events, logs, and links the model must inspect.
  4. Write stop conditions. Say what to do when evidence is missing, conflicting, sensitive, or outside scope.
  5. Set the smallest permissions. Prefer read-only access and bounded Safe Outputs.
  6. Compile and inspect. Run gh aw compile --strict, review the lock file, and test with representative and adversarial inputs.
  7. Operationalize. Document ownership, monitoring, cost expectations, rollback, and the review path for changes.

Commit together

Commit the editable Markdown source and generated lock file so reviewers see intent and executable configuration together.

Review like code

Use pull requests, ownership, dependency review, and regression cases. A prompt change can alter production behavior.

Keep outputs observable

Preserve reports, proposed patches, logs, and decisions as artifacts that maintainers can inspect later.

Plan for failure

Make retries bounded, no-op runs inexpensive, and human escalation clear when the agent cannot establish enough evidence.

09 · Readiness

Agentic workflow readiness checklist

Use this before enabling a workflow on a shared or production repository.

  • Workflow has a bounded, valuable maintainer outcome
  • Source Markdown and compiled lock file are both committed
  • Frontmatter uses minimal permissions and explicit triggers
  • Network access is limited to required hosts
  • Safe Outputs constrain every external side effect
  • Instructions require evidence and links
  • Missing, conflicting, and untrusted input cases are defined
  • Strict compilation passes
  • Manual test run has been reviewed by a human
  • Logs, artifacts, and outputs are observable
  • Owner, cost expectations, and rollback path are documented
  • Changes have a pull request and regression test path
Definition of done: a maintainer can explain what starts the workflow, what information the agent can access, what it may propose or release, how a person reviews the result, and what evidence proves the run behaved as intended.
