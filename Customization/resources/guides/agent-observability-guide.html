Customization guide

Make agent behavior inspectable.

Agent observability turns an opaque Copilot run into evidence you can use to understand context, tool use, permissions, failures, cost, and outcomes.

01 · Signals

Observe the whole agent loop

A useful record connects the user’s request to the final result. Capture enough detail to reproduce the decision without collecting unnecessary sensitive content.

Context

What instructions, prompt files, Skills, agents, repository files, and prior messages were available?

Decisions

What plan did the agent form, what assumptions did it make, and where did it change direction?

Tool calls

Which tools, MCP servers, commands, files, and APIs were called, with what inputs and results?

Outcome

What changed, what checks ran, what was approved, and what evidence supports the result?

SignalUseful questionsExample evidence
Trace identityWhich session, task, repository, branch, and user produced this run?Run ID, timestamp, working directory, commit SHA.
Context loadingWhich customization files were applied or skipped?Instruction paths, Skill matches, selected agent, MCP tool descriptions.
Tool executionWhat did the agent ask a tool to do, and what came back?Tool name, redacted arguments, result summary, duration, status.
Quality outcomeDid the result meet the acceptance criteria?Tests, lint, review findings, changed files, human approval.
02 · Trace

Trace a run from request to outcome

Start with a timeline. The goal is not to log every character forever; it is to preserve the causal chain needed to explain what happened.

Run: 2026-08-05T14:32Z / task-1842 Request: Add validation to the claims endpoint Context: repo instructions + api.instructions.md + Builder agent Plan: inspect controller -> find existing validator -> add tests Tool: search_codebase("claims endpoint") -> 12 matches / 420 ms Tool: read_file(ClaimsController.cs) -> success Permission: edit_file -> approved by user Change: ClaimsController.cs, ClaimsControllerTests.cs Validation: dotnet test -> 48 passed Outcome: ready for review

Minimum trace fields

  • Stable run or correlation identifier
  • Timestamp and duration for major steps
  • Task, repository, branch, and commit context
  • Selected agent, Skills, and instruction sources
  • Tool name, redacted arguments, result status, and error
  • Permission decisions and human approvals
  • Changed files and validation commands
  • Final outcome and unresolved limitations
Keep traces useful: record structured events where possible. A compact event with a tool name, status, duration, and redacted summary is easier to query than an unbounded transcript.
03 · Diagnose

Use evidence to locate the failure

Most agent failures fall into a small set of categories. Classify the failure before changing prompts or adding more context.

Failure patternEvidence to inspectLikely correction
Wrong or incomplete answerContext sources, file selection, prompt constraints, assumptions.Improve the relevant instruction, Skill description, or acceptance criteria.
Skill did not activateSkill metadata, task wording, available Skills, activation decision.Make the description precise about capability and trigger conditions.
Tool was not usedTool discovery, permissions, MCP connection status, agent tool list.Expose only the needed tool and state when it should be used.
Tool failedArguments, exit code, timeout, server logs, returned error.Fix the contract, input validation, timeout, or server behavior.
Unsafe action proposedPermission event, tool arguments, hook result, untrusted input.Default-deny, narrow permissions, add deterministic checks, require approval.
Run is slow or expensiveToken use, context size, tool latency, retries, repeated searches.Reduce always-on context, use progressive disclosure, cache stable results.
Do not tune blindly: adding more instructions can hide the real issue, increase context cost, and introduce contradictions. Change one layer, rerun the same scenario, and compare evidence.
04 · Improve

Turn recurring failures into system changes

Observability is valuable when it closes the loop between an observed failure and a small, testable improvement.

1. Capture

Save the run identifier, prompt, relevant context, tool events, errors, and result.

2. Classify

Decide whether the gap is context, capability, role, tool contract, permission, or validation.

3. Change

Update the narrowest responsible artifact and keep the change reviewable.

4. Replay

Run the original scenario plus a nearby negative case to check for regressions.

Useful operational metrics

MetricWhat it tells youUse carefully
Task success rateHow often the workflow meets its acceptance criteria.Define success independently from “the model returned an answer.”
Human correction rateHow often people revise, reject, or rerun the result.Track correction themes, not just a single percentage.
Tool success and latencyWhether external capabilities are reliable and responsive.Separate model delay from server or network delay.
Context and token costHow much always-on and on-demand material each run consumes.Redact content and aggregate by workflow rather than exposing prompts.
Permission denialsWhere the workflow reaches a boundary or asks for too much access.A denial can be a healthy guardrail, not necessarily a failure.
05 · Governance

Protect the evidence while making it useful

Agent traces can contain source code, prompts, identifiers, secrets, and business data. Observability must have its own access and retention design.

Minimize

Collect the smallest fields needed to debug the workflow. Prefer summaries and hashes where raw content is unnecessary.

Redact

Remove secrets, tokens, personal data, credentials, and sensitive payloads before storage or export.

Restrict

Limit who can view traces and separate operational metadata from sensitive request content.

Retain deliberately

Set retention, deletion, and export rules that match the risk and value of the evidence.

Guardrail design

  • Use permission handlers or approval prompts for shell, file-write, network, and external-system operations.
  • Use hooks for deterministic logging, validation, or blocking logic that should run independently of model wording.
  • Keep reviewers read-only where possible; planners should not need write or shell access.
  • Audit third-party Skills, MCP servers, scripts, and hook implementations before enabling them.
  • Store observability configuration and schemas in version control with a named owner.
Security boundary: logs are another data store. Apply the same classification, access control, secret scanning, and retention expectations to traces that you apply to application logs.
06 · Readiness

Agent observability readiness checklist

Use this checklist before a customized agent workflow becomes a team dependency.

  • Runs have stable identifiers and timestamps
  • Loaded instructions, Skills, agents, and tools are discoverable
  • Tool inputs and results are structured and redacted
  • Permission requests and approvals are recorded
  • Failures include actionable error context
  • Validation evidence is linked to the run outcome
  • Trace access and retention are documented
  • Owners review recurring failure patterns
  • Replay scenarios cover success and failure cases
  • Changes to observability behavior are tested
Definition of done: another engineer can use the trace to explain what the agent knew, what it attempted, what was allowed, what changed, and why the result was accepted.
