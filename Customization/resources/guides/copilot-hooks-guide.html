Put deterministic guardrails around agent work.

GitHub Copilot hooks let you observe, validate, or block workflow events at defined lifecycle points. Use them when a control must run consistently, regardless of model wording.

01 · Hook model

What a hook is responsible for

A hook is a boundary around an event in an agent workflow. It receives structured event data, applies deterministic logic, and returns an outcome that allows, denies, records, or changes the next step.

Event

Choose a lifecycle point that matters: before a tool runs, after a result returns, when a session starts, or when a workflow completes.

Handler

Use a script or program that performs one clear check. Keep it predictable, bounded, and independent of model persuasion.

Decision

Return an explicit allow, deny, warn, or failure outcome. Make the reason understandable to the user and traceable in logs.

Evidence

Record the event, decision, relevant identifiers, and validation result without capturing secrets or unnecessary source content.

Use the right layer: instructions explain desired behavior, Skills package repeatable expertise, and hooks enforce or observe behavior at runtime. A hook should not be a second prompt file.
02 · Design

Choose a narrow, meaningful boundary

The best hook controls a specific risk or creates useful evidence at a point where the input and decision are well defined.

NeedGood hook boundaryExample decision
Protect sensitive filesBefore a file-write or command operationDeny changes to protected paths and explain the approval route.
Prevent unsafe commandsBefore shell executionBlock destructive or network-sensitive commands unless explicitly approved.
Validate generated changesAfter edits, before completionRun a focused test or policy check and report the result.
Improve traceabilityAt session, tool, and completion eventsWrite a redacted structured event with status and duration.
Require a human decisionAt a high-impact action boundaryPause and request approval before external side effects.

One decision per hook

Keep each handler easy to reason about. Compose several focused checks instead of hiding a policy engine in one opaque script.

Fail closed for risk

When a security or permission check cannot determine a safe outcome, stop and surface the missing evidence.

Keep latency bounded

A hook is part of the user workflow. Avoid unbounded network calls and expensive scans on every low-risk event.

Make denial useful

Explain what was blocked, why it was blocked, and what evidence or approval would allow the work to continue.

Do not over-hook: adding checks to every event can slow the workflow, create noisy failures, and teach users to approve prompts without reading them.
03 · Implement

Make the contract explicit

Keep configuration and handlers close to version control. Treat the event payload and return behavior as an interface that deserves tests and change review.

Typical repository shape

.github/ hooks/ before-tool.ps1 after-edit.ps1 README.md copilot-instructions.md

Handler responsibilities

  1. Validate input. Reject missing, malformed, or unexpected event data before making a decision.
  2. Classify the operation. Identify the command, path, tool, target system, or data category involved.
  3. Apply policy. Use deterministic rules and configured allowlists or denylists where appropriate.
  4. Return a clear outcome. Distinguish allow, deny, warning, and handler failure.
  5. Record minimal evidence. Log identifiers and summaries, not credentials, tokens, or unrestricted payloads.
param([Parameter(ValueFromPipeline = $true)] $Event) $operation = $Event.toolInput.command if ($operation -match 'Remove-Item|git reset --hard|DROP TABLE') { Write-Output '{"decision":"deny","reason":"Destructive operation requires approval."}' exit 0 } Write-Output '{"decision":"allow"}'
Security boundary: a hook script runs with the permissions of its host environment. Review shell parsing, path handling, environment variables, dependency loading, and network behavior as carefully as application code.
04 · Test

Test the decision, not just the script

Hooks fail in configuration, event matching, handler logic, permissions, and user experience. Test the whole boundary with representative and adversarial inputs.

Test caseWhat to observePass condition
Allowed operationA normal read or bounded edit reaches the handler.The hook allows it without unnecessary delay or output.
Denied operationA protected path or destructive command is presented.The action does not execute and the reason is actionable.
Malformed eventRequired fields are missing or have the wrong type.The hook fails safely and reports the invalid contract.
Handler failureThe script times out, lacks permission, or returns invalid output.The workflow does not silently treat the failure as approval.
Bypass attemptCase, spacing, encoding, or shell syntax changes the input.Policy behavior remains intentional and documented.
Regression replayA previously fixed incident is repeated.The control still works and nearby valid work remains usable.

Useful evidence

  • Hook matched the intended lifecycle event
  • Input was parsed and classified correctly
  • Allow and deny decisions were both tested
  • Failure and timeout behavior was verified
  • Logs contain a redacted reason and correlation identifier
  • Latency and user-facing output are acceptable
05 · Governance

Keep runtime controls reviewable

Hooks can block work or trigger side effects, so they need ownership, change control, and a recovery path when policy or dependencies change.

Version control

Store configuration, scripts, test fixtures, and policy documentation together. Review changes like production code.

Least privilege

Give a handler only the file, command, network, and identity access it needs. Separate read-only checks from mutation.

Safe rollout

Start in observe-only or warning mode where possible, measure false positives, then enforce after the rule is trusted.

Recovery

Document how to disable or replace a broken hook without bypassing every other control or leaving users blocked indefinitely.

  • Assign an owner and review date for every enforcement hook.
  • Scan scripts and dependencies for secrets and unsafe execution patterns.
  • Keep user approval explicit for high-impact external actions.
  • Record denials as useful operational signals, not only as errors.
  • Review false positives and bypass requests as policy feedback.
06 · Readiness

Hooks readiness checklist

Use this before making a hook part of a shared repository or team workflow.

  • Hook event and lifecycle placement are documented
  • Input and output contract are explicit and validated
  • Allow, deny, warning, and failure outcomes are distinct
  • Handler has bounded latency and least-privilege access
  • Protected operations and approval requirements are clear
  • Secrets and sensitive payloads are excluded from logs
  • Positive, negative, malformed, and bypass cases were tested
  • Failure does not silently become approval
  • Owner, rollout mode, and recovery path are documented
  • Changes are versioned and regression-tested
Definition of done: another engineer can explain when the hook runs, what it can decide, what happens when it fails, and how to verify or safely change it.
