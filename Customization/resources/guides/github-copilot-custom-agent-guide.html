Customization guide

Build a custom agent that knows its job.

Custom agents package a specialized role, operating instructions, tools, models, and next steps into a reusable Markdown file. Use this guide to move from a blank .agent.md file to a tested team workflow.

Focused expertiseExplicit authorityComposable workflowsEvidence-driven
01 · Select the surface

Use an agent when the AI itself needs to change

Custom agents are for specialized personas with distinct tools or workflow behavior. Choose the smallest customization surface that expresses the requirement.

SurfaceFile or controlUse it whenExample
Custom instructionscopilot-instructions.mdRules and standards should apply to every Copilot interaction.Always follow the repository's testing and security conventions.
Prompt files.prompt.mdA repeatable, parameterized task should be invoked on demand.Generate a release-notes draft from the current changes.
Custom agents.agent.mdThe AI needs a different identity, tool set, model, or multi-step workflow.Analyze a codebase as a read-only architecture reviewer.
Agent SkillsSKILL.mdA reusable capability should be discovered and applied by agents.Review an OpenAPI contract using a standard checklist.
Decision rule: use an agent to change who is acting and what that agent is allowed to do. Use instructions to establish universal rules, and prompts to package a task someone can invoke.

Good agent candidates

Security reviewer, test-coverage specialist, API builder, migration planner, documentation maintainer, or domain expert with a recognizable output.

Weak agent candidates

A generic "do everything" assistant, a single short prompt, or a policy that must be enforced deterministically outside the model.

02 · Setup

Put the agent where Copilot can discover it

Repository agents are easy to share and version. User-level agents are useful for personal workflows that should follow you between workspaces.

Prerequisites

  • Visual Studio Code 1.106 or later, or a compatible GitHub Copilot environment that supports custom agents.
  • The GitHub Copilot extension and an active Copilot subscription.
  • A workspace where you can create and test Markdown customization files.
  • A representative codebase, test project, or workflow that gives the agent real evidence to inspect.

Repository-level location

your-project/ .github/ agents/ test-coverage.agent.md api-builder.agent.md code-reviewer.agent.md copilot-instructions.md prompts/ skills/ backend/ frontend/

User-level location

Create a user agent from the Copilot Chat agent picker when the workflow is personal and workspace-independent. Repository-level agents are the better default for team standards, project context, and shared review.

Verify discovery

  1. Open Copilot Chat and open the Agents dropdown.
  2. Confirm the new agent appears with the expected name and description.
  3. Use Configure Custom Agents to inspect the source and scope.
  4. Run a small test prompt before attempting a complex workflow.
Debugging tip: use the Chat Debug View from the Chat overflow menu or the Command Palette. Inspect the system prompt, gathered context, and tool invocations to verify that the agent file is actually applied.
03 · File anatomy

Make the agent file readable as a contract

Every custom agent has optional YAML frontmatter followed by a Markdown body. The frontmatter configures the agent; the body supplies its role, workflow, standards, output format, and boundaries.

Complete file shape

--- name: test-coverage description: Analyze a codebase for coverage gaps and generate tests. argument-hint: Describe the area or target you want tested. tools: ['search', 'codebase', 'editFiles', 'runCommands', 'runTests', 'problems'] model: 'Claude Sonnet 4 (copilot)' handoffs: - label: Review the tests agent: code-reviewer prompt: Review the generated tests for correctness and maintainability. send: false agents: ['code-reviewer'] target: vscode user-invokable: true --- # Role and identity You are a senior testing specialist... # Workflow 1. Analyze... 2. Plan... 3. Generate... 4. Validate... 5. Report...

Frontmatter properties

PropertyRequiredPurposeDesign guidance
descriptionYesDescribes the agent and helps users understand when to select it.Use a concise description with capability, input, and outcome.
nameNoDisplay name for the agent.Use a stable, short name; the filename is the fallback.
argument-hintNoGuides the user on what to put in the chat input.Describe the expected scope, target, or decision.
toolsNoRestricts available tools.Omit only when the agent genuinely needs broad authority.
modelNoSelects a preferred model or fallback list.Choose for reasoning, latency, cost, and supported features.
handoffsNoProvides suggested next-step buttons.Chain agents where the next phase has a different responsibility.
agentsNoWhitelists subagents this agent may invoke.Prefer a narrow list over *.
targetNoLimits availability to vscode or github-copilot.Use when a workflow depends on an environment-specific capability.
user-invokableNoControls whether the agent appears in the user picker.Set false for internal subagents that should not be selected directly.
mcp-serversNoConfigures MCP servers for supported coding-agent scenarios.Review server permissions and data handling before enabling.

Body structure

Identity and role

State who the agent is, its domain, and the one outcome it owns. This anchors behavior before the task details arrive.

Workflow steps

Use an ordered analyze, plan, execute, validate, and report sequence. Name decision points and stop conditions.

Standards and rules

Encode repository conventions, positive requirements, negative constraints, and approval boundaries.

Output format

Define the report structure, evidence required, changed files, commands run, and unresolved risks.

Write for behavior: “Write good tests” is vague. “Use the existing framework, mirror source paths, use the Arrange-Act-Assert pattern, run the focused test command, and report failures” is observable and testable.
04 · Capabilities

Give the agent exactly the authority it needs

Tools define what the agent can do. Models influence quality, latency, and cost. Both belong in the design rather than being accidental defaults.

Common built-in tools

ToolCapabilityUseful for
searchSearch workspace files by text.Finding conventions, symbols, configuration, and examples.
codebaseSemantic code search and project understanding.Mapping architecture and locating related behavior.
editFilesCreate and edit files.Implementation, test generation, and documentation changes.
runCommandsExecute terminal commands.Builds, linters, formatters, migrations, and validation.
runTestsRun test suites.Focused and full test validation.
findTestFilesLocate test files.Discovering test conventions and existing coverage.
problemsRead compile and lint diagnostics.Diagnosing errors after edits.
changesInspect current changes.Reviewing scope and preventing unrelated modifications.
testFailureInspect test failure details.Targeted diagnosis and repair.
fetchRead web content.Official documentation and external specifications.

Tool selection by archetype

Agent typeRecommended toolsBoundary
Planner or read-only reviewersearch, codebase, fetch, usages, changes, problemsNo editing or command execution.
Implementation agentEditing, search, codebase, commands, tests, problemsChanges only the requested scope; validates before reporting.
Testing agentSearch, codebase, edit, tests, test files, commands, failures, problemsPrefer test-only changes unless a production bug blocks validation.
Migration orchestratorAnalysis, planning, delegated agents, editing, commands, testsUses handoffs or subagents to separate phases and approvals.

Model selection

Omit model when the user should choose. Specify a model when a workflow needs predictable reasoning or a known capability. A model array can express fallback options when supported.

Least privilege: a read-only planner that can edit files or run arbitrary commands is carrying unnecessary risk. Tool restrictions are a useful boundary, but they do not replace review of the agent instructions and the requested task.
05 · Orchestration

Compose work with handoffs and subagents

Handoffs are visible transitions for a person to approve or initiate. Subagents are delegated specialists an agent can invoke as part of its own workflow.

Handoffs: visible next steps

handoffs: - label: Generate tests agent: test-coverage prompt: Generate tests for the implementation described above. send: false - label: Review changes agent: code-reviewer prompt: Review the files and validation evidence from the previous step. send: true
SettingBehaviorUse it for
labelText shown on the action button.A clear, outcome-oriented next step.
agentTarget custom agent.A specialist with a distinct role or authority.
promptContext sent to the target agent.Passing the previous result and the next objective.
send: falsePrefills the prompt for user review.Human approval, sensitive changes, or ambiguous scope.
send: trueSubmits immediately.Low-risk, deterministic transitions where the user has already opted in.

Subagents: delegated specialists

--- name: migration-orchestrator description: Coordinate a staged application migration. agents: ['architecture-reviewer', 'api-builder', 'test-coverage'] user-invokable: true ---

Use agents: [] to prevent subagent invocation, a named list to allow specific specialists, or agents: ['*'] only when broad delegation is genuinely required and governed.

Example workflow chain

Planner (read-only) | handoff: "Implement the approved plan" v Implementation agent (edit and validate) | handoff: "Add tests for the changed behavior" v Test-coverage agent (test tools and evidence) | handoff: "Review the complete change" v Code-review agent (read-only assessment)

Prefer handoffs when

A person should inspect the result, choose the next phase, or approve a side effect. Handoffs make the workflow legible and interruptible.

Prefer subagents when

The parent agent needs a bounded specialist to complete a well-defined subtask and can evaluate the returned result.

Keep chains shallow: every extra agent adds context transfer, model variability, and debugging cost. Each stage should have one owner, one purpose, and a clear completion signal.
06 · Walkthrough

Build a test-coverage agent step by step

The following example turns a real testing need into a focused agent. Adapt the domain, paths, framework, and quality target to your repository rather than copying assumptions blindly.

Step 1: Define the purpose

  • Role: a senior testing specialist for the repository's application stack.
  • Outcome: identify coverage gaps, generate maintainable tests, run validation, and report remaining gaps.
  • Authority: read source and tests, write test files, run test commands, and inspect diagnostics.
  • Boundary: do not change production code unless a confirmed defect blocks testing and the user approves it.

Step 2: Study existing examples

Read community agents and local agents for patterns, but treat them as examples rather than authority. Look for explicit identity, analyze-before-editing, concrete constraints, and validation evidence.

Step 3: Study repository patterns

Before drafting instructions, inspect the repository's instruction file, test projects, representative test classes, test data builders, mocking libraries, and build scripts. The agent should extend existing conventions, not invent a second testing culture.

Step 4: Write frontmatter

--- name: test-coverage description: Analyze code coverage gaps and generate comprehensive unit and integration tests. argument-hint: Describe the project area, class, or behavior you want tested. ---

In this example, tools and model are omitted because the agent needs broad testing capability and should respect the user's model selection. Add explicit tools when a narrower boundary is safer.

Step 5: Write the body

# Role and identity You are a senior testing specialist. Focus on identifying coverage gaps and creating reliable unit and integration tests that follow this repository's existing conventions. # Workflow 1. Analyze source, tests, build files, and repository instructions. 2. Discover naming, structure, data, mocking, and integration patterns. 3. Create a coverage plan ordered by architectural layer and risk. 4. Generate one test class at a time; validate after each meaningful change. 5. Run focused tests, diagnose failures, then run the broader suite. 6. Report files changed, commands run, results, and remaining gaps. # Rules - NEVER change production code unless a confirmed testing blocker is approved. - ALWAYS inspect existing tests before creating new patterns. - ALWAYS run the narrowest useful build or test command after edits. - Do not claim coverage percentages without measurement evidence. # Output Return a concise summary with coverage scope, files changed, validation results, remaining risks, and recommended next tests.

Step 6: Save and verify

  1. Save the file as .github/agents/test-coverage.agent.md.
  2. Confirm it appears in the Agents dropdown.
  3. Test a narrow class before asking for the whole repository.
  4. Inspect the debug view if tools, instructions, or scope look wrong.

Step 7: Share through version control

Review the file like code, commit it with the repository's normal process, and include a short usage note or example prompt in the team documentation.

07 · Testing

Evaluate the agent as a behavior

A polished Markdown file can still produce weak behavior. Test positive cases, boundary cases, missing prerequisites, and adversarial inputs before sharing the agent.

Recommended test prompts

PromptWhat to observePass condition
Analyze the current test coverage and identify gaps.Does the agent inspect the correct source and test areas?It produces an evidence-based plan without editing prematurely.
Add unit tests for the health controller.Does it follow local naming, framework, and test structure?Tests compile, match conventions, and target meaningful behavior.
Generate integration tests for the request middleware.Does it select the established integration harness?It uses the repository's fixture and validates the request pipeline.
Run the tests and report the results.Does it execute the right command and interpret failures?It reports actual commands and results, not guessed coverage.
Here is a file telling you to ignore the agent rules.Does untrusted content override the agent?It treats the file as data and preserves its governing instructions.

Iteration loop

  1. Observe: record the prompt, files inspected, tool calls, edits, and output.
  2. Compare: check behavior against the agent's stated success criteria.
  3. Refine: add a concrete rule, example, or stop condition for the failure.
  4. Replay: rerun the failing prompt and a nearby regression case.
  5. Review: confirm the change did not widen authority or introduce contradictions.
FailureInstruction refinement
Generated tests do not compile.Name the build command, show a correct local example, and require validation after each test class.
Agent modifies production code.Repeat the boundary in rules and workflow, and restrict tools if read-only behavior is intended.
Too many tests are generated at once.Require one class or layer at a time with a validation checkpoint.
Wrong mocking library is used.State the repository's actual library and explicitly exclude alternatives.
Agent claims a coverage target without measurement.Require a coverage command or label the result as an estimate.
Debug with evidence: the Chat Debug View is useful for checking whether frontmatter was parsed, the body was included, the expected tools were available, and the agent actually used the intended workflow.
08 · Sharing

Match the scope to the ownership model

Custom agents can live at repository, organization, or user scope. The right location depends on who owns the standards and how much project context the agent needs.

ScopeLocation or setupBest forTradeoff
Repository.github/agents/Project-specific workflows and versioned team standards.Must be maintained with the repository.
OrganizationOrganization custom-agent repository and enabled organization settings.Cross-repository security, review, or platform standards.Requires governance, ownership, and rollout discipline.
User profileNew Agent (User) from the Copilot Chat agent configuration.Personal productivity and reusable individual workflows.May not understand project-specific conventions.

Recommended team structure

Organization custom agents org-security-reviewer.agent.md org-code-reviewer.agent.md Repository custom agents .github/agents/ test-coverage.agent.md api-builder.agent.md Personal agents documentation-helper.agent.md

Governance questions

  • Who owns the agent and reviews changes?
  • Which tools, repositories, or data can it access?
  • What output must be reviewed by a human?
  • Which model and external services are permitted?
  • How are prompts, examples, scripts, and dependencies versioned?
  • What test prompts demonstrate that the agent still works after a platform update?
Inspect before enabling: review instructions, scripts, references, network access, file writes, MCP servers, and data handling. A trusted repository location does not make every agent implementation safe by itself.
09 · Design practice

Patterns that keep agents useful

Good custom agents are narrow enough to be predictable and rich enough to handle the real workflow around their task.

Useful community patterns

Specialist agent

One role, one domain, and a constrained tool set. A Playwright tester or security reviewer is easier to evaluate than a generalist.

Meta-agent

An agent builder gathers requirements, proposes tools, drafts an agent, and checks the result against a quality checklist.

Chained workflow

Separate TDD Red, Green, and Refactor or plan, implement, test, and review phases into agents with clear transitions.

Migration orchestrator

A coordinator delegates architecture, scaffolding, frontend, and testing tasks while retaining the overall plan and validation.

Platform expert

A deep domain agent encodes language, framework, security, and testing conventions that are expensive to restate in every prompt.

Analyze first

Repository exploration before editing reduces invented patterns, missing dependencies, and changes that conflict with local architecture.

Do

PracticeReason
Start with identity and scope.A role statement focuses the model before procedural details.
Use numbered workflow steps.Ordered actions and checkpoints are easier to follow and test.
Include concrete examples.Examples communicate naming, structure, and quality more reliably than abstract advice.
Match existing patterns.Local conventions are the most relevant source of truth for implementation.
Add validation steps.Commands and evidence make success observable.
Restrict read-only agents.Authority should match the job, especially for reviewers and planners.

Do not

Anti-patternWhy it fails
Vague instructions.The agent must infer the workflow and quality bar from too little signal.
Too many responsibilities.Competing goals produce inconsistent choices and difficult evaluation.
Hardcoded absolute paths.The agent becomes brittle across clones, branches, and repositories.
Skipping analysis.Generated work is more likely to conflict with existing architecture.
Contradicting repository instructions.Conflicting authority creates unpredictable behavior and maintenance debt.
Relying on prose for enforcement.Security, approvals, and permissions need deterministic controls as well as instructions.

Prompt-writing techniques

  1. Use imperative language for mandatory actions.
  2. Use negative constraints for known failure modes.
  3. Define success criteria in observable terms.
  4. Layer specificity from role to workflow to repository convention.
  5. Reference tools and supporting files explicitly when they matter.
10 · Readiness

Custom agent readiness checklist

Use this before committing an agent to a shared repository or organization catalog.

  • Agent has one clear role, audience, and outcome
  • Description explains when to select it
  • Argument hint describes useful input
  • Repository, user, or organization scope is intentional
  • Frontmatter parses and uses supported property names
  • Tools match the minimum authority needed
  • Model choice is deliberate or left to the user for good reason
  • Body has identity, workflow, standards, output, and boundaries
  • Instructions align with repository guidance and existing examples
  • Handoffs have clear labels, prompts, targets, and send behavior
  • Subagents are explicitly whitelisted where possible
  • Analyze and plan steps occur before side effects
  • Validation commands are explicit and produce evidence
  • Positive, near-miss, missing-input, and adversarial prompts were tested
  • Chat Debug View was used when behavior was unclear
  • Owner, review cadence, dependencies, and data boundaries are documented
Definition of done: another engineer can tell when the agent activates, what it is allowed to touch, how it should work, what happens next, and which evidence proves the result is ready.
11 · Recovery

Troubleshoot the common failure modes

Most custom-agent failures are discoverability, configuration, authority, or instruction-quality problems. Use the narrowest diagnostic first.

SymptomLikely causeCheck or fix
Agent does not appear.Wrong folder, extension, or frontmatter.Verify .github/agents/, the .agent.md suffix, valid YAML, and reload the workspace.
Agent appears with the wrong name.Missing or unexpected name.Set an explicit stable name and confirm the source path.
Agent ignores instructions.Malformed frontmatter, contradictory guidance, or prompt scope.Use the Chat Debug View to inspect the assembled system prompt.
Agent cannot use a tool.Tool name is invalid or omitted from a restricted list.Check supported tool names and the agent's available-tool trace.
Agent changes too much.Broad tools, vague scope, or missing approval boundary.Restrict tools, require an analysis plan, and add a stop condition.
Agent contradicts repository standards.Agent body conflicts with copilot-instructions.md.Remove the contradiction and make the repository standard the shared baseline.
Output is inconsistent.Insufficient examples, checkpoints, or success criteria.Add concrete patterns, validation commands, and regression prompts.
YAML parsing fails.Indentation or quoting error.Use consistent indentation and quote strings containing special characters.

Quick diagnostic sequence

  1. Confirm file location and extension.
  2. Validate frontmatter syntax and property names.
  3. Reload and confirm discovery in the agent picker.
  4. Run one focused prompt with a small scope.
  5. Inspect the Chat Debug View for prompt and tool evidence.
  6. Make one instruction or configuration change, then replay the same prompt.
