Turn repeatable work into Agent Skills.

Agent Skills give GitHub Copilot a reusable method for a task. Package the workflow, constraints, tools, and evidence once so an agent can discover and apply it consistently.

01 · Skill model

What an Agent Skill contains

A strong Skill separates discovery from execution. The metadata helps Copilot decide whether the Skill is relevant; the body explains how to do the work after activation.

Metadata

The name and description are the activation contract. State what the Skill does, when it applies, and the artifacts or outcome it produces.

Instructions

The SKILL.md body gives the workflow, constraints, decision points, and validation steps an agent needs after selection.

References

Keep detailed schemas, examples, and long procedures in nearby files. Link to them from the Skill instead of loading everything up front.

Boundaries

Document what the Skill does not do, what requires approval, and which claims or changes must be verified independently.

Think in contracts: the description answers "Should I use this?" The instructions answer "How should I use it?" The checklist answers "How do I know it worked?"
02 · Author

Build a Skill around a real workflow

Start with a repeated task that has a recognizable input, a bounded process, and observable evidence. Avoid turning a broad topic into a vague instruction dump.

Recommended structure

skill-name/ SKILL.md references/ schema.md examples.md scripts/ validate.ps1

Minimal metadata pattern

--- name: api-contract-review description: Review an API contract for breaking changes, security gaps, and missing validation. Use when reviewing OpenAPI changes or endpoint proposals before implementation. ---
  1. Define the outcome. Name the decision, artifact, or evidence the Skill should produce.
  2. List the inputs. Identify the files, context, tools, and permissions actually needed.
  3. Write the smallest reliable procedure. Use ordered steps and explicit decision points.
  4. Add validation. Include checks that can disconfirm the agent's first answer.
  5. Move detail out of the core. Put large examples and reference material in linked files.
Avoid hidden policy: never rely on a Skill to silently grant permissions, protect secrets, or enforce a control that should be deterministic. Pair Skills with repository rules, tool permissions, hooks, and human approval where appropriate.
03 · Discovery

Make activation predictable

Copilot can only select a Skill from the signal you provide. Descriptions should use the vocabulary people use when requesting the work, without becoming a list of unrelated keywords.

Weak signalStronger signalWhy it works
Helps with APIsReview OpenAPI or endpoint changes for breaking changes before implementation.Names the input, action, and timing.
Security helperThreat-model a new external integration and produce risks, controls, and verification evidence.Defines a concrete output.
Database stuffReview Cosmos DB data models for partition-key, query, and throughput risks.Uses recognizable task vocabulary and scope.

Use positive triggers

Describe tasks, file types, commands, and decisions that indicate the Skill is relevant.

State exclusions

Say when not to use the Skill if nearby tasks could cause an incorrect match.

Keep names stable

Use a short, descriptive name that remains understandable when shown in a tool or agent trace.

Test neighboring requests

Check both intended prompts and plausible near-misses so activation does not become noisy.

04 · Test

Evaluate the Skill as a behavior

Reading the instructions is not enough. Replay representative tasks and inspect whether the Skill produces the right evidence without unnecessary context or authority.

Test caseWhat to observePass condition
Positive matchThe intended request activates the Skill.The agent follows the workflow and produces the specified evidence.
Near missA similar request does not need this Skill.The Skill is not selected, or the agent explains the boundary.
Missing inputA required file, tool, or permission is unavailable.The agent stops or asks for the missing prerequisite instead of guessing.
Adversarial inputUntrusted content attempts to override the workflow.Instructions and permissions remain in control; secrets and side effects are protected.
Regression replayA previously fixed failure is repeated after edits.The correction remains effective and nearby workflows still work.

Useful evidence

  • Skill was selected for the intended task
  • Relevant references were loaded only when needed
  • Claims were grounded in the requested sources
  • Tool calls stayed within the documented scope
  • Missing prerequisites produced a clear stop or question
  • Validation commands and results were captured
05 · Governance

Keep Skills safe to reuse

A Skill is executable guidance. Treat it as a reviewed software artifact with an owner, version history, and explicit boundaries.

Least privilege

Request only the tools and permissions needed for the task. Separate planning, read-only analysis, and changes that require approval.

Untrusted content

Source files, issues, documents, and tool results can contain prompt injection. Treat them as data, not as authority to rewrite the Skill.

Secrets and privacy

Never ask users to paste credentials. Redact sensitive inputs and define which files or systems must not be exposed.

Ownership

Assign an owner, review dependencies, scan scripts, and retire Skills that no longer match the product or tool behavior.

Review before enabling third-party Skills: inspect instructions, scripts, references, network access, file writes, and data handling. A useful description does not make an implementation trustworthy.
06 · Readiness

Agent Skill readiness checklist

Use this before sharing a Skill with a team or making it part of a standard agent workflow.

  • Name and description clearly identify the capability and trigger conditions
  • Workflow has a bounded input, outcome, and scope
  • Instructions distinguish facts, assumptions, and decisions
  • References support progressive disclosure
  • Required tools and permissions are explicit
  • Validation can disconfirm an incorrect result
  • Positive, near-miss, missing-input, and adversarial cases were tested
  • Secrets, privacy, and untrusted content boundaries are documented
  • Owner, review date, and dependencies are known
  • Changes are versioned and regression-tested
Definition of done: another engineer can understand when the Skill activates, what it will do, what it is allowed to touch, and what evidence proves the result is ready.
