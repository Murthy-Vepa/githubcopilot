Scenario-based guide

Choose the right Copilot customization for the job.

Start with the situation you are facing, identify the behavior you need, and select the smallest customization layer that can solve it. These guides are designed for real repository decisions, not feature memorization.

The fast route

Ask these three questions first

Most customization choices become clear when you separate context, capability, role, and enforcement.

Who should activate it?

Everyone, a person on demand, a selected agent, or an external application?

What does it need?

Short rules, a repeatable procedure, specialist files and scripts, tools, or lifecycle events?

What can it change?

Context only, files, external systems, permissions, or released workflow outputs?

What is the smallest useful layer?

Start small. Move detail into a richer layer only when the current layer cannot carry the requirement.

Default rule: use instructions for durable context, prompt files for explicit requests, Skills for reusable expertise, custom agents for roles and handoffs, MCP for external capabilities, and hooks for deterministic controls.

Real situations

Scenario-based decisions

Scenario 1 · “Copilot does not follow our React conventions.”

Your team uses a shared component library, colocated tests, and named exports. Generated components often ignore one or more of these rules.

Choose: a path-specific instruction file such as .github/instructions/react.instructions.md.

Starter action

  1. Write three to five testable rules.
  2. Use applyTo to target the relevant files.
  3. Ask Copilot to create a component and verify the result against the rules.

Do not start with: a custom agent. The issue is missing context, not a missing role.

Scenario 2 · “We need a standard pull request summary.”

Every pull request should include a summary, test evidence, risk notes, and a rollout statement. The author should choose when to run it.

Choose: a prompt file such as .github/prompts/pr-summary.prompt.md.

Starter action

  1. Define the inputs the prompt should inspect.
  2. Specify the exact output headings.
  3. Add a stop condition for missing tests or unresolved risk.

Escalate to a Skill when: the process also needs scripts, templates, or repository-specific reference files.

Scenario 3 · “Our incident review needs logs, examples, and a known procedure.”

The workflow uses a diagnostic checklist, log-query examples, redaction guidance, and a report template. It should activate when an incident investigation is requested.

Choose: an Agent Skill with SKILL.md, examples, scripts, and templates.

Starter action

  1. Put the activation signals in the Skill description.
  2. Keep the main procedure short and link to supporting resources.
  3. Test one matching, one non-matching, and one ambiguous request.

Do not put everything in: repository-wide instructions. Large procedures consume context when they are not relevant.

Scenario 4 · “Planning must be read-only, but implementation can edit.”

Your team wants a visible plan, an approval point, implementation, and an independent review. Each phase needs different tools and expectations.

Choose: custom agents with explicit handoffs: Planner, Builder, and Reviewer.

Starter action

  1. Give the Planner search and inspection tools only.
  2. Require approval before handing the plan to the Builder.
  3. Make the Reviewer report defects and test gaps without changing files.

Guardrail: use human-reviewed handoffs when the next phase can make consequential changes.

Scenario 5 · “Copilot needs to look up service ownership.”

Ownership data lives in an internal catalog. Copilot should retrieve the owning team and escalation contact but should not modify the catalog.

Choose: a read-only MCP server exposing a narrowly scoped lookup tool.

Starter action

  1. Expose only the lookup operation and required parameters.
  2. Document data classification, authentication, and revocation.
  3. Test malformed requests and unauthorized access.

Do not use: a pasted static table when ownership changes frequently or access must be controlled.

Scenario 6 · “Every generated change must pass a policy check.”

A repository must run a deterministic secret scan and policy validation before a change is accepted. The check must not depend on model interpretation.

Choose: a hook or standard CI workflow, depending on when and where the check must run.

Starter action

  1. Define the event, command, failure behavior, and owner.
  2. Keep the check independent of the agent’s claim that it succeeded.
  3. Record actionable failure output for the developer.

Principle: deterministic enforcement belongs in code or automation, not in prose instructions.

Scenario 7 · “We want an internal assistant for deployment readiness.”

The assistant needs session management, repository context, approved MCP tools, custom roles, and a default-deny permission handler inside an application.

Choose: the Copilot SDK, with the repository customizations composed into the application.

Starter action

  1. Define the assistant’s user journeys and permission boundaries.
  2. Start with read-only tools and explicit approval for writes.
  3. Capture session events, tool calls, and validation evidence.

Do not build an SDK application when: a repository-local prompt, Skill, or agent already solves the problem.

Scenario 8 · “We are unsure whether this needs customization at all.”

The issue happened once, the requirement is unclear, and no stable behavior has been agreed by the team.

Choose: no artifact yet. Capture the example, clarify the desired behavior, and test a normal prompt first.

Starter action

  1. Collect two or three examples of the failure.
  2. Separate missing context from an incorrect expectation.
  3. Choose the smallest artifact only after the pattern repeats.

Principle: customization should encode a known improvement, not preserve an unexamined preference.

Before you commit

Decision quality checklist

  • The problem has happened more than once or has clear business impact
  • The expected behavior can be described and tested
  • The chosen layer is the smallest one that fits the requirement
  • Activation behavior is explicit and discoverable
  • Tool and data access are limited to what the scenario needs
  • Write actions have approval, validation, or rollback controls
  • An owner is responsible for maintenance and review
  • A realistic matching and non-matching test has been recorded
Next step: choose one repeated scenario from your repository, create the smallest artifact, and test it with a teammate who has not seen the implementation.
