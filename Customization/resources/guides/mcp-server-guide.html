Build MCP servers agents can trust.

The Model Context Protocol gives GitHub Copilot a consistent way to discover and use external tools, resources, and prompts. A good MCP server makes that boundary clear, useful, and safe.

01 · Architecture

Understand the MCP boundary

MCP separates the application that hosts the conversation from the client connection and the server that exposes capabilities.

Host

The AI application, such as an editor or agent runtime, coordinates the conversation, permissions, and user experience.

Client

A protocol client maintains a connection to one MCP server and negotiates capabilities, requests, notifications, and lifecycle state.

Server

A focused service exposes tools, resources, and prompts through a standard protocol contract.

Transport

The connection carries protocol messages. Choose a local process or remote transport based on deployment, trust, and operational needs.

Design principle: an MCP server is a capability boundary, not a second general-purpose agent. Expose the smallest set of operations that helps a user complete a defined workflow.
PrimitiveDirectionUse it for
ToolsModel or user invokes the serverActions such as querying data, creating a ticket, or validating a deployment.
ResourcesClient reads server-provided contextDocuments, schemas, records, configuration, or other addressable information.
PromptsUser or client selects a reusable templateRepeatable interaction patterns with clear arguments and expected context.
02 · Design

Shape a useful server contract

Before writing code, describe the user workflow, the data boundary, and the failure behavior. The contract should be understandable to both people and agent runtimes.

Start with one workflow

  1. Name the user outcome, such as “find an eligible policy and explain the decision.”
  2. List the minimum data and actions needed to achieve it.
  3. Separate read operations from mutations and high-impact actions.
  4. Define validation, authorization, timeouts, retries, and error messages.
  5. Specify what a successful result looks like and what the agent should do next.
Tool: search_claims Description: Find claims by policy number, status, and date range. Input: policyNumber: string, required status: "open" | "closed" | "all", optional fromDate: ISO date, optional toDate: ISO date, optional Output: claims: array of { id, status, openedAt, summary } Errors: INVALID_INPUT | NOT_AUTHORIZED | RATE_LIMITED | SERVICE_UNAVAILABLE

Names and descriptions

Use action-oriented names and describe when the tool should be used, what it changes, and what it returns.

Input schemas

Require critical values, constrain enums and formats, reject ambiguous input, and validate again on the server.

Output shape

Return compact, structured results with stable fields. Include identifiers and next-step information without dumping irrelevant data.

Failure behavior

Return errors that explain whether the agent should correct input, ask the user, retry, or stop.

03 · Capabilities

Expose tools, resources, and prompts deliberately

Each primitive answers a different question. Keeping their responsibilities distinct improves discovery, consent, and testing.

When the user needs...PreferExample
An action with a resultToolLook up an order, create a work item, or run a read-only report.
Reference informationResourceExpose a schema, policy document, or current service status.
A repeatable interactionPromptGuide a review with named arguments and a known output structure.

Make discovery safe

  • Publish only capabilities that the connected host is expected to use.
  • Keep descriptions factual. Do not rely on vague instructions such as “always call this first.”
  • Mark read-only and mutating behavior clearly in names, descriptions, and confirmations.
  • Return pagination, limits, and freshness information when results can be large or stale.
  • Keep secrets and internal implementation details out of tool descriptions and returned content.
Prompt injection still matters: content returned by an MCP server may be untrusted data. Treat records, documents, web pages, and tool results as data to analyze, not as authority to change permissions or bypass instructions.
04 · Security

Make permissions part of the design

An MCP server can turn an agent request into a real-world action. Authentication, authorization, validation, and user consent must be enforced at the server boundary.

Authenticate

Identify the caller and protect credentials in transit and at rest. Never ask the model to manage secrets.

Authorize

Check the user, service identity, tenant, resource, and action for every request. Do not trust tool names as permission checks.

Validate

Validate arguments, identifiers, ranges, URLs, paths, and payload sizes on the server before accessing downstream systems.

Confirm

Require explicit approval for destructive, financial, external, or irreversible actions. Prefer preview and dry-run modes.

Security review questions

  • Does every tool enforce authorization server-side?
  • Are mutating actions clearly separated from reads?
  • Are secrets excluded from logs and error messages?
  • Are external URLs, file paths, and queries constrained?
  • Are timeouts, rate limits, and payload limits configured?
  • Can a user preview the effect before committing?
  • Are dependencies and MCP SDK versions maintained?
  • Can the server fail closed when identity or policy is unavailable?
05 · Delivery

Test the contract, then operate it

Test MCP servers like APIs. The most valuable checks exercise discovery, valid and invalid inputs, permissions, failures, and the real host connection.

Unit tests

Validate schemas, business rules, authorization decisions, output shapes, and error mapping without network dependencies.

Contract tests

Verify that the server advertises the expected tools, resources, prompts, capabilities, and protocol behavior.

Integration tests

Connect to representative downstream services and exercise timeouts, rate limits, retries, and partial failures.

Host smoke tests

Connect from the intended Copilot host and verify discovery, consent, invocation, result rendering, and disconnect behavior.

Practical exercise: build a read-only server first

  1. Choose a small local dataset or mock API with no sensitive data.
  2. Expose one search tool with a strict input schema and bounded results.
  3. Add one resource that describes the dataset fields and freshness.
  4. Test valid input, missing input, oversized input, unauthorized access, and downstream failure.
  5. Connect it to Copilot, inspect the tool description, and run a user scenario.
  6. Record what the agent attempted, what the server allowed, and what the user saw.
  7. Only then consider adding a mutation, protected by preview and explicit confirmation.
Operational events to record: server_start | protocol_initialize | capability_discovery request_received | authorization_decision | validation_failed tool_started | tool_completed | tool_failed | rate_limited resource_read | prompt_selected | shutdown For each event: correlationId, timestamp, operation, status, duration, redacted actor/context, and a safe error summary.
Keep operations observable: correlate a host run, MCP request, downstream call, and final result without logging raw secrets or unrestricted user content.
06 · Readiness

MCP server readiness checklist

Use this checklist before making a server available to a team or production workflow.

  • The server has one named workflow and a clear owner
  • Tools, resources, and prompts have distinct responsibilities
  • Descriptions explain purpose, limits, and side effects
  • Inputs and outputs use stable, validated schemas
  • Authentication and authorization run at the server boundary
  • Mutations require appropriate confirmation or approval
  • Timeouts, rate limits, retries, and payload limits are defined
  • Secrets and sensitive data are excluded from logs
  • Contract, integration, and host smoke tests pass
  • Failures return actionable, non-sensitive errors
  • Protocol and SDK dependencies are maintained
  • Monitoring, incident ownership, and shutdown behavior are documented
Definition of done: a user can understand what the server exposes, an agent can discover the right capability, the server can reject unsafe requests, and the team can diagnose failures from safe operational evidence.
