Module 04 - Prompts Lab

Prompt Engineering

Six guided exercises for turning one-off requests into precise, reusable, testable prompts for GitHub Copilot.

~80 min total
6 exercises
Intermediate
Before You Begin

Use a safe branch or practice repository. Do not include secrets, personal data, or production credentials in prompt examples.

Prompts are strongest when they specify context, outcome, constraints, and evidence. Test them in fresh chats so you can tell which prompt produced the behavior.

EX 01Build a Reusable Prompt File15 min▼
Goal
Create a .prompt.md file for a repeated task so teammates can run the same workflow consistently.
  1. 1
    Choose a repeated task
    Pick a task such as adding an API endpoint, generating tests, reviewing a pull request, or updating documentation.
  2. 2
    Create the prompt
    Add .github/prompts/add-endpoint.prompt.md with a description, agent mode, clear task, and expected files.
    --- description: Add an API endpoint with validation and tests mode: agent --- Add the requested endpoint. Inspect existing patterns first. Update the route, handler, tests, and API documentation. Run the focused test command and report the result.
  3. 3
    Run and refine it
    Use Command Palette - Chat: Run Prompt, then revise the file when the output misses a required artifact.
Validation Checklist
✓Prompt file has valid frontmatter and a clear description
✓Prompt appears in Chat: Run Prompt
✓Run produces the named files and verification result
EX 02Add Variables and Input Contracts15 min▼
Goal
Make a reusable prompt flexible without making its required inputs ambiguous.
  1. 1
    Define the inputs
    Add variables for the entity, field, or feature name, and document the expected format and an example.
  2. 2
    Use variables in the task
    Reference every variable consistently and tell Copilot what to do when an input is missing or invalid.
    variables: - name: EntityName description: Existing entity in PascalCase, for example TodoItem - name: FieldName description: New field in PascalCase, for example Priority - name: FieldType description: Valid project type, for example string or DateTime?
  3. 3
    Try a valid and invalid input
    Run the prompt once with valid values and once with a missing or malformed value. Improve the failure guidance.
Validation Checklist
✓Variables have names, descriptions, formats, and examples
✓Valid inputs flow into every required task step
✓Invalid or missing input produces a useful stop message
EX 03Design Context and Constraints15 min▼
Goal
Give Copilot enough context to act accurately while keeping the prompt focused and portable.
  1. 1
    Map the context
    List the files, symbols, conventions, and examples the prompt needs. Distinguish required context from optional context.
  2. 2
    Write explicit constraints
    State allowed files, forbidden changes, dependency limits, compatibility requirements, and security boundaries.
  3. 3
    Compare context sizes
    Run the prompt with a minimal context request and a broad workspace request. Record which produced the more reliable result.
Prompt pattern: Role or perspective, relevant context, desired task, constraints, output format, and verification command.
Validation Checklist
✓Required context is named without unnecessary workspace scope
✓Constraints define allowed files and prohibited behavior
✓Context comparison has a recorded quality judgment
EX 04Specify an Output Contract10 min▼
Goal
Replace vague requests with an output contract that makes completeness and correctness easy to review.
  1. 1
    Name the deliverables
    Specify the files, code changes, tests, documentation, and summary that should exist when the prompt finishes.
  2. 2
    Define the report format
    Ask for changed files, decisions, commands run, test results, and unresolved risks in a fixed order.
  3. 3
    Review against the contract
    Run the prompt and mark each deliverable present, correct, and verified. Update the prompt for the first missing item.
Validation Checklist
✓Prompt names every required deliverable
✓Final response format includes commands and evidence
✓Output was reviewed against the contract
EX 05Evaluate and Improve a Prompt15 min▼
Goal
Evaluate prompt quality with evidence instead of deciding that a response is good because it sounds plausible.
  1. 1
    Create two versions
    Write a short one-sentence request and a structured version with context, constraints, output contract, and verification.
  2. 2
    Use fresh chats
    Run both versions against the same task and capture the responses, changed files, and test evidence.
  3. 3
    Score and revise
    Score correctness, completeness, convention fit, safety, and testability from 1 to 5. Revise the lowest-scoring dimension.
Validation Checklist
✓Two prompt versions were tested in comparable fresh chats
✓Scores cite observable output evidence
✓A revised prompt targets the lowest-scoring dimension
EX 06Govern a Team Prompt10 min▼
Goal
Make a reusable prompt safe, discoverable, and maintainable for other developers to run.
  1. 1
    Add guardrails
    Cover secrets, personal data, destructive commands, dependency installation, file scope, and required approvals.
  2. 2
    Document usage
    Add purpose, inputs, example invocation, expected outputs, owner, and review date in a nearby README.
  3. 3
    Run a handoff test
    Ask a teammate to use the prompt with an incomplete input and an unsafe-looking request. Improve the failure guidance.
Validation Checklist
✓Safety, scope, and approval guardrails are explicit
✓README documents purpose, inputs, output, owner, and example
✓Teammate test improves handling of incomplete or unsafe requests
