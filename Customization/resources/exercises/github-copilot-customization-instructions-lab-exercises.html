Module 04 - Instructions Lab

Copilot Instructions

Six guided exercises for writing durable repository guidance that gives Copilot the right context at the right scope.

~80 min total
6 exercises
Intermediate
Before You Begin

Use a safe branch or practice repository. Instructions should describe stable project conventions, not temporary task details or secrets.

Keep rules specific, testable, and close to the code they govern. When instructions conflict, the narrowest applicable scope should win.

EX 01Write Repository-Wide Instructions15 min▼
Goal
Create a concise .github/copilot-instructions.md that gives every Copilot conversation the essential project context.
  1. 1
    Create the file
    Add .github/copilot-instructions.md at the repository root.
  2. 2
    Document stable conventions
    Include the stack, architecture boundaries, naming rules, test commands, and security constraints.
    ## Tech Stack - TypeScript, Node.js, and Vitest ## Conventions - Keep business logic in src/services. - Add tests beside changed modules. ## Verification - Run npm test before reporting completion. ## Security - Never expose secrets or commit .env files.
  3. 3
    Test the guidance
    Ask Copilot to add a small function and inspect whether the response follows the documented conventions.
Validation Checklist
✓Global instructions file exists at the repository root
✓Rules cover stack, conventions, verification, and security
✓A generated change demonstrates the rules are applied
EX 02Create Scoped Instructions15 min▼
Goal
Use .instructions.md files and applyTo patterns to give different parts of the repository their own rules.
  1. 1
    Choose two boundaries
    Pick areas such as src/data and src/pages that need different conventions.
  2. 2
    Add frontmatter and rules
    Create one file per area with a precise applyTo glob and rules that apply only to that area.
    --- applyTo: 'src/data/**/*.ts' --- ## Data Layer Rules - Use repository interfaces for persistence. - Use parameterized queries. - Add a test for every query path.
  3. 3
    Compare the scopes
    Ask for one change in each area and verify that each response follows the correct local rules.
Validation Checklist
✓Two scoped instruction files have valid frontmatter
✓Each applyTo pattern matches only its intended files
✓Generated changes follow the correct local scope
EX 03Layer Project and Language Rules15 min▼
Goal
Build a useful instruction hierarchy without repeating or contradicting the same rule in several files.
  1. 1
    Separate concerns
    Keep repository-wide rules in the global file, language rules in a language-scoped file, and feature rules near the feature.
  2. 2
    Resolve duplication
    Remove repeated rules and rewrite vague guidance as an observable action with a clear scope.
  3. 3
    Document precedence
    Record which file owns each rule and what should happen when two applicable files disagree.
Rule of thumb: A smaller number of precise rules is easier for both developers and Copilot to follow than a large collection of overlapping instructions.
Validation Checklist
✓Global, language, and feature rules have distinct ownership
✓Duplicate and contradictory rules were removed
✓Precedence is documented with an example
EX 04Encode Testing and Security Guardrails15 min▼
Goal
Turn quality and security expectations into instructions Copilot can apply during implementation, not just reminders after the fact.
  1. 1
    Add verification commands
    Specify the formatter, linter, unit test, and build commands that must run for relevant changes.
  2. 2
    Add security boundaries
    State how to handle secrets, personal data, authentication, input validation, and dependency changes.
  3. 3
    Generate a test change
    Ask Copilot to modify a small module and verify that it includes tests and reports command results.
Validation Checklist
✓Instructions name the commands used to verify changes
✓Security rules cover secrets, input, and sensitive data
✓A generated change includes tests and verification evidence
EX 05Debug an Instructions Conflict10 min▼
Goal
Diagnose why Copilot is not following a rule by tracing file location, scope, syntax, precedence, and prompt context.
  1. 1
    Create a deliberate conflict
    Place one broad rule and one narrower rule that appear to disagree, then ask for a change in the narrower area.
  2. 2
    Inspect the likely causes
    Check the filename, frontmatter, glob match, rule wording, and whether the file is included in the current chat context.
  3. 3
    Fix and retest
    Make one change at a time, start a fresh chat, and record which change restored the expected behavior.
Validation Checklist
✓Conflict cause was traced to scope, syntax, precedence, or context
✓The fix changes the smallest necessary instruction surface
✓Fresh-chat retest confirms the expected rule is followed
EX 06Govern and Maintain Instructions10 min▼
Goal
Make instruction files reviewable, discoverable, and resilient as the repository and team evolve.
  1. 1
    Add ownership metadata
    Document the owner, scope, supported stack or versions, and last review date in a nearby README or catalog.
  2. 2
    Create a review checklist
    Review applicability, clarity, conflicts, security, test commands, and whether each rule still reflects the codebase.
  3. 3
    Run a handoff
    Ask a teammate to find the right instruction file, explain its scope, and use it for one small change.
Validation Checklist
✓Owner, scope, supported stack, and review date are recorded
✓Review checklist covers behavior, security, and conflicts
✓A teammate can locate and apply the right instructions
