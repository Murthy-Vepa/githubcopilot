Before You Begin

Use a disposable branch or practice repository. Do not include secrets, personal data, or unverified commands in a skill package.

A skill should be narrow enough to activate for a clear task, complete enough to act on, and bounded enough to avoid surprising tool use. Review activation, scope, examples, and maintenance ownership.

EX 01Choose and Bound a Capability15 min▼
Goal
Turn a repeated specialist task into a capability with a clear purpose, owner, inputs, outputs, and boundary.
  1. 1
    Choose a real recurring task
    Pick a task such as browser testing, database migrations, accessibility review, or release notes.
  2. 2
    Write the boundary
    Record what the skill does, what it does not do, which files it may use, and when a human must approve.
  3. 3
    Define observable success
    List the expected artifacts, commands, evidence, and failure conditions.
Validation Checklist
✓Capability has one narrow purpose and named owner
✓Inputs, outputs, and out-of-scope work are documented
✓Success evidence and human stop conditions are defined
EX 02Author the SKILL.md Contract20 min▼
Goal
Create a valid, discoverable skill package with metadata that helps Copilot select it for the right request.
  1. 1
    Create the package
    Create .github/skills/<skill-name>/SKILL.md. Use a short, descriptive, lowercase name.
  2. 2
    Write activation metadata
    Include a keyword-rich description with explicit WHEN and DO NOT USE FOR clauses.
    --- name: webapp-testing description: Guide for creating and running browser tests. WHEN: "browser test", "Playwright", "verify user flow". DO NOT USE FOR: production deployment or load testing. ---
  3. 3
    Add the first procedure
    Write the shortest complete path from request to verified result. Link supporting files instead of copying large reference material.
Validation Checklist
✓SKILL.md exists at the expected package path
✓Description includes useful triggers and exclusions
✓Procedure produces a defined, reviewable result
EX 03Package Progressive Disclosure15 min▼
Goal
Keep the main skill concise while making scripts, templates, examples, and reference material available when the task needs them.
  1. 1
    Separate the three levels
    Level one is the description, level two is the core procedure, and level three is supporting material loaded on demand.
  2. 2
    Add one supporting asset
    Create an examples/, scripts/, or templates/ file that removes repetition from the main procedure.
  3. 3
    Link it from SKILL.md
    State when the asset should be opened or run and what evidence it produces.
Design check: If the skill needs a long history lesson before it can act, move detail into a reference file and improve the first-level description.
Validation Checklist
✓Main SKILL.md stays focused on the common procedure
✓At least one supporting asset is linked and usable
✓Supporting asset has a clear load or execution condition
EX 04Test Skill Activation15 min▼
Goal
Test whether the skill activates for the intended task, stays quiet for unrelated work, and handles ambiguity safely.
  1. 1
    Run three prompts
    Use one prompt that should activate the skill, one that should not, and one ambiguous prompt near the boundary.
  2. 2
    Record the behavior
    Capture whether the skill loaded, which instructions were followed, and which context or files were requested.
  3. 3
    Refine the description
    Add missing trigger terms or exclusions, then repeat the ambiguous test.
Validation Checklist
✓Positive prompt activates the intended skill
✓Negative prompt does not cause an unrelated activation
✓Ambiguous prompt has a documented safe response
EX 05Add Tools, Scripts, and Guardrails10 min▼
Goal
Make skill automation useful without granting silent access to secrets, destructive commands, or unrelated workspace content.
  1. 1
    List every action
    Mark each read, write, execute, and external-network action required by the skill.
  2. 2
    Add explicit guardrails
    Require confirmation before destructive commands, secret access, dependency installation, or changes outside the named folders.
  3. 3
    Test a failure path
    Give the skill an unavailable dependency, missing file, or unsafe request and document how it should stop.
Validation Checklist
✓All tool and script actions are documented by permission type
✓Destructive or external actions require approval
✓Failure path stops safely with an actionable message
EX 06Maintain and Handoff a Skill10 min▼
Goal
Leave the skill understandable, testable, and maintainable for the next developer who inherits it.
  1. 1
    Write the ownership record
    Document the owner, supported versions, dependencies, test prompts, and last review date.
  2. 2
    Create a change checklist
    Include activation tests, procedure tests, script tests, security review, and documentation review.
  3. 3
    Run a handoff review
    Ask a partner to explain when the skill should load, what it can change, and how to recover from failure.
Validation Checklist
✓Owner, dependencies, supported scope, and review date are recorded
✓Maintenance checklist covers activation, behavior, and security
✓A partner can explain use, limits, and recovery steps
