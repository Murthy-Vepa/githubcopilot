Module 05 - Plugins Lab

Copilot Plugins

Six guided exercises for discovering, configuring, testing, and governing reusable Copilot plugins and their tools, instructions, and integrations.

~85 min total
6 exercises
Intermediate
Before You Begin

Use a disposable branch or practice workspace. Review plugin manifests and startup commands before enabling anything, and use mock data wherever possible.

Plugins can bundle instructions, skills, tools, and external integrations. Treat every plugin as untrusted code until its permissions, network access, dependencies, and data handling are understood.

EX 01Discover the Plugin Package12 min▼
Goal
Understand what a plugin contributes and identify its boundaries before installing or activating it.
  1. 1
    Inspect the manifest
    Locate the plugin manifest and record its name, version, description, entry points, dependencies, and supported Copilot surfaces.
  2. 2
    Inventory bundled components
    List included instructions, skills, agents, prompts, hooks, MCP servers, scripts, and configuration files.
  3. 3
    Draw the trust boundary
    Mark which components read files, execute commands, access networks, or send data outside the workspace.
Validation Checklist
✓Plugin manifest and version are identified
✓All bundled components and entry points are inventoried
✓Trust boundaries and external effects are documented
EX 02Install and Configure a Plugin15 min▼
Goal
Enable a plugin in a controlled workspace and configure only the settings required for the exercise.
  1. 1
    Choose a safe source
    Use an approved repository, local sample, or disposable test plugin. Check its ownership, release history, and documentation.
  2. 2
    Configure the minimum surface
    Enable only the required components and set explicit paths, commands, timeouts, and environment values.
    { "plugin": { "name": "workspace-review", "enabled": true, "tools": ["review_changed_files"], "timeout": 5000 } }
  3. 3
    Verify activation
    Restart or reload the supported Copilot surface, confirm the plugin appears once, and record how to disable it.
Validation Checklist
✓Plugin source and version were reviewed before installation
✓Only required components and least-privilege settings are enabled
✓Activation and disable steps are verified
EX 03Trace Plugin Instructions and Tools15 min▼
Goal
Separate the plugin's instructions from its executable tools and understand how each changes an agent workflow.
  1. 1
    Run an inspection prompt
    Ask Copilot to describe the plugin's available capabilities and identify which instruction or tool was selected.
  2. 2
    Inspect tool schemas
    Record each tool's input fields, required values, output shape, side effects, and error behavior.
  3. 3
    Compare with and without the plugin
    Run the same bounded task with the plugin disabled and enabled. Note changes in available actions, output, and user approvals.
Good boundary: Instructions shape behavior; tools perform operations. Document the handoff between them instead of treating the plugin as a black box.
Validation Checklist
✓Plugin instructions and executable tools are distinguished
✓Tool inputs, outputs, and side effects are recorded
✓The same task was compared with the plugin off and on
EX 04Control Permissions and Secrets15 min▼
Goal
Configure a plugin so credentials, files, network destinations, and command execution remain bounded and reviewable.
  1. 1
    List required permissions
    For every component, record file scope, command access, network destinations, environment variables, and write permissions.
  2. 2
    Use external secret storage
    Reference credentials through approved environment or secret-management mechanisms. Do not place tokens in manifests, prompts, logs, or source control.
    { "env": { "SERVICE_TOKEN": "${env:SERVICE_TOKEN}" } }
  3. 3
    Test the denied path
    Attempt an operation outside the declared scope and confirm the plugin refuses it or requests explicit approval.
Never commit secrets: Use placeholders in lab files and rotate any credential that was accidentally exposed.
Validation Checklist
✓Plugin permissions are documented by component
✓Secrets are externalized and absent from tracked files and logs
✓An out-of-scope operation is denied or approval-gated
EX 05Test Plugin Behavior and Failure Modes15 min▼
Goal
Prove that a plugin behaves predictably with valid input, invalid input, missing dependencies, and unavailable services.
  1. 1
    Create a bounded test matrix
    Include a normal task, empty input, malformed input, unavailable tool, timeout, denied permission, and duplicate invocation.
  2. 2
    Check user-visible behavior
    Confirm errors are actionable, sensitive values are redacted, approvals are clear, and partial results are labeled.
  3. 3
    Verify rollback
    For any write operation, test interruption and failure recovery. Confirm repeated runs do not create unsafe duplicate effects.
Validation Checklist
✓Test matrix covers valid, invalid, unavailable, and denied cases
✓Errors, approvals, partial results, and redaction are reviewed
✓Write operations have interruption and rollback coverage
EX 06Govern, Update, and Handoff a Plugin13 min▼
Goal
Make a plugin maintainable for team use with ownership, change review, versioning, rollback, and removal procedures.
  1. 1
    Create an ownership record
    Document purpose, maintainer, source, version, components, permissions, data handling, dependencies, and supported environments.
  2. 2
    Define update controls
    Require version pinning or review, changelog inspection, regression tests, security review, rollback, and a clean-workspace test.
  3. 3
    Run the handoff
    Ask a teammate to explain what the plugin adds, what it can access, how to test it, and how to disable or remove it safely.
Validation Checklist
✓Owner, source, version, permissions, and data handling are recorded
✓Update, regression, security, rollback, and removal steps are defined
✓A teammate can explain plugin use, risk, testing, and disable steps
