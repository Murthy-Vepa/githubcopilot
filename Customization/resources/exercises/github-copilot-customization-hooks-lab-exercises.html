Module 04 - Hooks Lab

Copilot Hooks

Six guided exercises for using lifecycle hooks to observe, validate, and control agent workflows with explicit safety boundaries.

~85 min total
6 exercises
Intermediate
Before You Begin

Use a disposable branch or practice workspace. Hooks may run commands automatically, so start with read-only actions and review every script before enabling it.

Keep hooks deterministic, fast, narrowly scoped, and safe when inputs are missing or unexpected. Never expose secrets or trust unvalidated command arguments.

EX 01Map the Hook Lifecycle10 min▼
Goal
Understand when hooks run and what workflow event each hook is allowed to observe or influence.
  1. 1
    List the lifecycle points
    Identify the available events in your Copilot or agent workflow, such as session start, tool invocation, file change, or session completion.
  2. 2
    Map inputs and outputs
    For each event, record the payload, environment, expected exit behavior, and whether the hook can block or only observe.
  3. 3
    Choose one safe use case
    Select a read-only use case such as logging tool names, checking changed file paths, or validating a command request.
Validation Checklist
✓Lifecycle events and their order are documented
✓Hook inputs, outputs, and blocking behavior are identified
✓A narrow, read-only use case is selected
EX 02Configure Your First Hook15 min▼
Goal
Create a minimal hook configuration that runs one reviewed command at one lifecycle point.
  1. 1
    Create the hook file
    Add the hook configuration in the supported workspace location and give it a descriptive name.
  2. 2
    Start with a harmless command
    Use a script that records a timestamp or validates a file path. Do not begin with deletion, network access, or credential handling.
    { "hooks": { "onToolCall": [ { "command": "node .github/hooks/log-tool-call.js", "timeout": 5000 } ] } }
  3. 3
    Trigger and disable it
    Run the workflow, confirm the hook fires once at the intended event, then disable it and confirm normal behavior returns.
Validation Checklist
✓Hook configuration uses the supported location and schema
✓Read-only hook runs at the intended lifecycle event
✓Hook can be disabled without changing application code
EX 03Validate Commands and Arguments15 min▼
Goal
Prevent a hook from becoming an unsafe command runner by validating inputs and limiting what it can execute.
  1. 1
    Define an allowlist
    Allow only the commands, file extensions, directories, or tool names required for the hook's purpose.
  2. 2
    Reject unsafe input
    Handle empty values, path traversal, shell metacharacters, unexpected arguments, and commands outside the allowlist.
  3. 3
    Test safe and unsafe cases
    Run the hook with a valid input, an invalid path, and an attempted destructive command. Record the exit code and message.
Safety boundary: Prefer direct process arguments over shell string concatenation. Never pass untrusted hook payloads directly to a shell.
Validation Checklist
✓Hook uses an explicit command or path allowlist
✓Unexpected paths, arguments, and shell characters are rejected
✓Safe and unsafe test cases have recorded outcomes
EX 04Inspect Hook Payloads and Logs15 min▼
Goal
Use structured logging to understand what a hook received and did without leaking secrets or creating noisy output.
  1. 1
    Capture a redacted payload
    Log event type, tool name, file scope, and result status. Redact tokens, environment variables, personal data, and full request bodies.
  2. 2
    Correlate one run
    Add a correlation identifier and timestamp so you can follow one hook invocation from input to outcome.
  3. 3
    Review the log volume
    Run several workflow events and decide which fields are useful for diagnosis and which should be removed.
Logging rule: Log enough to explain a decision, but never use logs as a second channel for secrets or unbounded prompt content.
Validation Checklist
✓Payload logging captures event context without sensitive data
✓One invocation can be correlated from input to outcome
✓Log fields and volume were reviewed and minimized
EX 05Handle Failure, Timeout, and Retry15 min▼
Goal
Make a hook fail predictably so a slow, unavailable, or broken helper does not silently corrupt an agent workflow.
  1. 1
    Define exit behavior
    Decide which failures block the workflow, which produce a warning, and which can be safely ignored.
  2. 2
    Set a timeout
    Use a short, explicit timeout and return a clear diagnostic that names the failed check without exposing private input.
  3. 3
    Test recovery
    Simulate a missing dependency, non-zero exit code, and timeout. Confirm whether retry is safe and whether duplicate side effects are possible.
Validation Checklist
✓Blocking and non-blocking failure behavior is documented
✓Timeout produces a bounded, actionable diagnostic
✓Missing dependency, failure, timeout, and retry cases are tested
EX 06Govern and Handoff a Hook15 min▼
Goal
Make a hook safe for team use by documenting ownership, permissions, lifecycle impact, and change review.
  1. 1
    Create an ownership record
    Document purpose, maintainer, lifecycle event, commands, permissions, data handled, timeout, and supported environments.
  2. 2
    Write a change checklist
    Require tests for safe and unsafe inputs, security review, log review, rollback steps, and a fresh-workspace check.
  3. 3
    Run a teammate handoff
    Ask a teammate to explain when the hook runs, what it can block, what it records, and how to disable it.
Validation Checklist
✓Owner, lifecycle, permissions, data, and supported environments are recorded
✓Change checklist covers safety, tests, logs, and rollback
✓A teammate can explain use, impact, and disable steps
