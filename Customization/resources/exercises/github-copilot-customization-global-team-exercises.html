Instructions

5 exercises
I-01Bootstrap Repo-Wide Copilot Instructions20 min▼
Create .github/copilot-instructions.md for metlife-investments-platform covering .NET 10 stack, architecture boundaries, C# naming conventions, verification commands, and non-negotiable financial security rules.
Without it, Copilot generates generic C# that ignores the layered architecture, EF Core patterns, and financial compliance requirements. This is the single highest-impact customization file.
Steps
1
Create .github/copilot-instructions.md at the repo root. Add Tech Stack: .NET 10, C# 13, ASP.NET Core Web API, Blazor Server, Entity Framework Core 9, SQL Server, xUnit + Moq + FluentAssertions, Azure DevOps CI.
2
Add Architecture Boundaries: business logic only in src/Investments.Services/; HTTP concerns only in src/Investments.Api/Controllers/; data access only via repository interfaces in src/Investments.DataAccess/; Blazor components in src/Investments.Web/.
3
Add Naming Conventions: PascalCase files and classes (PortfolioService.cs), interface prefix I (IPortfolioService), private fields _camelCase, async methods suffix Async, test classes suffix Tests.
4
Add Verification Steps: run dotnet test, dotnet build -warnaserror (zero warnings), dotnet format --verify-no-changes. Copilot must confirm these pass before declaring complete.
5
Add Security — Non-Negotiable: never log PII (account numbers, SSN, tax IDs, portfolio values tied to an individual); parameterized SQL/EF Core only — never string-concatenated queries; [Authorize] on protected controllers; validate inputs with FluentValidation.
6
Add Domain Context: MetLife Investments Management; domains include Portfolio, Fund, Trade, Asset, Holdings; financial calculations use decimal only — never double or float; soft-delete only on Portfolio and Trade records (DeletedAt column).
Tip
Keep each section under 10 bullet points. Add the decimal rule prominently — floating-point financial bugs are the most common .NET gotcha in investment applications.
Validation Checklist
Present This
Show one Copilot suggestion without the instructions file, then repeat with the file. Did Copilot use decimal for financial values and inject the repository interface correctly?
I-02Scoped Instructions for Blazor Components20 min▼

The glob src/Investments.Web/**/*.razor matches only .razor files. If you have .razor.cs code-behind files, add a second entry: src/Investments.Web/**/*.razor.cs.

I-03Encode API Security Guardrails for Controllers20 min▼
Create .github/instructions/api.instructions.md scoped to src/Investments.Api/** encoding ASP.NET Core security rules: FluentValidation, [Authorize], repository injection, ProblemDetails responses, and OWASP controls.
Without explicit instructions, Copilot often omits [Authorize], uses inline LINQ instead of repositories, or returns raw exception messages in error responses. Investment data APIs are high-value targets.
Steps
1
Create .github/instructions/api.instructions.md with applyTo: "src/Investments.Api/**".
2
Add input validation rule: inject and call a FluentValidation validator for every request DTO; reject with HTTP 400 (RFC 7807 ProblemDetails) if invalid — never process an unvalidated body.
3
Add auth rule: every controller touching investment or client data must have [Authorize]; use [Authorize(Policy = "PortfolioManager")] for write operations; return 401 for unauthenticated requests.
4
Add data access rule: inject repository interfaces from src/Investments.DataAccess/ — never instantiate DbContext directly in a controller; no inline LINQ in action methods.
5
Add error handling rule: use global exception middleware; return ProblemDetails with a correlationId — never include stack traces or SQL messages in responses.
Tip
Reference your actual policy names (PortfolioManager, ReadOnly, TradeExecutor). Copilot generates the correct attribute if policy names match what's registered in Program.cs.
Validation Checklist
Present This
Generate a "get fund by ID" action with and without the instructions file. How many security attributes were included automatically — and how many were missing without the file?
I-04Audit and Rationalize Conflicting Instructions15 min▼
Given the three instruction files you just created, identify conflicts and overlaps, produce a conflict log, assign clear rule ownership, and eliminate redundancy.
Rules that exist in both the global file and a scoped file create ambiguous output. A rule about error response shape in two files will cause Copilot to alternate between them.
Steps
1
List all instruction files in .github/: global copilot-instructions.md, blazor.instructions.md, api.instructions.md. Create a conflict log.
2
Scan for contradictions: global says "return JSON with message field on errors" but api.instructions.md says "use ProblemDetails". Log each contradiction.
3
Scan for duplicates: identical or near-identical rules in multiple files. Decide which file owns each rule.
4
Apply the ownership decision: narrowest scope wins. Move the rule to the most specific file, delete from broader files.
5
Re-test: ask Copilot to generate a Blazor component and an API controller. Confirm consistent, non-contradictory output.
Common trap
Keeping "important" rules in both files "just to be safe" creates ambiguity, not safety. Pick one owner per rule — the narrower the scope, the higher the priority.
Validation Checklist
Present This
Walk through one contradiction you found and explain why you chose the narrower file as owner. How would leaving the conflict harm code generation quality?

P-02xUnit + Moq Test Generation Prompt20 min▼
Author .github/prompts/generate-tests.prompt.md that generates comprehensive xUnit tests for a C# service class using Moq for mocks, FluentAssertions for assertions, and AAA structure with happy, boundary, and error paths.
Without explicit C# test conventions, Copilot mixes MSTest, NUnit, and xUnit APIs, forgets to reset mocks between tests, or misses async/await patterns on Task-returning methods.
Steps
1
Create .github/prompts/generate-tests.prompt.md with mode: agent. Specify: xUnit, Moq, FluentAssertions — no MSTest, no NUnit.
2
Define setup conventions: constructor injection for the SUT; Mock<IDependency> as private fields; no sharing mock state between tests.
3
Specify AAA with comment labels: // Arrange / // Act / // Assert. Test names: MethodName_Condition_ExpectedOutcome.
4
Define coverage: per public method — ≥1 happy path, ≥1 error path (_mock.Setup(...).ThrowsAsync(new ...)), ≥1 boundary test for nullable params.
5
Add post-generation step: run dotnet test --filter FullyQualifiedName~[ClassName]Tests and include results; flag methods that are hard to test.
Tip
Add: "For async methods, use await Assert.ThrowsAsync<T>() — never .Result or .Wait()." This prevents the most common xUnit deadlock in .NET test code.

P-05EF Core Query Performance Review Prompt20 min▼
Author .github/prompts/ef-performance-review.prompt.md that reviews repository/service code for EF Core anti-patterns: N+1 queries, missing AsNoTracking(), unbounded result sets, and sync-over-async.
The investments platform queries large datasets — portfolios with hundreds of holdings, funds with multi-year histories. EF Core anti-patterns at this scale degrade P95 latency from 50ms to 8 seconds.
Steps
1
Create the prompt with mode: ask. Define anti-patterns: N+1 (navigation property access in a loop without Include()), tracking overhead (missing AsNoTracking() on read-only queries), unbounded results (no .Take(n)), sync-over-async (.Result or .Wait()).
2
Add missing index signals: WHERE clauses on columns without HasIndex() in EF model config. Include a recommendation to add a migration for the missing index.
3
Define output format: findings table with File:Line, Anti-Pattern, Estimated Impact, and a corrected code snippet per finding.
4
Test on a real repository class or a sample with at least one deliberate N+1 issue.
Watch out
AsNoTracking() is a performance win for read-only queries, but avoid it when you intend to update the entity — EF Core won't track changes and SaveChanges() will do nothing.
Validation Checklist
Present This
Show the N+1 detection in action. What was the "before" code and the suggested Include() fix? How many SQL queries does this reduce?

A-01Read-Only Security Reviewer Agent20 min▼
Author .github/agents/security-reviewer.agent.md — a read-only agent that reviews C# code for OWASP violations, PII exposure, and investments-domain security rules, producing a signed severity-rated report.
Investment data is a high-value target. A dedicated agent that cannot modify files forces the human reviewer to make all remediation decisions. The agent's role is to surface findings, not to fix-and-continue.
Steps
1
Create the agent file. Set tools to [read_file, list_directory, search_workspace] — explicitly no write tools.
2
Define the role: "Senior application security engineer — OWASP Top 10, ASP.NET Core security, financial services compliance (SOX, FINRA, GDPR)."
3
Define method: (1) read instruction files first; (2) list changed files; (3) check each file for OWASP, PII in logs, parameterized queries, [Authorize], FluentValidation; (4) produce report.
4
Add hard boundary: for CRITICAL findings (hardcoded connection string, missing auth on financial endpoint) — pause and ask for confirmation before continuing.
5
Define report format: Scope, Date, files reviewed, findings table (# | Severity | Category | File:Line | Finding | Remediation), Overall Risk, Required fixes before merge.
Critical design rule
Tool list must not include create_file or edit_file. If the agent can modify code, it becomes a "fix-and-ship" agent that bypasses human review. Read-only + report is the correct model.
Validation Checklist
Present This
Run the agent on a C# controller missing [Authorize] with a log statement including an account number. Did it find both? Did it attempt to fix the code?

S-02EF Core Migration Safety Review Skill20 min▼
Author .github/skills/review-db-migration/SKILL.md that checks EF Core migration files for 6 safety properties: reversibility, non-destructiveness, FK index coverage, NOT NULL safety, transaction wrapping, and large-table awareness.
A bad migration on the investments platform can lock the Portfolios or Trades table during market hours. A skill codifying the migration checklist catches dangerous patterns before the deploy pipeline.
Steps
1
Create the skill. Trigger phrases: "review migration", "check migration", "migration safe", "db migration".
2
Check 1 — Reversible: both Up() and Down() methods with symmetric operations. FAIL if Down() is empty or throws NotImplementedException.
3
Check 2 — Non-Destructive: no DropTable, no DropColumn on a queried column, no Truncate in Up().
4
Check 3 — FK Index: every AddForeignKey() paired with a CreateIndex() on the FK column. SQL Server does NOT auto-create FK indexes.
5
Checks 4–6: (4) NOT NULL Safety — new NOT NULL columns need defaultValue: or two-step migration; (5) Transaction wrapping; (6) Large Table — Trades/AuditLog require ONLINE = ON in raw SQL.
SQL Server vs PostgreSQL
SQL Server does NOT automatically create indexes for foreign keys (unlike PostgreSQL). Every FK without an explicit index causes table scans on joins. This check is more critical on SQL Server.
Validation Checklist
Present This
Run on a migration that adds a FK without an index. Show the FAIL result and the corrected CreateIndex() call the skill recommends.
S-03Financial Services Compliance Check Skill25 min▼
Author .github/skills/compliance-check/SKILL.md that checks C# code for PII in log statements, missing audit events on financial writes, hard-delete on regulated records, and SOX change control evidence.

Steps
1
Create the skill. Triggers: "compliance check", "privacy review", "audit this", "pii check", "finra check".
2
Rule 1 — PII in Logs: scan _logger.* calls for PII field names (AccountNumber, TaxId, SSN, DateOfBirth, PortfolioHolderName). FAIL if within 3 lines of a log call.
3

H-01Pre-Change Secret Detection Hook20 min▼

H-02Post-Change Build and Test Verification Hook20 min▼
Author .github/hooks/build-and-test.hook.md that runs after any write to src/**/*.cs, executes dotnet build and the corresponding test class, and feeds failures back into the agent session before it declares completion.
Without this hook, an agent can deliver syntactically valid C# that doesn't compile or breaks existing tests. The hook creates a mandatory self-verification loop before the agent is done.
Steps
1
Create the hook. Set event: post_file_write, scope: "src/**/*.cs". Does NOT trigger on db/Migrations/, docs/, or *.json.
2
Action sequence: (1) find changed file's *.csproj, (2) run dotnet build [project] --no-restore — if compilation fails, return errors to agent and stop, (3) find [ClassName]Tests.cs, (4) run dotnet test --filter FullyQualifiedName~[ClassName]Tests --no-build.
3
On compilation failure: return full compiler output with "Fix these compilation errors before declaring this task complete."
4
On test failure: return failing test names and errors with "Fix the failing tests or explain why this breakage is acceptable." 90-second test timeout emits WARN but does not block.

Always run dotnet build before dotnet test. If build fails, test output is meaningless and confusing. Sequencing avoids the agent chasing test failures that are actually compilation errors.
