GitHub Copilot Fundamentals

Choose the model for the situation.

Model selection is a practical tradeoff between speed, reasoning depth, context, input type, availability, and cost. Start with the work you need to complete, then choose a model that is proportionate to the risk and complexity.

Scenario-first guidanceTask and cost awareVerify availability in Copilot
01

Model selection is not a popularity contest

A model that is excellent for architecture may be unnecessarily slow for a one-line edit. A fast model may be ideal for routine work but struggle with a cross-cutting change.

Start with Auto when you are uncertain. Then switch deliberately when the result is too slow, too shallow, too expensive, or unable to handle the input type.
Speed and throughput

How quickly do you need an answer, and how many similar requests will you run?

Reasoning depth

Does the task require tradeoffs, multi-step diagnosis, or coordination across files?

Context and tools

Will the model need sustained repository context, tool calls, or long-running agent work?

Input and output

Does the task involve screenshots, diagrams, code, prose, structured data, or a precise patch?

03

Scenario-based model decisions

These are starting points. Measure the result on your repository and change models when the task evidence says to change.

Scenario 1 · Add a small endpoint or component

The requirement is clear, the change is localized, and the repository already contains a nearby example.

First choice: a balanced or fast coding model. Give it the nearby implementation, the acceptance criteria, and the focused test command.

Switch models when

  • The model cannot infer the local pattern after you provide a concrete example.
  • The change unexpectedly crosses multiple layers or services.

Scenario 2 · Diagnose a failing test or production error

The failure may involve logs, control flow, configuration, and a chain of related calls. The cost of a confident but wrong explanation is high.

First choice: a deeper-reasoning model with the error, relevant code path, reproduction command, and observed-versus-expected behavior.

Switch models when

  • The response repeats generic debugging advice without narrowing the hypothesis.
  • The investigation requires more context or multiple tool-driven inspection steps.

Scenario 3 · Plan a multi-file refactor

You need to understand dependencies, preserve public behavior, identify migration risks, and sequence changes safely.

First choice: a strong reasoning model for discovery and planning. Use a faster model later for mechanical edits that follow the approved plan.

Switch models when

  • The plan misses a dependency or contradicts repository evidence.
  • The model proposes broad changes without a clear validation strategy.

Scenario 4 · Review a screenshot or UI layout

The task depends on visual input such as spacing, hierarchy, responsive behavior, or a visual regression.

First choice: a vision-capable model available in the current Copilot surface. State what must be inspected and attach the smallest useful image.

Switch models when

  • The model cannot access or interpret the visual input in your current surface.
  • The task becomes implementation-heavy and needs repository inspection rather than visual critique.

Scenario 5 · Process a large batch of similar files

The operation is repetitive, bounded, and easy to validate with a script, formatter, or test.

First choice: a fast, cost-aware model or deterministic automation. Use the model to generate or review the transformation, then let tooling enforce consistency.

Switch models when

  • Each file has meaningful exceptions that require reasoning.
  • Validation cannot reliably detect a bad transformation.

Scenario 6 · Complete a multi-step agent task

The agent must inspect the repository, plan, edit, run checks, recover from failures, and stop at permission boundaries.

First choice: a capable tool-use and context model with narrow permissions, explicit stop conditions, and focused validation.

Switch models when

  • The agent loses the task objective after tool calls or makes changes outside scope.
  • It cannot recover from a failed command without repeating the same action.

Scenario 7 · Summarize documentation or translate technical prose

The task is primarily language transformation with a defined audience, terminology, and output shape.

First choice: a fast or balanced general-purpose model. Supply a glossary and a short example of the desired tone.

Switch models when

  • Terminology, factual nuance, or structured output is consistently wrong.
  • The document is sensitive and requires an approved enterprise model or workflow.

Scenario 8 · Optimize usage across a team

The team wants quality, predictable latency, and responsible credit consumption rather than the strongest model for every request.

First choice: define a routing policy: fast models for routine tasks, balanced models for normal development, and deep models for high-risk or ambiguous work.

Switch models when

  • Rework costs more than the additional model usage would have cost.
  • A task category repeatedly fails the team's quality threshold.
04

Use a short selection experiment

Do not compare models using only one impressive response. Use the same task, the same context, and observable criteria.

  1. Choose a representative task from the work category you want to improve.
  2. Give each candidate model the same prompt, files, constraints, and expected output.
  3. Record time to useful result, correction effort, validation result, and approximate usage.
  4. Repeat on a second task so the decision is not driven by a single lucky response.
  5. Choose the least expensive and fastest model that consistently meets the quality bar.
MeasureQuestion to record
CorrectnessDid the result satisfy the requirement and preserve existing behavior?
ReworkHow many corrections or retries were needed before validation passed?
LatencyWas the wait appropriate for the task and workflow?
Context fitDid the model use the relevant files and ignore distracting context?
Cost and limitsIs the usage sustainable for the expected volume and plan?
Do not confuse confidence with correctness. A fluent explanation is not evidence. Require tests, source references, reproducible steps, or an explicit human review for consequential work.
05

Model selection checklist

Use this before standardizing a model choice in a team guide or workflow.

  • The task category and risk level are clear
  • The chosen model supports the required input type
  • The model is available in the user's Copilot plan and surface
  • Fast, balanced, and deep alternatives were considered
  • The task has a focused validation or review signal
  • Expected volume and credit impact are understood
  • Tool permissions and data boundaries are explicit
  • The selection was tested on representative work
Practical policy: standardize routing guidance, not a permanent model name. Model availability, capabilities, limits, and pricing change. Revisit the decision when the task, product surface, or quality bar changes.
