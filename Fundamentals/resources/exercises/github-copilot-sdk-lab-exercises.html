Before You Begin

This lab uses C# with .NET 8 or later and the GitHub.Copilot.SDK NuGet package. Use a disposable console application so you can experiment with sessions, tools, permissions, and cleanup safely.

Verify the Copilot CLI runtime is available, and keep credentials in environment variables. Never put tokens or personal data in prompts, source files, or telemetry.

EX 01Install the SDK and Connect a Client10 min▼
Goal
Create the smallest working SDK program and understand that the SDK connects your application to the Copilot CLI runtime.
  1. 1
    Create a .NET console project and install the SDK:
    dotnet new console -n CopilotSdkLab
cd CopilotSdkLab
dotnet add package GitHub.Copilot.SDK
  2. 2
    Verify the runtime and authentication before writing application code:
    copilot --version
gh auth status
  3. 3
    Replace Program.cs with a client, session, prompt, response output, and cleanup:
    using GitHub.Copilot;

      await using var client = new CopilotClient();
      await client.StartAsync();
      await using var session = await client.CreateSessionAsync(new SessionConfig
      {
        Model = "gpt-5"
      });

      var done = new TaskCompletionSource();
      session.On<SessionEvent>(evt =>
      {
        if (evt is AssistantMessageEvent message)
          Console.WriteLine(message.Data.Content);
        else if (evt is SessionIdleEvent)
          done.SetResult();
      });

      await session.SendAsync(new MessageOptions { Prompt = "What is 2 + 2?" });
      await done.Task;
  4. 4
    Run the sample with dotnet run. Confirm the process exits cleanly through await using disposal.
Validation Checklist
✓
SDK package and runtime are available
✓
A prompt returned a response and the client stopped cleanly
EX 02Manage Sessions and Conversation State12 min▼
Goal
Use a session as the unit of conversation, inspect its identifier, and understand the difference between sending a message and waiting for idle.
  1. 1
    Change the sample to send two related messages through the same session:
    await session.SendAsync(new MessageOptions
      {
        Prompt = "Remember the number 42 for this session."
      });
      await session.SendAsync(new MessageOptions
      {
        Prompt = "What number did I ask you to remember?"
      });
      await done.Task;
  2. 2
    Print the session ID and record it in the terminal output. Explain what state belongs to the session versus the client.
  3. 3
    Use SendAsync, subscribe to SessionIdleEvent, and identify which event tells your app the turn is complete.
  4. 4
    Dispose the session, then use ResumeSessionAsync(sessionId) with a new client to continue the conversation when session storage is enabled.
Keep session IDs out of logs that may contain user data. In a real app, define how long session state should remain resumable.
Validation Checklist
✓
Two messages shared context in one session
✓
Explained SendAsync, SessionIdleEvent, disposal, and resume
EX 03Stream Responses and Handle Events12 min▼
Goal
Render incremental response deltas for a responsive application while keeping completion and error handling explicit.
  1. 1
    Create a streaming session and subscribe to typed message events:
    await using var session = await client.CreateSessionAsync(new SessionConfig
      {
        Model = "gpt-5",
        Streaming = true
      });

      session.On<SessionEvent>(evt =>
      {
        switch (evt)
        {
          case AssistantMessageDeltaEvent delta:
            Console.Write(delta.Data.DeltaContent);
            break;
          case SessionIdleEvent:
            Console.WriteLine("\n[complete]");
            break;
        }
      });
  2. 2
    Send a prompt that produces a multi-paragraph answer. Observe the difference between streamed deltas and the final idle event.
  3. 3
    Add an error handler and an abort path. Test cancellation with a long-running prompt rather than leaving a request uncontrolled.
Validation Checklist
✓
Displayed response text incrementally
✓
Handled idle, error, and cancellation behavior
EX 04Give the Agent a Safe Custom Tool15 min▼
Goal
Define a deterministic application tool and observe how the model requests it through the SDK.
  1. 1
    Define a read-only weather tool with a narrow schema and deterministic sample result:
    using GitHub.Copilot;
using Microsoft.Extensions.AI;
using System.ComponentModel;

var getWeather = CopilotTool.DefineTool(
    ([Description("City name")] string city) =>
        new { city, condition = "sunny", temperature = "72F" },
    factoryOptions: new AIFunctionFactoryOptions
    {
        Name = "get_weather",
        Description = "Get sample weather for a city"
    });

await using var session = await client.CreateSessionAsync(new SessionConfig
{
    Model = "gpt-5",
    Tools = [getWeather]
});
  2. 2
    Ask: What is the weather in Seattle? and observe the typed tool handler result.
  3. 3
    Log the tool input and output. Confirm the handler validates or safely handles an unexpected city value.
  4. 4
    Refactor the handler so it never reads secrets, writes files, or performs network calls without an explicit design decision.
A tool is application code with an AI-controlled caller. Keep schemas narrow, validate inputs, and return the minimum data needed.
Validation Checklist
✓
Tool schema, input, handler, and result are visible
✓
Tool cannot access secrets or perform unintended side effects
EX 05Enforce Permission Decisions12 min▼
Goal
Make permission handling an explicit part of the host application instead of allowing every requested operation.
  1. 1
    Add an OnPermissionRequest handler that rejects shell requests and approves only the harmless operation you intend to test:
    await using var session = await client.CreateSessionAsync(new SessionConfig
{
    OnPermissionRequest = async (request, invocation) =>
    {
        if (request is PermissionRequestShell shell)
            return PermissionDecision.Reject($"Shell denied: {shell.FullCommandText}");

        return PermissionDecision.ApproveOnce();
    }
});
  2. 2
    Ask the agent to use a tool that requires approval. Observe the request kind and the rejection feedback.
  3. 3
    Compare PermissionDecision.ApproveOnce(), session or location approval, Reject(), and NoResult(). Choose the least persistent decision for this lab.
  4. 4
    Write a test that proves a denied request cannot invoke the protected operation.
Validation Checklist
✓
Denied operation returned feedback and did not execute
✓
Permission behavior has an automated test
EX 06Extend and Operate the Agent Safely14 min▼
Goal
Connect an optional MCP server or custom agent, then define the lifecycle, observability, and cleanup rules your host application needs.
  1. 1
    Optional MCP path: configure a known, trusted server with an explicit URL and ask the agent to perform one read-only operation. Review the server configuration before connecting.
    var sessionConfig = new SessionConfig
{
    McpServers = new Dictionary<string, object>
    {
        ["github"] = new
        {
            Type = "http",
            Url = "https://api.githubcopilot.com/mcp/"
        }
    }
};

await using var session = await client.CreateSessionAsync(sessionConfig);
  2. 2
    Optional custom agent path: define a narrow pr-reviewer agent with a prompt that focuses on security and maintainability, then select it at session creation.
  3. 3
    Add cleanup in a finally block, or use await using for the client and session. Configure TelemetryConfig to diagnose latency and tool failures without recording secrets or full user prompts.
  4. 4
    Document the production boundary: allowed tools, session retention, retry behavior, cancellation, error handling, and who can approve permissions.
Skip MCP and custom agents if you do not have a trusted test configuration. The lifecycle, permission, and cleanup checks still complete the exercise.
Validation Checklist
✓
Optional extension was read-only, scoped, and reviewed
✓
Lifecycle, telemetry, cleanup, and production boundaries are documented
