GitHub Copilot CLI
Lab Exercises

Six guided exercises to explore a repository, plan and implement a bounded change, inspect the diff, and keep tool approvals under your control.

⏱ ~75 min total
6 exercises
Terminal required
GitHub Copilot access needed

Before You Begin

Use a small, non-production repository with a clean working tree. Replace the example paths and test commands with those used by your project.

Copilot proposes; you authorize. Read every command, keep secrets out of prompts, and inspect git diff before keeping a change.

EX 01Install, Launch, and Orient10 min▼
Goal
Start Copilot CLI in the correct repository and learn the controls that keep a session understandable.
  1. 1
    Install the CLI if needed, then open a terminal in a test repository:
    npm install -g @github/copilot
cd path/to/your-repository
copilot
  2. 2
    Run /help, then check the working directory with /cwd. Confirm it is the repository you intended.
  3. 3
    Run /context and /session. Note what context and workspace information the CLI reports.
  4. 4
    Use /exit to end the session, then relaunch it from the same repository.
Validation Checklist
✓
CLI launched from the intended repository
✓
Used /help, /cwd, /context, and /session
EX 02Explore the Repository with Evidence12 min▼
Goal
Use natural-language prompts to build a useful mental model without asking Copilot to change files.
  1. 1
    Ask Copilot to map the repository:
    map the architecture of this repository. Identify the application entry point, main modules, test projects, and build command. Do not modify files.
  2. 2
    Ask it to trace one real workflow from entry point to persistence or external API:
    trace the login or primary user request end to end. Cite the files and methods that support each step, and call out anything uncertain.
  3. 3
    Verify two claims by opening the cited files yourself. Record one accurate claim and one assumption or missing detail.
Use concrete file names and evidence requests. A confident answer without source references is a hypothesis, not project documentation.
Validation Checklist
✓
Repository map names the real entry point and test command
✓
Two workflow claims were verified against source files
EX 03Plan Before You Change Anything12 min▼
Goal
Create a bounded implementation plan before granting Copilot permission to edit files.
  1. 1
    Choose a small behavior change, such as adding a filter, improving an empty state, or adding validation. Do not choose authentication, deployment, or data deletion.
  2. 2
    Use /plan, then provide a constrained request:
    Inspect the existing patterns and create a plan only for [your change]. Name the files you would change, acceptance criteria, focused tests, and validation command. Do not edit files.
  3. 3
    Compare the plan with the repository. Remove speculative files and add any missing acceptance criterion before approving implementation.
Validation Checklist
✓
Plan was produced before any file edit
✓
Plan includes files, acceptance criteria, tests, and a check command
EX 04Implement a Small Change with Guardrails15 min▼
Goal
Turn the approved plan into a focused change while keeping the command and file boundaries visible.
  1. 1
    Before implementation, run git status and confirm the working tree is clean or that your existing work is understood.
  2. 2
    Ask Copilot to implement only the approved plan and to stop before unrelated files or commands:
    Implement the approved plan only. Preserve the existing public API and project conventions. Make the smallest change that satisfies the acceptance criteria. Stop if you need to change an unlisted file or run a destructive command.
  3. 3
    Review each proposed tool call. Allow only commands that are necessary for the task; deny anything outside scope.
  4. 4
    Run /diff and compare the changed files with the approved plan.
Keep Ask mode for the first run. Do not use /allow-all for a learning exercise or a repository you do not fully control.
Validation Checklist
✓
Only approved files were changed
✓
Every tool call was reviewed before approval
EX 05Test, Review, and Refine15 min▼
Goal
Validate the change with focused tests and use a separate review pass to challenge the result.
  1. 1
    Ask Copilot to identify the narrowest test command for the changed behavior. Confirm the command against the project files before running it.
  2. 2
    Run the focused test or build, then provide the real output if it fails:
    Run the focused validation for the changed behavior. If it fails, explain the root cause from the output, propose the smallest fix, and wait for approval before editing.
  3. 3
    Run /review. Verify at least two findings against the source, and reject findings that are not supported by evidence.
  4. 4
    Inspect git diff and git status. Keep the change only when the acceptance criteria and validation result agree.
Validation Checklist
✓
Focused test or build command was run and understood
✓
Review findings were verified against the source and diff
EX 06Customize the Session Boundary11 min▼
Goal
Make the CLI aware of project conventions and understand how tools and MCP servers expand its operating boundary.
  1. 1
    Run /init in a disposable or practice repository. Review the generated instruction file and remove any inaccurate assumptions.
  2. 2
    Add three specific rules: the build or test command, a project naming convention, and a rule requiring focused tests for behavior changes.
  3. 3
    Start a new session and ask Copilot to describe those conventions. Use /instructions if you need to inspect instruction sources.
  4. 4
    Optional: use /mcp to inspect configured MCP servers. Approve a tool call only when you understand its server, target, and requested permission.
Never place secrets in instruction files or prompts. Treat an MCP server as an extension of the tool boundary and review its configuration before connecting it.
Validation Checklist
✓
Instruction rules are project-specific and verifiable
✓
MCP configuration was inspected or safely skipped

Bonus Challenge: Terminal Playbook

Choose a small recurring maintenance task. Write a four-line playbook containing the goal, scope, constraint, and validation command. Run it in a fresh session, use /clear when context drifts, and compare the result with your acceptance criteria.
