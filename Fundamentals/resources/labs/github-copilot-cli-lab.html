Lab

Copilot CLI

Build a complete Task Manager REST API from scratch using only GitHub Copilot CLI as your coding partner, then take it through testing, review, delegation, and secure automation.

1.5–2 hoursBeginner → IntermediateTerminal-firstSource lab ↗
Copilot CLI is evolving fastFeatures and commands change frequently. Run /changelog inside the CLI or check the official docs if something looks different.

Objective

In this lab you will build a complete Task Manager REST API from scratch using only GitHub Copilot CLI as your coding partner. You won't open an editor. Every file, test, bug fix, and commit happens through the terminal.

Along the way you'll learn installation, interactive chat, plan mode, non-interactive scripting with copilot -p, custom instructions, code review, IDE integration, security sandboxing, and more, in context as you need each capability.

What You'll Build

  • Express.js server with CRUD endpoints: GET, POST, PUT, and DELETE
  • Input validation with Zod
  • Jest test suite with more than 80% coverage
  • Error handling middleware
  • Custom Copilot instructions that enforce coding standards
  • Git history with AI-generated commit messages
  • A code review pass that catches real bugs
  • A React frontend connected to the API through a plugin
  • End-to-end Playwright tests generated by Copilot

Prerequisites

You need an active GitHub Copilot subscription, Node.js 22 or later, and Docker Desktop 4.58 or later for Exercise 10.

Exercise 2

Scaffold with Plan Mode

Instead of writing boilerplate yourself, use Plan Mode to have Copilot design and build the project skeleton.

2.1 Switch to Plan Mode

Press Shift+Tab to cycle from interactive to plan mode. The mode indicator changes in your prompt.

2.2 Describe What You Want

Prompt with the following text and watch as it executes. This takes a minute or less.

Create a Node.js REST API project for a task manager. Use Express.js and Zod for validation. Set up the project with:
- package.json with scripts for start, dev, test, and lint
- src/index.js as the entry point (port 3000)
- src/routes/tasks.js with full CRUD routes (GET /, GET /:id, POST /, PUT /:id, DELETE /:id)
- src/middleware/errorHandler.js for centralized error handling
- An in-memory array as the data store (no database needed)
- Jest configured for testing
- A .gitignore for Node.js

2.3 Review the Plan

Copilot presents a step-by-step plan describing files, contents, and commands. Check the structure, dependencies, and anything you would change. Select Suggest Changes to modify the plan:

Can you also add input validation on the POST and PUT routes using Zod schemas?

2.4 Approve and Execute

Select Accept plan and build on autopilot (recommended). Autopilot may need /experimental enabled. When prompted, select Enable all permissions (recommended). Copilot creates files, installs dependencies, creates and runs tests, and fixes issues while you watch.

  1. Create the project structure and each file
  2. Run npm init and npm install
  3. Create and run tests, fixing issues until they pass

2.5 Verify the Scaffold

Use the ! prefix to run shell commands without leaving Copilot:

!ls src/
!cat package.json
!npm start

Press Ctrl+C or Esc after confirming the server starts.

CheckpointYou have a running Express server with route files, error handling middleware, and a valid package.json. Copilot created it all.

Exercise 4

Add Custom Instructions

Custom instructions teach Copilot your team's conventions.

4.1 Initialize Instructions

/init

This creates .github/copilot-instructions.md. Review it with !cat .github/copilot-instructions.md, then create your own rules:

Create a .github/copilot-instructions.md with these project rules:

- Language: JavaScript (ES2022+, no TypeScript)
- Framework: Express.js with Zod validation
- Testing: Jest with describe/it blocks, aim for >80% coverage
- Error handling: Always use the AppError pattern from src/middleware/errorHandler.js
- Style: Use const over let, arrow functions, async/await (no callbacks)
- Naming: camelCase for variables/functions, PascalCase for classes
- All route handlers must validate input before processing
- Include JSDoc comments on all exported functions

State that the file should be overwritten if you want to replace the baseline. Run /restart to reload instructions.

4.2 See It in Action

Add a PATCH /tasks/:id/status endpoint that only updates the status field. Follow the project conventions.

Check that the output uses const, arrow functions, Zod validation, and JSDoc comments.

4.3 View Active Instructions

/instructions

Instructions created during a session may not appear until you restart or reload.

4.4 Add Path-Specific Instructions (Optional)

Create .github/instructions/tests.instructions.md with frontmatter "applyTo: **/*.test.js" and these rules:
- Use describe/it blocks (not test())
- Each describe block should have beforeEach for setup
- Test both success and error cases
- Use meaningful test names that describe behavior

Exercise 5

Break It, Then Fix It

Real development involves debugging. Introduce a bug and use Copilot to find and fix it.

5.1 Introduce a Bug

In @src/routes/tasks.js, change the DELETE route so it uses findIndex but forgets to check if the index is -1 before splicing. Just make the change, don't fix the bug.

5.2 Watch It Fail

!npm start

Create two tasks, then delete a nonexistent ID:

!curl -s -X POST http://localhost:3000/tasks -H "Content-Type: application/json" -d '{"title": "Task 1"}'
!curl -s -X POST http://localhost:3000/tasks -H "Content-Type: application/json" -d '{"title": "Task 2"}'
!curl -s -X DELETE http://localhost:3000/tasks/nonexistent-id
!curl -s http://localhost:3000/tasks

The server will not crash, but an existing task disappears. When findIndex returns -1, splice(-1, 1) removes the last item. It is a subtle but serious bug.

5.3 Ask Copilot to Find It

I think there's a bug in the DELETE endpoint. Review @src/routes/tasks.js and find any issues.

Copilot should identify the missing bounds check. Prompt Yes to apply the fix.

5.4 Use /review for a Broader Check

/review

The review agent scans all uncommitted changes and may find additional improvements. You can request focused feedback:

/review Review for security issues
/review Review for performance improvements

5.5 Use /diff to See All Changes

/diff

Scroll through the changes since the last commit. This is a good habit before committing.

CheckpointYou found and fixed a bug with conversational debugging and the /review agent, then inspected the result with /diff.
Exercise 6

Automate with copilot -p

The -p flag sends one prompt and outputs the result without an interactive session. This is the key to scripting with Copilot.

6.1 Generate a Commit Message

Exit with Ctrl+C twice or /exit. You can later use copilot --resume.

git add -A
git diff --cached | copilot -p "Write a concise conventional commit message for these changes."

git diff --cached | copilot --allow-tool='shell(git:*)' -p "Write a concise conventional commit message for these changes. And git commit with that message."
git log

6.2 Generate a README

copilot --allow-tool='write(README.md)' -p "Look at the files in this project and generate a comprehensive README.md with: project description, setup instructions, API endpoint documentation with curl examples, and how to run tests. Write the output to README.md."

Review it with cat README.md. The specific write permission is a least-privilege practice.

6.3 Generate Test Scaffolding

mkdir -p src/routes/__tests__
cat src/routes/tasks.js | copilot --allow-tool='write(src/routes/__tests__/tasks.test.js)' --model claude-haiku-4.5 -p "Generate a comprehensive Jest test file for this Express router. Test all CRUD operations, validation errors, and edge cases. Use supertest for HTTP assertions. Write the test file to src/routes/__tests__/tasks.test.js"

6.4 Pipe Errors for Diagnosis

npm test 2>&1 | copilot --allow-tool='shell(npm:*)' -p "These are test results. Explain any failures and suggest fixes." 2>/dev/null

The final redirect suppresses verbose execution output and leaves the analysis.

6.5 Batch Operations in a Script

copilot --allow-tool='write(scripts/pre-commit.sh), shell(mkdir), shell(chmod)' -p "Write a shell script called scripts/pre-commit.sh that:
1. Runs npm test
2. If tests pass, generates a conventional commit message from the staged diff
3. Prints the suggested message and asks for confirmation
Output ONLY the shell script content."

Review scripts/pre-commit.sh.

CheckpointYou can use copilot -p for scripting, CI/CD, commit messages, and batch automation without an interactive session.

New requirements arrive: add task filtering by status and a /stats endpoint. Use plan mode to design the changes, then delegate them to Coding Agent so the work runs asynchronously and opens a pull request.

SecurityRuns on your machineIsolated cloud environment

8.2 Switch to Plan Mode

Start a new CLI session and press Shift+Tab to enter plan mode. This time, hand off the plan instead of executing locally.

Add two new features:

1. GET /tasks?status=todo — filter tasks by status (query parameter)
2. GET /tasks/stats — return { total, byStatus: { todo, inProgress, done }, lastCreated }

Both should:
- Follow existing code conventions
- Have tests with >80% coverage
- Update existing tests if needed
- Be documented in JSDoc comments

Plan the changes but don't execute yet.

Review the plan and request changes as needed. When satisfied, select Exit plan mode and I will prompt myself.

/delegate

Watch the agentOpen the repository's Agents tab for a live or past session. You can also open the PR and select View Session.

When complete, review the commits, changed-file diffs, PR explanation, and test coverage. You can assign Copilot as a reviewer.

9.1 Customization Mechanisms

Skills

Skills are portable capabilities defined in SKILL.md. A matching description automatically invokes a skill and adds its instructions, scripts, and resources.

ScopeLocation
Project skills.github/skills/<skill-name>/SKILL.md
User-wide skills~/.copilot/skills/<skill-name>/SKILL.md
/skills list          # See all loaded skills
/skills info <name>   # View a skill's details
/skills add           # Add a skill interactively
/skills remove <name> # Remove a skill
/skills reload        # Reload after changes

Custom Agents

Custom agents are specialized personas in Markdown files. Each can have its own model, tool restrictions, and domain expertise.

/agent                         # Browse and select agents
copilot --agent=<name>         # Launch with a named agent

Built-in agents include code-review, explore, general-purpose, research, and task.

Hooks

Hooks run shell commands at lifecycle points for validation, logging, security scanning, or workflow automation. JSON files are auto-loaded from .github/hooks/.

EventWhenCan block?
sessionStartNew or resumed sessionNo
preToolUseBefore each toolYes
postToolUseAfter each toolNo
agentStopMain agent finishesYes
subagentStopSubagent completesYes
  • Command hooks run shell scripts such as secret scans.
  • Prompt hooks submit text automatically at events such as sessionStart.

MCP Servers

MCP servers give Copilot external tools and data sources such as databases, APIs, and browser automation.

Exercise 10

Orchestration, Permission Controls, and Sandbox

Understand the permission model, safe autonomous operation, and parallel workflows.

10.1 Allow-All / YOLO Mode

--allow-all, also called --yolo, combines three permissions:

FlagAllows
--allow-all-toolsAny command without approval
--allow-all-pathsAny file path without verification
--allow-all-urlsAny URL without approval

Interactive equivalents are /allow-all and /yolo. Use them only while actively watching a trusted, throwaway environment or verified automation.

RisksWith these permissions Copilot can run destructive commands, read sensitive files such as .env or SSH keys, and fetch arbitrary URLs. Your development machine may contain sensitive data and access to important systems.

10.2 Granular Permission Controls

# Allow specific commands
copilot --allow-tool='shell(git:*)'
copilot --allow-tool='shell(npm test)'

# Allow writes to specific paths
copilot --allow-tool='write(src/*.js)'
copilot --allow-tool='write(README.md)'

# Allow specific MCP tools or URLs
copilot --allow-tool='github(create_issue)'
copilot --allow-tool='playwright'
copilot --allow-tool='url(github.com)'
copilot --allow-tool='url(https://*.github.com)'

# Combine allow and deny rules
copilot --allow-all-tools \
  --deny-tool='shell(rm)' \
  --deny-tool='shell(git push)' \
  --deny-tool='shell(git push --force)'

# Read-only profile
copilot --available-tools='view, grep, glob' -p "Analyze this codebase for security issues"

At scale, use a wrapper or alias, a preToolUse hook backed by policy logic, or tool profiles created with --available-tools.

10.3 Isolation Options

Permissions can be paired with isolation. Options include GitHub Copilot Coding Agent, Codespaces, and a separate development machine or VM. GitHub is working on additional options. Docker Sandboxes provide experimental microVM isolation, and Nvidia OpenShell explores a similar direction.

10.3.1 Docker Sandbox

A Docker Sandbox confines file access, shell commands, and network traffic. Docker Desktop 4.58 or later is required; the feature is experimental on macOS and Windows.

docker sandbox run copilot ~/task-manager-api

Authenticate inside the sandbox with /login. Pass Copilot options after --:

docker sandbox run my-sandbox -- --yolo

Sandboxes block private networks and localhost by default. Configure a denylist policy and inspect network activity:

docker sandbox network proxy my-sandbox \
  --policy deny \
  --allow-host "*.npmjs.org" \
  --allow-host github.com \
  --allow-host "*.githubusercontent.com"

docker sandbox network log

For more detail, see the Docker Sandbox network policies documentation. Sandboxing adds setup overhead, so compare it with simpler options such as delegating to Coding Agent.

10.4 Git Worktrees for Parallel CLI Sessions

Multiple CLI sessions can conflict when they write to one repository. Git worktrees provide separate working directories attached to the same repository and branch history.

Limitations include shared Git objects and index behavior, one branch per worktree, separate node_modules, and cleanup overhead. Removing a worktree does not remove its branch.

# From the main repository
git worktree add ../task-manager-feature-a -b feature-a
git worktree add ../task-manager-feature-b -b feature-b

# Terminal 1
cd ../task-manager-feature-a && copilot

# Terminal 2
cd ../task-manager-feature-b && copilot

# Inspect and clean up
git worktree list
git worktree remove ../task-manager-feature-a
git worktree remove ../task-manager-feature-b
git branch -l

Combine worktrees with /fleet when independent subagents need separate working areas.

CheckpointYou understand permissions from /allow-all to granular patterns, isolation options, Docker Sandboxes, and worktrees for parallel sessions.

npm install -g typescript-language-server

Create .github/lsp.json or ~/.copilot/lsp-config.json:

  "lspServers": {
    "typescript": {
      "command": "typescript-language-server",
      "args": ["--stdio"],
      "fileExtensions": { ".ts": "typescript", ".tsx": "typescript" }
    }
  }
}
