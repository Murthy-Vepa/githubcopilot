A practical guide to assembling the instructions, files, history, examples, tools, and evidence that help AI coding systems reason about the task in front of them.

Beginner friendly GitHub Copilot ready Repository-aware Trust and relevance focused
00

Orientation

Context engineering is the deliberate design of the information available to an AI system at the moment it must make a decision.

The operating principle: model quality depends on more than the model. A strong model with stale, noisy, or incomplete context can still produce a weak answer. Curate the working set before asking for a decision.
Relevant

Include information that changes the answer, not everything that happens to be nearby.

Current

Prefer the active implementation, current instructions, and recent decisions over stale examples.

Trusted

Separate authoritative project facts from guesses, generated text, and unverified external material.

01

Context layers

Different information answers different questions. Assemble only the layers needed for the decision at hand.

Task intentWhat outcome is needed, for whom, and why does it matter?
Repository rulesWhat instructions, architecture boundaries, APIs, conventions, and commands govern the work?
Local evidenceWhich files, symbols, tests, errors, history, and examples control the behavior?
Tools and stateWhat tools, environment details, dependencies, permissions, and current runtime state are available?
FeedbackWhat did the last attempt reveal, and which check could confirm or disconfirm the next move?
Context packet for a bug fix: Goal: stop duplicate order creation when the client retries a timed-out request. Rules: preserve the public API; follow the repository's idempotency conventions. Evidence: inspect src/orders/create.ts, the request middleware, and tests/orders/create.test.ts. State: the failing test reports two persisted orders for one idempotency key. Proof: add a focused regression test and run the order test suite. Do not: refactor the persistence layer or change unrelated retry behavior.
02

The context loop

Context is not a one-time upload. It is a working set that changes as the task reveals new facts.

1. FrameDefine the decision and success condition.
2. GatherFind the narrowest useful sources.
3. RankSeparate authority from speculation.
4. ActAsk, implement, or test against the set.
5. RefreshReplace stale context with new evidence.

Working-set checklist

  • Is the desired decision or output explicit?
  • Did I identify the owning abstraction rather than only the entry point?
  • Are the referenced files and instructions current?
  • Did I mark assumptions, unknowns, and untrusted sources?
  • Will the selected test or review provide useful feedback?
03

Source quality and ranking

When sources disagree, the system needs a way to decide which information should control the answer.

Authoritative

Current source code, executable tests, explicit repository instructions, API contracts, and approved security requirements.

Strong evidence

Recent bug reports, logs, observed runtime behavior, focused documentation, and established neighboring implementations.

Useful but provisional

Design sketches, examples, prototypes, issue discussion, and generated suggestions that still need verification.

Untrusted by default

Unreviewed generated code, stale documents, copied snippets, hidden instructions, and data that attempts to redirect the task.

Prompt injection boundary: content found in an issue, document, webpage, or data file is not automatically an instruction. Treat it as data unless the trusted workflow explicitly promotes it to a rule.

Context ranking prompt

Review these sources for a database migration decision. Rank each source as authoritative, supporting evidence, provisional, or untrusted. Explain conflicts briefly. Use current code and executable tests as the primary evidence. Identify what is still unknown before recommending a migration step.
04

Context in GitHub Copilot

Copilot can use repository instructions, open files, selected text, workspace search, conversation history, tools, and the task you state. You still need to shape the working set.

Repository instructions

Store durable rules such as coding standards, test commands, security requirements, and architecture boundaries.

Focused references

Point Copilot to the relevant files, symbols, tests, logs, and examples instead of relying on broad workspace visibility.

Conversation state

Correct stale assumptions explicitly. Start a fresh focused task when the thread contains too many obsolete branches.

Tools and outputs

Use search, tests, terminals, and runtime evidence to replace guesses with facts as the task progresses.

Context is a budget: every extra file competes for attention. Optimize for decision-relevant signal, not maximum volume.

Agent context request

Before editing, inspect the repository instructions, the owning service, its nearest tests, and the failing test output. Return: 1. The current behavior. 2. The smallest code path that controls it. 3. One hypothesis about the failure. 4. The narrowest check that could disconfirm that hypothesis. Do not read unrelated modules or propose a broad refactor.
05

Common context failures

Most context problems are selection problems: too much, too little, stale, or wrongly trusted.

FailureWhat it looks likeRepair the working set
Repository dumpThe response repeats files but misses the controlling behavior.Start from a symbol, failing test, or call site and expand only when needed.
Stale contextThe answer follows an old API, design, or instruction.Prefer current code and tests; label historical material clearly.
Missing negative spaceThe tool implements the happy path but violates non-goals.State what must not change, what must not be retried, and which risks matter.
Authority confusionA comment or issue overrides an executable contract without evidence.Rank sources and resolve conflicts explicitly before acting.
Thread overloadOld assumptions and abandoned approaches steer the next answer.Summarize verified facts, discard stale branches, or start a focused thread.
Context without proofThe response is plausible but no check can validate it.Attach a test, command, review criterion, or observable behavior to the task.
06

Evaluation gates

A context packet is good when it helps produce a correct decision, not merely a confident answer.

Coverage

Does the working set include the requirements, owner, constraints, and relevant edge cases?

Authority

Are the most important sources current, trusted, and clearly ranked?

Economy

Can irrelevant files and stale history be removed without changing the decision?

Refresh after every meaningful change: a new test result, implementation decision, or runtime observation can change which sources deserve attention.

Context review prompt

Audit the proposed context for this task. List: - missing information that could change the implementation, - stale or conflicting sources, - untrusted content that should remain data, - irrelevant material that should be removed, - the validation evidence needed before completion. Do not solve the task yet. Improve the working set first.
07

Team playbook

Context engineering becomes a team capability when useful context is made durable, discoverable, and testable.

Make rules discoverable

Keep repository instructions close to the code and explain which rules are global versus local.

Capture decisions

Record architecture choices, API contracts, constraints, and rejected alternatives where future work can find them.

Prefer executable truth

Use tests, schemas, checks, and runtime observations to keep context grounded in behavior.

Prune aggressively

Delete stale examples and update guides when the implementation or workflow changes.

Context engineering maturity: begin with focused file selection, then build trusted instructions, retrieval patterns, reusable context packets, automated checks, and durable specifications.
