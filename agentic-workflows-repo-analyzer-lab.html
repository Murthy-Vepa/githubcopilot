Customization lab · Agentic Workflows

Build a Repo Health Analyzer with gh-aw.

Create a GitHub Agentic Workflow that examines repository health and publishes a comprehensive, evidence-based report as a GitHub issue.

~45 minutesIntermediateGitHub ActionsSafe Outputs
Objective

What you will build

By the end of this lab, you will have a workflow that runs weekly and on demand, gathers repository data through the GitHub MCP server, generates trend charts, and creates one labeled health report issue.

AI agent readiness

A scorecard for README quality, architecture documentation, repository structure, tests, CI, custom instructions, and contribution guidance.

CI/CD health

Workflow inventory, pass rates, average duration, failure frequency, and likely flaky jobs from recent GitHub Actions runs.

DORA and SPACE proxies

Approximate deployment frequency, lead time, change failure rate, MTTR, activity, performance, collaboration, and efficiency from GitHub data.

Review and PR flow

Time to first review, review-to-merge, reviewer throughput, review backlog, stale pull requests, and lead time by PR size.

Copilot adoption

Copilot-assisted commits, pull requests, reviews, adoption rate, and four-week trends based on repository evidence.

Actionable recommendations

A week-over-week summary and five to seven prioritized recommendations with an action, reason, and expected impact.

What are GitHub Agentic Workflows? gh-aw lets you write GitHub Actions workflows in Markdown with natural-language instructions. The gh aw CLI compiles the source into a secure .lock.yml workflow that runs an AI agent with scoped permissions, tools, and guardrails.

Prerequisites

  • GitHub CLI installed and authenticated
  • A GitHub repository with some issue, PR, commit, and Actions history
  • GitHub Copilot access for workflow requests
  • Linux, macOS, or Windows with WSL

Important safety boundary

The agent remains read-only. It does not receive issues: write or other direct write permissions. Report creation is declared as a validated Safe Output with a limit.

Exercise 1 · Install

Install and verify gh-aw

The GitHub CLI extension provides the compiler and runner for Markdown-authored agentic workflows.

1.1 Verify GitHub CLI

gh auth status

You should see the authenticated account and the host it can access. Run gh auth login if the CLI is not authenticated.

1.2 Install the extension

# Official installer for Linux, macOS, or WSL curl -sL https://raw.githubusercontent.com/github/gh-aw/main/install-gh-aw.sh | bash # If gh-aw is already installed, upgrade the extension gh extension upgrade aw

1.3 Verify installation

gh aw version gh aw --help
Checkpoint: you have an authenticated GitHub CLI and gh aw version returns a version number.
Exercise 2 · Understand

Understand the two-part workflow

Every agentic workflow has a Markdown source with two responsibilities: machine configuration in YAML frontmatter and agent guidance in the Markdown body.

PartContainsWhen changes take effect
YAML frontmatterTriggers, permissions, environment, tools, network, Safe Outputs, setup stepsRecompile when changed
Markdown bodyMission, data collection, analysis criteria, output structure, evidence rulesLoaded at runtime; body edits do not require recompilation
Compiled lock fileGenerated GitHub Actions workflow with runner infrastructure and guardrailsCreated or refreshed by gh aw compile
.github/workflows/repo-health-analyzer.md ├── YAML frontmatter between --- markers │ ├── triggers and timeout │ ├── read-only permissions │ ├── tools and network allowlist │ ├── Safe Outputs │ └── setup steps └── Markdown body ├── repository health mission ├── data collection instructions ├── eight analysis sections ├── chart generation rules └── report issue format
Never edit the lock file. Edit the .md source and recompile. Direct changes to .lock.yml will be overwritten and are difficult to review as intent.

2.1 Security model

# Correct: the agent reads; Safe Outputs perform bounded writes permissions: contents: read issues: read pull-requests: read actions: read safe-outputs: create-issue: max: 3 # Wrong: this bypasses the Safe Outputs safety boundary permissions: issues: write
Checkpoint: explain why the workflow uses read-only permissions and why report creation belongs under safe-outputs.
Exercise 3 · Configure

Write the workflow frontmatter

Create .github/workflows/repo-health-analyzer.md. Add the frontmatter in small pieces so each permission, tool, and output has a reason.

3.1 Description and triggers

--- description: | Weekly repository health analyzer that assesses AI-agent readiness, CI/CD health, DORA and SPACE metrics, review efficiency, PR lead times, and GitHub Copilot adoption. Produces a comprehensive report as a GitHub issue with trend charts and actionable recommendations. on: schedule: - cron: '0 6 * * 0' # Every Sunday at 06:00 UTC workflow_dispatch: timeout-minutes: 30
  • The weekly schedule provides a repeatable baseline; adjust the cron hour to your timezone (for example, 0 12 * * 0 for 7 AM ET / 4 AM PT during daylight saving time).
  • workflow_dispatch enables manual development runs.
  • Thirty minutes gives the agent time to collect data, create charts, and publish the report.

3.2 Permissions and target repository

permissions: contents: read issues: read pull-requests: read actions: read env: TARGET_REPOSITORY: ${{ vars.TARGET_REPOSITORY || github.repository }}
Analyzing a different repo: setting the TARGET_REPOSITORY repository variable under Settings → Variables points the analyzer at any repository you have access to. The built-in Actions token only carries permissions for the current repository, so cross-repository analysis of a private target needs a broader credential such as a PAT.

3.3 Network and tools

network: allowed: - defaults - python - node tools: edit: bash: - '*' github: lockdown: false min-integrity: none toolsets: [default] allowed-repos: all
ConfigurationPurpose
editLets the agent create temporary Python scripts for chart generation.
bashRuns the chart scripts and verifies generated files.
githubReads repository metadata, issues, pull requests, commits, and workflow runs through the GitHub MCP server.
networkAllows Python and Node package access needed by the setup steps; narrow additional hosts when possible.

3.4 Safe Outputs and setup

safe-outputs: mentions: false allowed-github-references: [] upload-asset: create-issue: title-prefix: '[Repo Health] ' labels: [report, repo-health, weekly] close-older-issues: true steps: - name: Setup Python environment run: | mkdir -p /tmp/charts /tmp/data pip install --user --quiet numpy pandas matplotlib seaborn scipy python3 -c "import pandas, matplotlib, seaborn; print('Python environment ready')" ---
  • upload-asset makes chart images available to the report.
  • create-issue limits and labels the final report output.
  • mentions: false prevents accidental notifications.
  • The closing --- separates configuration from the agent instructions.
Checkpoint: save a complete frontmatter block with a schedule, manual trigger, read-only permissions, tools, network access, Safe Outputs, and Python setup.
Exercise 4 · Instruct

Write the repository analysis instructions

The Markdown body tells the agent how to collect evidence, calculate metrics, handle sparse data, generate charts, and structure the final issue.

4.1 Mission and data collection

# Repository Health Analyzer Analyze repository `${{ env.TARGET_REPOSITORY }}` and produce a comprehensive health report as a GitHub issue. Help maintainers understand repository health, AI-agent readiness, and improvement trends. ## Data Collection Use GitHub tools to gather data for the past 30 days: 1. Repository metadata: README, file tree at the top two levels, key config files. 2. Pull requests: opened, merged, closed, authors, reviewers, timestamps, and commits. 3. Issues: opened and closed issues, labels, timestamps, and comments. 4. Commits: recent default-branch commits, authors, and co-author trailers. 5. Workflow runs: CI/CD results, duration, jobs, and failure details. 6. Releases and tags: recent releases or deployment-like events. Collect enough data to compute four weekly trend points.

4.2 AI Agent Readiness

Assess the repository against this scorecard. For each criterion use Present & Good, Partial, or Missing, with a brief finding and evidence.

#CriterionWhat to check
1Clear READMEPurpose, architecture summary, build steps, test steps, and repository layout.
2Architecture documentation/docs/architecture.md, components documentation, diagrams, or similar.
3Predictable structureClear /src, /tests, /docs, and /scripts boundaries.
4In-repository documentationBuild, test, contribution, and operational instructions in Markdown.
5Architecture decisionsAn ADR directory or another visible decision-record practice.
6Scriptable build and testMake, npm scripts, task runner, or similarly simple commands.
7Test suiteTest directory, configured framework, and evidence of meaningful coverage.
8Automated CIActions workflows for tests, linting, security, or other checks on pull requests.
9Linting and formattingConfiguration such as ESLint, Prettier, Ruff, EditorConfig, or pyproject tools.
10Copilot auto-reviewReview configuration or evidence of Copilot review activity.
11Custom instructions.github/copilot-instructions.md or equivalent project guidance.
12CONTRIBUTING.mdMeaningful coding standards, branch strategy, and pull request expectations.

Compute a grade: A for 10 or more criteria met, B for 7–9, C for 4–6, and D for 0–3. Follow with three to five specific recommendations.

4.3 CI/CD health and DORA

## CI/CD Health List workflows, trigger types, runs, pass rate, average and median duration, failure frequency, and jobs that alternate between pass and fail. Present a table with Workflow, Runs, Pass Rate, Average Duration, and Trend. ## DORA Metrics Approximate from the last 30 days: - Deployment frequency: releases, tags, deployments, or merges as a proxy. - Lead time for changes: first commit on a branch to PR merge. - Change failure rate: reverted PRs, hotfixes, or bug/regression issues after merge. - MTTR: time from bug, incident, or regression issue opened to closed. Classify each as Elite, High, Medium, or Low and explain proxy limitations.

4.4 SPACE and review efficiency

## SPACE Metrics Use proxy indicators for Satisfaction and well-being, Performance, Activity, Communication and collaboration, and Efficiency. Include contributors, new contributors, CI pass rate, commits, PRs, issues, review comments, reviewer participation, PR cycle time, review turnaround, and review load. Present a four-week activity trend table. ## Review Efficiency Calculate median time to first review, first review to merge, total review cycle, reviews completed per reviewer, review backlog, and stale PRs over seven days. Highlight bottlenecks and state when data is incomplete.

4.5 PR lead times and Copilot adoption

## PR Lead Times Analyze Open to First Review, First Review to Merge, and Open to Merge. Group PRs as Small (<50 lines), Medium (50–250), and Large (>250). Create /tmp/charts/pr_lead_times.png as a 300 DPI 12x7 horizontal grouped bar chart. ## GitHub Copilot Adoption Search commit messages and PR descriptions for Copilot co-author trailers, Copilot-authored PRs, and Copilot review activity. Report assisted commits, assisted PRs, reviews, adoption rate, and week-over-week trend. Create /tmp/charts/copilot_adoption.png as a 300 DPI 12x7 trend chart.

4.6 Trends, charts, and recommendations

## Activity Trends and Recommendations Create /tmp/charts/activity_trends.png with weekly PRs opened, PRs merged, issues opened, issues closed, and total commits for four weeks. Use matplotlib.use('Agg'), pandas, seaborn whitegrid, tight_layout, and 300 DPI. Handle sparse data with bars and zero data with a placeholder message. Create a week-over-week table for PRs, issues, commits, average PR lead time, CI pass rate, and Copilot adoption using ↑, ↓, or →. Then provide 5–7 prioritized recommendations. Each must include What, Why, and Impact (High, Medium, or Low).
Evidence rule: never invent a metric. If a value cannot be computed, explain why and mark the gap. A smaller report with honest limitations is more useful than a complete-looking report built on guesses.

4.7 Report and metadata

## 📊 Repository Health Report **Repository**: {repo_name} **Report Date**: {date} **Analysis Period**: Past 30 days ### 🤖 AI Agent Readiness {scorecard, grade, and recommendations} --- ### 🔧 CI/CD Health {workflow table and highlights} --- ### 📈 DORA Metrics {metric, value, classification, and trend} --- ### 🧭 SPACE Metrics {dimension tables and four-week activity} --- ### 👀 Review Efficiency {review metrics and bottlenecks} --- ### ⏱️ PR Lead Times {lead-time table and chart} ![PR Lead Times]({chart_url}) --- ### 🤝 GitHub Copilot Adoption {adoption metrics and chart} ![Copilot Adoption]({chart_url}) --- ### 📉 Activity Trends {activity chart and week-over-week table} ![Activity Trends]({chart_url}) --- ### 💡 Top Recommendations {prioritized recommendations}
📋 Report Metadata Workflow, run URL, analysis period, and data collection timestamp.
Checkpoint: the Markdown body contains the mission, data collection, all eight report sections, chart requirements, output format, evidence rules, and recommendations.
Exercise 5 · Validate

Compile and inspect the workflow

Compilation produces the Actions workflow that GitHub will execute. Treat the generated artifact as a security and configuration review surface.

5.1 Compile the workflow

gh aw compile repo-health-analyzer
✓ .github/workflows/repo-health-analyzer.md (58.3 KB) ✓ Compiled 1 workflow(s): 0 error(s), 0 warning(s)

The command creates .github/workflows/repo-health-analyzer.lock.yml, the compiled GitHub Actions workflow that GitHub Actions actually runs.

5.2 Check generated-file handling

Get-Content .gitattributes # Expected pattern: .github/workflows/*.lock.yml linguist-generated=true merge=ours

On Linux or macOS, use cat .gitattributes. This marks lock files as generated and reduces merge noise.

5.3 Inspect without editing

Get-Content .github/workflows/repo-health-analyzer.lock.yml -TotalCount 80 # Linux/macOS: # sed -n '1,80p' .github/workflows/repo-health-analyzer.lock.yml
  • Confirm the trigger and timeout are present.
  • Confirm the job uses read-only permissions.
  • Confirm Safe Outputs are configured.
  • Confirm setup steps create chart directories and install dependencies.
  • Confirm the generated workflow is committed alongside the Markdown source.
Checkpoint: you have the source Markdown, compiled lock file, and appropriate .gitattributes handling. Do not modify the lock file directly.
Exercise 6 · Run

Deploy, trigger, and review the report

Use a branch and pull request when branch protection applies. Keep credentials out of the workflow source and logs.

6.1 Commit and push

git add .gitattributes .github/workflows/repo-health-analyzer.md .github/workflows/repo-health-analyzer.lock.yml git commit -m "Add repository health agentic workflow" git push
Protected branches: create a feature branch and pull request instead of pushing directly to the default branch. Review permissions, network access, tools, Safe Outputs, and the compiled lock file.

6.2 Configure Copilot authentication

Agentic workflows currently need a personal access token to authorize Copilot requests (expected to be simplified with org-level support so the built-in Actions token can be used instead).

  1. Open Create a fine-grained PAT, which pre-fills the name, description, and Copilot Requests permission.
  2. Set Resource owner to your user account, not the organization — the Copilot seat is owned by you. Repository permissions do not matter since none are granted.
  3. Set an appropriate expiration, generate the token, and copy the value.
  4. Add it as the repository secret COPILOT_GITHUB_TOKEN under Settings → Secrets and variables → Actions → New repository secret.
  5. Never paste the token into this lab, workflow Markdown, an issue, a log, or chat.
Credential safety: token setup is account-specific and may change. Follow the current gh-aw authentication reference and your organization's policy.

6.3 Trigger and monitor

# From the Actions tab: Run workflow → select branch → Run workflow # Or trigger from the CLI: gh workflow run repo-health-analyzer # Watch the latest run: gh run watch

A run typically takes 5 to 15 minutes depending on repository size and activity. Inspect the Actions log if a tool, package installation, chart, or Safe Output step fails.

6.4 Review the report issue

gh issue list --label repo-health

Open the generated issue and review the AI readiness scorecard, CI/CD table, DORA and SPACE approximations, review metrics, charts, Copilot adoption, trends, recommendations, and metadata. Check that every conclusion has evidence or a limitation note.

Checkpoint: the workflow runs successfully and creates one labeled issue with the repository health report and chart assets.
Exercise 7 · Extend

Customize the analyzer

Once the baseline works, change one dimension at a time and observe how the report changes.

7.1 Analyze a different repository

Add a repository variable named TARGET_REPOSITORY under Settings → Secrets and variables → Actions → Variables, with a value such as facebook/react, then run the workflow again. The built-in Actions token can read a public target; private repositories need an approved credential with access.

# Or set it via CLI: gh variable set TARGET_REPOSITORY --body "octocat/hello-world" gh workflow run repo-health-analyzer

This repository is small, so its report will not be very interesting — try the workflow against an active repository to see meaningful metrics and a baseline for improvement.

7.2 Edit the body without recompiling

The Markdown body is loaded at runtime. On GitHub, edit the body of .github/workflows/repo-health-analyzer.md to add a ninth section such as Security Posture:

## Section 9: Security Posture Check for Dependabot alerts, CodeQL, secret scanning, branch protection, and required pull request reviews. Report enabled, partial, or missing controls with links to repository settings or configuration files.

Body-only edits do not require compilation. Frontmatter changes do require compilation, and a pull request is still recommended for reviewability.

Wrap-up

Make repository health a repeatable conversation.

You built an agentic workflow that turns repository evidence into a recurring report while keeping the agent read-only and side effects bounded.

What you built

  • A weekly and on-demand GitHub Agentic Workflow
  • A 12-point AI Agent Readiness scorecard
  • DORA and SPACE metric approximations
  • Python-generated trend charts
  • A labeled GitHub issue with recommendations

Key takeaways

  • Markdown expresses intent; the lock file is the executable artifact.
  • Read-only agents plus Safe Outputs keep writes constrained.
  • Runtime body edits support quick iteration.
  • Evidence and limitations matter more than a complete-looking score.
  • Workflows can be composed from reusable tools and patterns.

Final readiness checklist

  • gh-aw is installed and authenticated
  • Manual trigger works before scheduling
  • Source and lock file are both committed
  • Permissions are read-only for the agent
  • Network access is explicit and minimal
  • Safe Outputs have limits and labels
  • All eight report sections have evidence rules
  • Charts handle sparse and zero data
  • Credentials are stored only as repository secrets
  • Report recommendations include impact and rationale
