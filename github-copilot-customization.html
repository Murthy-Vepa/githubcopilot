Module 02 / Customization

Customization

Shape the context, behavior, tools, and boundaries that make Copilot useful for your team.

ContextBehaviorToolsGovernance
01 / Introduction

Customization turns a general assistant into a team-aware collaborator.

The goal is simple: make the right context repeatable, useful behavior discoverable, and permissions explicit.

Capture once

Turn recurring conventions into guidance the whole team can reuse.

Behave consistently

Give Copilot stable instructions, skills, and roles for common work.

Extend safely

Connect tools only when access is controlled, reviewable, and worth governing.

Customization outcome:the team can explain why Copilot behaves a certain way, where that behavior is defined, and how to change it.

02 / Concepts

Every customization answers four design questions.

01

Intent

What outcome should improve?

02

Guidance

What rules and knowledge shape the answer?

03

Capability

What skill, agent, or tool can help?

04

Control

What boundary makes the workflow trustworthy?

Design principle:add the smallest customization that reliably improves the outcome. More configuration is not the same as better context.

03 / Architecture

Put guidance where it belongs.

PersonalPreferences and working notes for one person's workflow.
RepositoryInstructions and conventions that travel with the codebase.
WorkflowSkills, agents, hooks, and tools for a repeatable team activity.
OrganizationPolicies and standards that establish the quality boundary.
Placement test:if guidance is useful in one repository, keep it local; if it defines a shared policy, make the broader ownership visible.

04 / Agents

An agent is a role with a mission and a reviewable method.

Role

Who is this agent for, and what expertise does it bring?

Mission

What outcome, boundaries, artifacts, and success conditions are expected?

Method

What steps, tools, approvals, and checks must it follow?

Agent design rule:be opinionated about the workflow, transparent about decisions, and bounded about permissions.

05 / Skills

Skills turn expertise into a reusable move.

Package the expertise

  • One focused procedure
  • Clear inputs and outputs
  • Examples and failure conditions

Reach for a skill when

  • The task repeats
  • The process is domain-specific
  • The result needs a consistent format
Keep skills composable:one skill should make one kind of work easier to invoke, understand, and verify rather than becoming a hidden handbook for everything.

06 / Instructions

Instructions make the local rules visible.

applyTo: "**/*.ts"
purpose: "Keep service boundaries explicit."
rules:
  - Prefer existing repository helpers.
  - Add tests for changed behavior.
  - Do not expose secrets in logs.
# Guidance should be specific enough to act on.
Instruction test:a reviewer can tell whether the rule was followed and can find the source when it was not.

07 / Prompts

Prompts turn intent into a useful next move.

Frame

State the role, goal, audience, constraints, and context.

Sequence

Ask for the plan, change, review, or explanation that reduces uncertainty.

Evaluate

Request tests, assumptions, alternatives, and limitations.

Prompt rule:the best prompt is not the longest one. It makes the desired decision and evidence easy to produce.

08 / Hooks

Hooks turn workflow boundaries into checks.

Before

Check inputs, permissions, context, and the proposed plan.

During

Observe tool use, capture state, or enforce policy at a transition.

After

Run checks, record evidence, and request review before completion.

Hook test:the check protects a real boundary, and failure tells the person what to do next.

09 / Agent observability

Observability turns “it failed” into a fixable question.

Trace

See the prompt, context, tools, decisions, and returned result.

Diagnose

Separate missing context from unclear guidance, tool failure, or permission issues.

Improve

Turn recurring failures into better guidance, tests, hooks, or tool contracts.

Debug logs are evidence, not a substitute for judgment:protect sensitive data, control access to session records, and use the trace to improve a reproducible workflow.

10 / MCP servers

MCP makes tool access discoverable, consistent, and governable.

ClientChooses when a tool is relevant and starts the interaction.
ServerPublishes tools, resources, and prompts through one protocol boundary.
SystemPerforms the approved operation against the target system.
ApprovalApplies identity, permissions, confirmation, and audit expectations.
MCP is an integration boundary:treat every exposed tool as an API with a clear contract, least privilege, safe failure behavior, and an owner.

11 / Plugins

Plugins package a workflow so teams can extend Copilot consistently.

Package

Bundle the capabilities that support one recognizable workflow.

Compose

Reuse the integration instead of rebuilding it for every project.

Govern

Make ownership, permissions, dependencies, and change review visible.

A plugin is a product boundary:give it a clear audience, a narrow purpose, documented setup, safe defaults, and a versioning or retirement plan.

13 / Agentic Workflows

Agentic Workflows bring bounded AI reasoning into GitHub Actions.

Write the intent in Markdown, compile the workflow, and let an agent interpret repository context inside explicit permissions and Safe Outputs.

01

Author

Define the goal, evidence, stop conditions, and output.

02

Compile

Run gh aw compile --strict and review the lock file.

03

Interpret

Evaluate repository state with approved context and tools.

04

Release safely

Use bounded Safe Outputs instead of unrestricted writes.

Automation rule:let the agent interpret and propose; let permissions, allowlists, Safe Outputs, and human review control what becomes real.

14 / Design and governance

Good customization is discoverable, testable, and governed.

Discoverable

Clear name, owner, scope, and documentation.

Testable

Representative tasks prove the guidance changes behavior.

Governed

Permissions, data handling, review, and rollback are explicit.

Quality bar:customization should reduce uncertainty for the team, not move complexity into a place nobody can see.
