Lab

Prompt Engineering

Turn an underspecified development request into a reliable Copilot workflow by adding structure, context, examples, techniques, and evaluation.

⏱ ~60 minutes🎯 Beginner to intermediate💻 GitHub Copilot in VS Code🧪 One running scenario
How to use this labKeep the same scenario throughout: you are adding a CSV customer-import endpoint to a web application. Run each prompt in Copilot Chat, save the useful output, and compare it with the previous version. The goal is not a magic phrase; it is a repeatable design and review process.

Objective

Prompt engineering is the practice of designing and optimizing instructions so an LLM can produce accurate, relevant, and useful results. In this lab you will move from a one-line request to a prompt that is explicit about role, task, context, constraints, examples, output format, and verification.

By the end, you will have a reusable prompt pattern for a development task and a small evaluation rubric for deciding whether the result is good enough.

Prerequisites

  • VS Code with GitHub Copilot Chat enabled.
  • Any small code repository you can safely edit, or a scratch folder with a sample API.
  • A basic understanding of your repository's language, test runner, and API conventions.
Use representative, non-sensitive dataDo not paste production customer records, credentials, access tokens, private keys, or regulated data into a prompt. Use a fabricated sample such as customer_id,name,email.

Part 1

Prompt Anatomy

The source guide describes a well-structured prompt as a sequence of system message, task, context/input, constraints, and output format. Start by observing what changes when you add those components.

1.1 Establish a Baseline

Open Copilot Chat and submit this intentionally underspecified request:

Build a customer CSV import endpoint.

Record the response. Look for assumptions about the framework, file location, CSV shape, validation, duplicates, error handling, and tests.

CheckpointWrite down three assumptions Copilot made and two acceptance criteria it could not infer. Those gaps become the inputs for your next prompt.

1.2 Add Structure

Run a second prompt that makes the task and desired output explicit:

Role: You are a senior backend developer working in this repository.

Task: Design a customer CSV import endpoint. First inspect the existing
routing, validation, persistence, and test patterns. Do not edit files yet.

Output format:
1. Files and symbols you would reuse
2. Proposed request and response contract
3. Validation and error cases
4. Test cases
5. Open questions and assumptions

Compare the response with the baseline. The prompt is still incomplete, but its structure makes uncertainty visible before code is generated.

Prompt design principleUse clear labels such as ROLE, TASK, CONTEXT, CONSTRAINTS, and OUTPUT FORMAT. Labels separate instructions from input and make prompts easier to reuse.
Part 2

Context and Instructions

Context turns a generic request into a repository-specific request. Add only relevant facts: domain, audience, current situation, previous attempts, and constraints.

2.1 Add Relevant Context

Adapt the prompt below to your repository. Replace the bracketed values with facts you can verify by reading the code.

ROLE:
You are a senior backend developer familiar with [language/framework].

TASK:
Design the customer CSV import endpoint. Inspect the repository first;
propose a plan before making edits.

CONTEXT:
- API entry point: [existing route/controller pattern]
- Validation: [existing library or convention]
- Persistence: [repository/service pattern]
- Tests: [test framework and command]
- Audience: maintainers who prefer small, reviewable changes

INPUT:
CSV columns are customer_id, name, email. The file can contain a header.

OUTPUT FORMAT:
Return a short implementation plan, impacted files, and tests.

Ask Copilot to cite the files it used for each repository convention. If it cannot find a convention, record that as an open question rather than allowing it to invent one.

2.2 Make Success Measurable

Extend the prompt with SMART-style instructions: specific, measurable, actionable, realistic, and bounded.

CONSTRAINTS:
- Preserve existing API response and error conventions.
- Reject missing required columns and malformed email addresses.
- Define duplicate behavior explicitly; do not silently overwrite records.
- Return a row-level error summary without exposing sensitive input values.
- Add unit tests for valid rows, malformed rows, duplicates, empty files,
  headers-only files, and mixed valid/invalid rows.
- Keep the change limited to the import feature; do not refactor unrelated code.
- At the end, list any requirement that remains ambiguous.
Why constraints helpConstraints reduce unwanted variation and make an output reviewable. They should describe boundaries and acceptance criteria, not merely ask the model to “do a good job.”
Part 3

Examples and Techniques

Examples demonstrate patterns more precisely than prose. The source guide distinguishes zero-shot prompting, where no examples are supplied, from few-shot prompting, where representative input/output pairs guide the model.

3.1 Use Few-Shot Examples

Add these fabricated examples to your structured prompt. Keep examples small and choose cases that expose the behavior you care about.

EXAMPLES:
Input row: 42,Ada Lovelace,ada@example.com
Result: accepted; normalized email to ada@example.com

Input row: 43,Grace Hopper,not-an-email
Result: rejected; code EMAIL_INVALID; report row number and column

Input row: 42,Ada Lovelace,ada@example.com
Result: rejected; code CUSTOMER_DUPLICATE; do not overwrite existing data

Ask Copilot to propose the response schema for row-level errors. Then ask it to explain which part of each example influenced the proposal.

Example quality beats quantityUse a few diverse, accurate examples. Include an edge case when the edge case is part of the contract. Do not include real customer data merely to make a prompt look realistic.

3.2 Choose a Technique

Choose the least complex technique that can reliably solve the task.

TechniqueUse it whenTry it here
Zero-shotThe task is clear and follows an established pattern.Ask for a short explanation of an existing endpoint.
Few-shotYou need consistent classification, formatting, or edge-case behavior.Classify CSV rows as accepted or rejected with error codes.
Prompt chainingA single prompt mixes discovery, design, implementation, and verification.Separate repository analysis, implementation, and test review.
Role/personaA perspective or audience changes the quality criteria.Ask a security reviewer to inspect import validation and data exposure.

Run the same task with zero-shot and few-shot prompts. Compare consistency across three fabricated rows. Record whether the more complex prompt produced enough benefit to justify its maintenance cost.

Part 4

Prompt Chaining

Prompt chaining decomposes a complex workflow into focused steps. Each step produces a bounded artifact that becomes input to the next step.

4.1 Split the Workflow

flowchart TD A["1. Inspect repository"] --> B["Conventions + open questions"] B --> C["2. Design contract"] C --> D["Contract + acceptance criteria"] D --> E["3. Implement small change"] E --> F["Diff + tests"] F --> G["4. Review and refine"] style A fill:#ccfbf1,stroke:#0f766e style C fill:#dbeafe,stroke:#2563eb style E fill:#fef3c7,stroke:#d97706 style G fill:#dcfce7,stroke:#16a34a

A chain keeps each prompt focused and makes handoff artifacts inspectable.

Run these prompts as separate turns. Do not allow the implementation step to skip the discovery artifact.

Step 1 - Discovery:
Inspect the repository's existing API, validation, persistence, and test patterns.
Return only verified conventions, candidate files, and open questions.
Do not edit files.

Step 2 - Contract:
Using the discovery notes below, propose the import request, response, error
codes, duplicate policy, and acceptance criteria. Flag contradictions.

Step 3 - Implementation:
Using the approved contract below, implement the smallest change that matches
existing conventions. Add focused tests. Do not refactor unrelated code.

Step 4 - Verification:
Review the diff and run the relevant tests. Report failures, missing edge cases,
security concerns, and whether each acceptance criterion is satisfied.

4.2 Handle Handoffs

A chain is only useful when its handoffs are explicit. After each step, check that the next prompt receives the right artifact and that uncertainty is preserved.

  • Use a named section for the handoff, such as DISCOVERY NOTES or APPROVED CONTRACT.
  • Ask the model to identify missing or contradictory inputs before continuing.
  • Keep intermediate outputs concise enough to inspect and reuse.
  • Stop the chain when a requirement needs a human decision.
Do not turn a chain into a blind pipelineEach handoff is a checkpoint. Review the plan and contract before asking Copilot to edit files.
Part 5

Evaluate and Optimize

Prompt engineering is iterative. Evaluate outputs against observable dimensions rather than relying on whether the answer sounds convincing.

5.1 Build a Rubric

Score the final implementation or plan from 0 to 2 for each dimension. A score of 2 means the criterion is fully met, 1 means partial, and 0 means missing or incorrect.

DimensionQuestionScore
RelevanceDoes the answer fit this repository and scenario?0 / 1 / 2
CorrectnessDoes it preserve verified conventions and handle valid inputs?0 / 1 / 2
CompletenessDoes it cover errors, duplicates, tests, and acceptance criteria?0 / 1 / 2
ConsistencyDoes the same prompt behave predictably across sample rows?0 / 1 / 2
SafetyDoes it avoid secrets, unnecessary personal data, and unsafe exposure?0 / 1 / 2
MaintainabilityIs the prompt clear, bounded, and reusable by another developer?0 / 1 / 2

Set a threshold before you optimize. For example, require at least 10/12 overall and no zero in correctness or safety.

5.2 Run an Iteration Loop

Use the rubric to make one targeted revision at a time. Avoid adding length without evidence that it addresses a failed dimension.

OPTIMIZATION REQUEST:
Here is the current prompt and its score: [paste both].
The weakest dimension is [dimension] because [evidence].
Suggest the smallest prompt change that should improve that dimension.
Preserve all requirements that already score 2.
Return:
1. Revised prompt
2. What changed
3. Why it should help
4. A test case that could disconfirm the improvement
Final checkpointRun the revised prompt on a happy path, an edge case, and a deliberately ambiguous input. Keep a short log of prompt version, model, input, score, and observed failure. That log is more valuable than a single impressive response.

Safety and Privacy Guardrails

  • Use synthetic or minimized data; never paste credentials, tokens, private keys, or unnecessary personal information.
  • Ask Copilot to flag uncertainty and identify assumptions instead of filling gaps silently.
  • Review generated code, especially validation, authorization, logging, data handling, and external calls.
  • Do not use a prompt as a substitute for tests, security review, human approval, or domain expertise.
  • Keep prompts and examples free of secrets because reusable prompt files may be shared with the repository.

Recap

You practiced the core progression from the Prompt Engineering guide:

  1. Start with user intent and observe a baseline.
  2. Make the task explicit with role, context, instructions, constraints, and output format.
  3. Use relevant examples to demonstrate formats and edge cases.
  4. Choose zero-shot, few-shot, role-based, or chained prompting based on the task.
  5. Evaluate outputs with a rubric and iterate against evidence.
TakeawayThe best prompt is not the longest prompt. It is the smallest clear specification that gives the model enough context to produce a verifiable result.
