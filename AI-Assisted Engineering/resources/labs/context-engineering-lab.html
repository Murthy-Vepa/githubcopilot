Lab

Context Engineering

Design, measure, and optimize the information you feed to AI models so every token produces more useful work.

~2 hoursIntermediateGitHub Copilot CLINode.js 22+
How to use this labUse a scratch repository or a non-sensitive project. Keep a short log of the context size, model, prompt, tool output, and observed result after each experiment. Context engineering is an evidence loop, not a contest to fit the most words into a window.

Objective

Every token an AI coding agent reads or writes has a cost. Context engineering is the practice of designing, measuring, and optimizing the information supplied to an AI model so signal stays high and noise stays low.

By the end of this lab, you will be able to:

  • Explain the difference between prompt engineering and context engineering.
  • Measure token usage in real time with Copilot CLI.
  • Reduce output tokens with high-value custom instructions.
  • Choose the right model for each task and manage stale sessions.
  • Filter tool output and write information-dense prompts.

Prerequisites

  • An active GitHub Copilot subscription and Copilot CLI installation.
  • Basic familiarity with Copilot CLI, or completion of a Copilot CLI introductory lab.
  • Node.js 22+ and a scratch repository or non-sensitive project.
Use representative, non-sensitive dataNever place credentials, access tokens, private keys, customer records, or regulated data in prompts, examples, instruction files, or tool output.

Background: From Prompt Engineering to Context Engineering

A prompt is only one part of what a model receives. The context window also includes system prompts, custom instructions, conversation history, tools, tool results, referenced files, and model reasoning.

Context componentExamplesWho controls it
System and instructionsPlatform behavior, .github/copilot-instructions.mdCopilot and you
Conversation and filesMessages, @ mentions, explored sourceAccumulates or is selected
Tools and resultsMCP servers, CLI output, shell commandsYou, indirectly
ReasoningHidden thinking tokens on reasoning modelsModel configuration
Key insightYou control most of what enters the context window. Engineer it deliberately: maximize signal, minimize noise, and measure the result.

Why Cost and Caching Matter

As Copilot transitions from premium requests to usage-based billing, token use has a direct impact on cost. Output tokens typically cost three to five times more than input tokens, making unnecessary explanation an especially expensive form of waste.

Cost = (Uncached input * input price)
  + (Cached input * input price * 0.1)
  + (Output tokens * output price)

Prompt caching is automatic on most platforms. Stable prefixes such as the system prompt, project instructions, tool definitions, and early conversation history can be served at roughly 10% of normal input price during an active session. The initial cache write costs more, but repeated hits within the cache lifetime are much cheaper.

Cache deliberatelyKeep stable instructions near the start of the session, work in focused bursts, compact before a long break, and start a fresh session when the task changes. This preserves a small cache-friendly prefix instead of repeatedly processing stale history.

Use prices as ratiosModel rates change frequently. The durable lesson is that output is more expensive than input, cache hits are deeply discounted, and stronger models cost more.

A useful context loop keeps only the information that changes the decision or result.

  • A baseline context measurement and cost comparison

Exercise 1

See What's in the Window

Start by observing what the model receives before optimizing it. The system prompt, tool definitions, project instructions, conversation history, and your current request all compete for the same window.

1.1 Establish a Baseline

Open a Copilot CLI session and inspect the initial context:

copilot
/context

Record the system and tool overhead, available space, and any loaded instructions. In VS Code, also note the context usage indicator after your first chat turn.

CheckpointWrite down the fixed overhead and identify one source you did not expect to be present. That is your first optimization candidate.

1.2 Watch Context Grow

Ask a short question, then inspect the window again:

What is context engineering, and how does it differ from prompt engineering?
/context

Compare the result with the baseline. Your request, the response, tool calls, and the retained conversation history all consume space. Repeat once with a follow-up that references the first answer.

Context is not just your promptThe model may see more input than is visible in the chat composer. Treat the complete request envelope as the unit you measure.
Exercise 2

Measure the Real Cost

Input and output have different cost profiles, and reasoning models may produce hidden thinking tokens. Compare behavior rather than assuming that a larger model or longer answer is better.

2.1 Compare Output Size

Clear the session and run a verbose request:

/clear
Explain the SOLID principles with examples, best practices, common mistakes, and modern JavaScript guidance.

Record /context and /usage. Clear again, then run:

/clear
List the five SOLID principles in one sentence each. No examples or preamble.

Compare visible output, total tokens, and usefulness. Concise output is valuable when the task is already clear; it is not a license to omit required reasoning or evidence.

Cost heuristicPut stable, reusable context early so it can be cached. Put the task-specific request and changing inputs later. Remove output requirements that do not help a reviewer make a decision.

2.2 Choose the Right Model

Use a lightweight model for pattern-following work and reserve reasoning-capable models for tasks that genuinely require competing hypotheses or multi-file analysis.

TaskContext strategyModel posture
Rename or formatOne file, exact acceptance criteriaFast / low cost
Add a familiar endpointReference one analogous route and its testGeneral purpose
Debug a concurrency issueRelevant files, failing trace, reproduction stepsReasoning capable
Explore an unfamiliar repositoryBounded discovery artifact, not the whole treeAuto or agentic

Run the same small task on two models and record whether the quality difference justifies the token difference. Change models mid-session only when the preserved context is still relevant.

2.2 Check Usage and Cost

Use /usage in Copilot CLI and the Chat Debug View in VS Code to compare input, cached input, visible output, and reasoning tokens. For a rough comparison, multiply uncached input and output by the model rates shown for your plan.

Record the resultCapture model, total tokens, cached tokens, visible output, and whether the answer required rework.
Exercise 3

Tame the Output

Output tokens are often the biggest controllable cost. Compare an unconstrained response with one that has a clear format, length, and stopping condition.

3.1 Add Conciseness Constraints

Start a fresh session and ask for an explanation without constraints. Then repeat it with a precise output contract:

Explain context engineering for a new developer in exactly five bullets.
Each bullet must be one sentence and contain no example or preamble.

Compare usefulness, token count, and whether the response obeyed the contract. Constraints should remove waste without suppressing information needed to make a decision.

High-value constraintSpecify audience, format, length, and what to omit when those details materially improve the result.

3.2 Make Instructions Permanent

Move stable response preferences into the project instruction file instead of repeating them in every prompt:

# .github/copilot-instructions.md
- Prefer concise answers with a short rationale.
- Use existing project conventions before introducing new abstractions.
- Include focused verification steps after code changes.

Verify that the instructions are loaded, then remove any rule that is too vague, too rarely useful, or likely to conflict with the current task.

Exercise 4

Right-Size Your Model

Model choice changes both quality and cost. Use a fast model for bounded pattern-following work and a reasoning-capable model when the task contains competing hypotheses or cross-file uncertainty.

4.1 Match Model to Task

TaskBest starting posture
Rename, format, or apply a known patternFast / low cost
Add a familiar endpoint with an analogous testGeneral purpose
Debug concurrency or multi-file behaviorReasoning capable
Explore an unfamiliar repositoryAuto or agentic, with bounded outputs

Run one small task on two models and record whether the quality difference justifies the token difference.

4.2 Account for Thinking Tokens

Reasoning models may spend hidden tokens before producing visible output. Include input, cached input, visible output, and reasoning output when comparing cost. A shorter answer is not automatically cheaper if the model used substantial internal reasoning.

Selection rulePay for deeper reasoning when it reduces rework; otherwise keep the task bounded and use the least expensive model that meets the acceptance criteria.
Exercise 5

Practice Session Hygiene

Long sessions accumulate intermediate states, abandoned approaches, and stale assumptions. More history can make a task less reliable even when the context limit has not been reached.

3.1 Compact Stale History

Build a short conversation by asking for a health endpoint, a users endpoint, validation, and a test. Inspect the window, then compact it:

/context
/compact Focus on the current API contract, files changed, open issues, and tests. Discard superseded implementation steps.
/context

Check whether the compacted summary preserves the current code state, decisions, constraints, and unresolved questions. If it does not, correct the summary before continuing.

Compaction is a lossy operationNever assume a summary is correct because it is short. Verify important names, paths, contracts, and acceptance criteria against the repository.

3.2 Start Fresh on Purpose

Use /clear or restart the session when the task changes, the conversation contains contradictory attempts, or you return after a long break. Carry forward a concise handoff instead of the entire history:

PROJECT STATE:
- Current goal: add validation to POST /users
- Relevant files: src/routes/users.js, test/users.test.js
- Existing convention: errors use { error, code }
- Failing test: rejects an empty email with the wrong status
- Do not change: authentication middleware

Compare a fresh session with a stale one. Note which session produces fewer corrections and less irrelevant discussion.

Exercise 6

Select Better Inputs

Relevant context beats complete context. Give the model the smallest set of sources that lets it make the next decision, then expand only when evidence shows a missing dependency.

4.1 Target Files and Symbols

Compare a whole-file request with a symbol-level request:

Review the entire repository and improve the delete behavior.

Inspect the DELETE /items/:id handler in @src/app.js and its tests. Explain
whether the 404 and 204 responses match the existing API conventions. Do not edit.

Use references to point at the relevant file, symbol, test, or line range. Ask the model to cite the sources it used and to list what it did not inspect.

Explore, then focusFor an unfamiliar area, first ask for candidate files and verified conventions. The implementation turn should receive that bounded artifact, not the entire exploratory transcript.

4.2 Control Tool Output

Tool output becomes context. Run noisy commands and then filtered equivalents:

npm test
npm test -- --reporter=dot
rg "DELETE /items|status\(204\)|Not found" src test

Prefer commands that return the smallest useful result. Use least-privilege tool access for one-off tasks and ask for summaries of logs, package lists, or generated files instead of pasting them wholesale.

Think in artifactsA command is useful when its output changes the next decision. If it only confirms routine progress, keep a one-line status rather than sending the full transcript.
Exercise 7

Compare MCP and CLI Tools

Agents and integrations multiply context: tool definitions and returned artifacts may each add tokens. Prefer the simplest surface that can answer the question.

5.1 Compare MCP and CLI Tools

Choose one repository task, such as finding all test files for an endpoint. Compare an MCP tool with a focused CLI command. Record tool-definition overhead, returned fields, latency, and whether the extra capability improved the result.

Input sourceTypical strengthContext risk
Focused CLISmall, composable outputRequires the right command and filters
MCP toolStructured access and richer operationsTool schemas and default fields add overhead
Browser or IDE stateUseful for interactive verificationLarge hidden state for a small question

Use the simplest surface that can answer the question. A richer tool is worthwhile when its structured result prevents multiple exploratory calls.

5.2 Bound Delegated Work

Give an agent a narrow objective and a return contract:

ROLE: Repository test investigator
TASK: Find the tests that define the DELETE /items/:id contract.
SCOPE: Search src/routes and test only. Do not edit files.
RETURN: Verified file paths, relevant test names, expected statuses, and open questions.
LIMIT: Do not summarize unrelated modules.

Before passing the result to another agent, remove duplicated prose and preserve uncertainty. A small handoff is cheaper and easier to review than a second agent receiving the full first session.

Delegation checkpointAsk whether the delegated result is sufficient to make the next decision. If not, add one missing source; do not automatically widen the entire context.
Exercise 8

Bound Agent Workflows

Agent workflows multiply tokens across planning, tool calls, delegation, and returned artifacts. Make each boundary explicit so the next agent receives only what it needs.

8.1 Understand Context Isolation

Compare interactive mode, plan mode, and a delegated sub-agent. Record which instructions, files, tools, and prior results each participant receives. Do not assume that a child agent sees the parent session.

8.2 Bound Delegated Work

ROLE: Repository test investigator
TASK: Find tests that define the DELETE /items/:id contract.
SCOPE: Search src/routes and test only. Do not edit files.
RETURN: File paths, test names, expected statuses, and open questions.
LIMIT: Do not summarize unrelated modules.

Before passing the result onward, remove duplicated prose and preserve uncertainty. A small return contract is easier to review than a full transcript.

Exercise 9

Write Information-Dense Prompts

A dense prompt is not a long prompt. It puts the goal, verified context, constraints, acceptance criteria, and return format in an order that makes the next decision unambiguous.

9.1 Replace Vague Requests

Rewrite a request such as Improve the users API into a bounded task:

GOAL: Reject POST /users when email is empty.
CONTEXT: Follow the existing { error, code } response shape.
FILES: Inspect src/routes/users.js and test/users.test.js.
CONSTRAINTS: Do not change authentication or unrelated endpoints.
ACCEPTANCE: Return HTTP 400 with code VALIDATION_ERROR and add a focused test.
RETURN: Files changed, test command, and any unresolved question.

9.2 Use References and Structure

Point to analogous files and symbols instead of describing their contents from memory. Use headings or labeled fields for complex work, and ask the model to cite what it inspected and what it deliberately did not inspect.

CheckpointRemove any sentence that does not affect the implementation, validation, or decision. The goal is maximum signal per token.
Exercise 10

Build Knowledge Graphs and Pre-Compiled Context

Repeated exploration is a recurring context cost. Durable, high-value project knowledge lets the model start closer to the decision without rereading the whole repository.

10.1 Build an Architecture Map

Replace repeated file discovery with compact relationships:

## Where Things Live
| Component | Path | Responsibility |
|---|---|---|
| Entry point | src/app.js | Route registration |
| Middleware | src/middleware.js | Auth and validation |
| Tests | tests/ | Jest and supertest |

## Key Relationships
- src/app.js -> src/middleware.js -> route handlers
- tests/ mirrors the source structure

Ask Copilot to create an ARCHITECTURE_MAP.md under 200 words, reference it from the instruction file, then compare the token usage for a question answered from the map with a fresh session that must search the source.

10.2 Compare LLM-Wiki, Graphify, and LSP

Use the right pre-compilation surface for the question:

Tool or patternBest fitWhat it provides
LLM-wikiExternal documentationInterlinked summaries and a compact navigation index
GraphifyBroad codebase architectureAST-derived modules, relationships, graph report, and cached snapshot
LSPLive symbol navigationExact definitions, references, and type information with little noise

Graphify and LLM-wiki are point-in-time summaries; LSP is live and precise. For Graphify, read GRAPH_REPORT.md before raw files and use a preToolUse hook to inject that reminder when the graph exists. Measure the same architecture question before and after the graph to see the token savings.

Rule of thumbUse Graphify for architecture, LLM-wiki for documentation, and LSP for per-symbol resolution.

6.1 Keep Instructions High-Value

Create a small instruction file containing rules that are stable, specific, and useful on nearly every task:

# Project Instructions
- Run `npm test` for focused verification.
- Use the existing `{ error, code }` response shape.
- Prefer small changes and cite files before editing.
- Never include secrets or production customer data in examples.
- Return concise summaries with tests run and unresolved questions.

Ask Copilot to list which instructions it loaded, then remove any rule that does not change behavior. Instruction files are sent repeatedly, so a short high-signal file beats a project encyclopedia.

6.2 Build a Knowledge Graph

For a larger repository, record relationships rather than copying every file:

MODULE: src/routes/items.js
RESPONSIBILITY: HTTP handlers for item CRUD
DEPENDS ON: src/services/items.js, src/validation/items.js
TESTS: test/items.test.js
CONTRACT: 404 { error, code: "ITEM_NOT_FOUND" }; delete success is 204
OPEN QUESTION: authorization is enforced by middleware, not this module

This kind of precompiled context can live in project documentation, a generated wiki, or a graph-backed retrieval system. Keep it current and link claims to source files so it remains verifiable.

Context architecture principleUse the context window for the decision at hand, durable files for stable knowledge, and tools for evidence that changes over time.

Complete Lab Walkthrough

1. Measure the Window and a Session

Use an empty scratch repository so the first measurement is reproducible:

copilot

What is context engineering?
How does it differ from prompt engineering?

Clear the session, compare a verbose and concise request, then inspect usage and exit totals:

/clear
Explain the SOLID principles in software engineering. Include examples for each principle, best practices, common mistakes, and how they apply to modern JavaScript development.
/context
/clear
List the 5 SOLID principles. One sentence each, no examples.
/context
/usage

The exit line reports input, output, cached, and reasoning totals. For deeper local analytics, Codeburn can read CLI session data and report cost by model, tool, task, and project.

2. Reduce Output With a Durable Contract

Compare an unconstrained implementation request with one that explicitly stops extra prose:

Write a JavaScript function that validates an email address using a regex. Include error handling.

Write a JavaScript function that validates an email address using a regex. Include error handling. Code only - no explanation, no examples, no notes.

Then create a compact project instruction file and restart Copilot to load it:

mkdir -p .github
cat > .github/copilot-instructions.md << 'EOF'
# Project Instructions
## Response Style
- Be extremely concise. No pleasantries or filler.
- Return code only for code requests unless explanation is requested.
- Do not restate the question or add notes, tips, examples, or unsolicited improvements.
## Code Style
- JavaScript (ES2022+); use const and arrow functions where appropriate.
- Add inline comments only for genuinely complex logic.
EOF
copilot
/instructions
Instructions are recurring inputEvery instruction is sent on every turn. Keep only stable, high-impact rules; caching reduces repeated cost but does not make a long instruction file free.

3. Compare Models and Thinking Cost

Create a small, pattern-following target and try the same task on a fast and a reasoning model:

cat > calculator.js << 'EOF'
function add(a, b) { return a + b; }
function subtract(a, b) { return a - b; }
function multiply(a, b) { return a * b; }
function divide(a, b) {
  if (b === 0) throw new Error('Division by zero');
  return a / b;
}
module.exports = { add, subtract, multiply, divide };
EOF
cat calculator.js | copilot --model claude-haiku-4.5 --allow-tool='write' -p "Add a modulo function following the existing pattern. Code only."
cat calculator.js | copilot --model claude-opus-4.6 --allow-tool='write' -p "Add a modulo function following the existing pattern. Code only."

Reset the file and repeat with a multi-requirement refactor: a chaining class, finite-number validation, a ten-operation history, and CommonJS plus ESM support. The cheaper model is normally sufficient for the first task; deeper reasoning can justify cost for the second.

For hidden reasoning cost, inspect a concurrency bug with both models:

cat > scheduler.js << 'EOF'
const tasks = [];
let running = false;
async function addTask(fn, priority = 0) {
  tasks.push({ fn, priority }); tasks.sort((a, b) => b.priority - a.priority);
  if (!running) await drain();
}
async function drain() {
  running = true;
  while (tasks.length > 0) await tasks.shift().fn();
  running = false;
}
module.exports = { addTask };
EOF
cat scheduler.js | copilot --model claude-haiku-4.5 -p "Identify all race conditions and concurrency bugs. Be thorough."
cat scheduler.js | copilot --model claude-opus-4.6 -p "Identify all race conditions and concurrency bugs. Be thorough."

Read the CLI summary as input, visible output, cached, and reasoning. Thinking tokens are billed output even though they are not displayed. Use them for subtle debugging, security, or trade-off analysis, not boilerplate or formatting. You can use /model mid-session: start on Auto or Haiku, switch to Opus or GPT-5.5 for one hard turn, then switch back for a short summary.

4. Maintain Session Hygiene

Build a session by iteratively adding GET /health, POST /users, Zod validation, GET /users, and DELETE /users/:id. Inspect the accumulated history, compact it, then add a products endpoint and compact with a focus hint:

/context
/compact
/context
/compact Focus on the current Express server state and API endpoints. Discard the step-by-step build process.

Review the returned session checkpoint and verify names, paths, contracts, and open questions before using the summary. Compaction is lossy. Quality can decline well before the hard context limit, particularly once a session is dominated by stale intermediate states.

Before a break, compact the session. After a task switch or a long absence, use /clear or start a new session and provide a compact handoff:

PROJECT STATE:
- Current goal: add validation to POST /users
- Relevant files: src/routes/users.js, test/users.test.js
- Existing convention: errors use { error, code }
- Failing test: empty email returns the wrong status
- Do not change: authentication middleware

Focused bursts preserve prompt-cache hits. Returning to an old session after cache expiry can force the entire bloated history to be reprocessed as uncached input. Copilot CLI session recall and Agentic Memory can help retrieve durable history without keeping every old turn in the active window.

5. Build the Input Experiment and Filter Tool Output

Create the small API project used by the input exercises:

mkdir -p src tests
cat > src/app.js << 'EOF'
const express = require('express');
const app = express(); app.use(express.json());
const items = []; let nextId = 1;
app.get('/items', (req, res) => res.json(items));
app.post('/items', (req, res) => { const item = { id: nextId++, ...req.body, createdAt: new Date() }; items.push(item); res.status(201).json(item); });
app.get('/items/:id', (req, res) => { const item = items.find(i => i.id === parseInt(req.params.id)); if (!item) return res.status(404).json({ error: 'Not found' }); res.json(item); });
app.delete('/items/:id', (req, res) => { const index = items.findIndex(i => i.id === parseInt(req.params.id)); if (index === -1) return res.status(404).json({ error: 'Not found' }); items.splice(index, 1); res.status(204).send(); });

{"scripts":{"start":"node src/server.js","test":"vitest run --reporter=verbose"},"dependencies":{"express":"^5.2.1"},"devDependencies":{"vitest":"^4.1.5","supertest":"^7.2.2"}}

npm test 2>&1 | tail -20

6. Measure MCP and Agent Multipliers

MCP servers add tool definitions to system context and often return rich JSON, HTML, or browser snapshots. Measure the overhead with /context, inspect servers with /mcp show, and temporarily disable unused servers with /mcp disable. Compare the same result through GitHub MCP and the CLI:

/clear
Use the GitHub MCP tool to list the latest 5 open issues in this repository.
/context
/clear
gh issue list --limit 5
/context

Prefer gh, curl, psql, or mysql when they can produce the required compact result. MCP is worthwhile when structured capabilities prevent several exploratory calls, or when browser interaction is actually necessary.

Plan mode, sub-agents, parallel agents, and cloud delegation each use independent or growing context. Use direct interactive prompts for small tasks. Reserve plans for dependent multi-step work, and use a bounded delegation contract that states role, scope, allowed paths, return fields, and non-goals.

7. Make Prompts Dense, Not Long

Replace open-ended planning with a concrete implementation contract:

GOAL: Add GET /products filtering in src/app.js.
CONTEXT: Follow the /items response and error conventions.
REQUIREMENTS: ?status=active exact match; ?q=term name substring; ?sort=createdAt&order=desc.
CONSTRAINTS: Return 400 for invalid sort fields. Do not change other endpoints.
RETURN: Code only.

For multi-part work, use labeled requirements and constraints. Point to an analogous implementation instead of retelling it. Remove sentences that do not affect the decision, implementation, acceptance criterion, or verification.

8. Precompile Knowledge With Maps, Wikis, and Graphs

Create ARCHITECTURE_MAP.md under 200 words with a Where Things Live table and Key Relationships list, then link it from project instructions:

## Architecture Map
Read ARCHITECTURE_MAP.md before exploring src/.

Clear the session and test whether Copilot can answer a structural question from the map without searching files. Then remove the map and repeat to compare usage. Structured facts are cheaper to navigate than rediscovering raw source.

For external documentation, install and initialize the pin-llm-wiki skill, use /pin-llm-wiki init, ingest focused source URLs, and compare the same question with and without the compiled wiki. For broad codebase architecture, install Graphify, generate a graph, and have Copilot read graphify-out/GRAPH_REPORT.md before raw exploration:

uv tool install graphifyy
graphify install --platform copilot
copilot
/graphify .

Use Graphify for an architecture snapshot, LLM-wiki for external documentation, and LSP for current definition, reference, and type lookups. Graphs are a point-in-time aid, not a substitute for source verification or tests.

Safety and Privacy Guardrails

  • Use synthetic or minimized data; never paste credentials, tokens, private keys, or unnecessary personal information.
  • Apply least privilege to tools and delegation, especially when a task can modify files or execute commands.
  • Ask the model to cite sources, state assumptions, and flag uncertainty instead of silently inventing context.
  • Review generated code for authorization, validation, logging, external calls, and data exposure.
  • Do not treat compaction, retrieval, an instruction file, or a knowledge graph as a substitute for tests and human review.

Recap

  1. Measure the full context envelope, not only the visible prompt.
  2. Remove stale history and start fresh when the task or assumptions change.
  3. Prefer targeted files, symbols, filtered tool output, and bounded handoffs.
  4. Match model and tool capability to the reasoning required.
  5. Precompile stable project knowledge, but keep it concise and verifiable.
TakeawayThe best context is not the most context. It is the smallest, freshest, most relevant set of evidence that lets the model produce a result you can verify.
