A practical guide to designing prompts that give AI coding tools the right goal, context, constraints, examples, and feedback loop to produce useful work.

00

Orientation

Prompt engineering is the disciplined design of instructions and context so an AI system can produce an answer you can inspect, test, and improve.

The operating principle: a prompt is not a magic phrase. It is a small interface between human intent and machine behavior. Good prompts reduce ambiguity and make quality visible.
Intent

What outcome should exist when the task is finished?

Signal

What context, examples, constraints, and references will shape the answer?

Evidence

How will you know the response is correct, useful, secure, and complete?

01

Prompt anatomy

Use the parts that matter for the task. A short, specific prompt is stronger than a long prompt full of unrelated background.

Role and stanceTell the tool what perspective is useful: senior reviewer, test writer, accessibility specialist, or pair programmer.
GoalState the desired outcome and the user or system behavior it should enable.
ContextPoint to the relevant files, APIs, conventions, prior decisions, data shapes, and examples.
ConstraintsSpecify scope, frameworks, compatibility, security, performance, accessibility, and things that must remain unchanged.
Output and proofDefine the response format, requested edits, tests, checks, assumptions, and completion criteria.
Act as a focused code reviewer. Goal: review the pagination change for correctness and regressions. Context: inspect src/api/orders.ts and tests/api/orders.test.ts. The API uses cursor-based pagination. Constraints: do not refactor unrelated code; preserve the public response shape. Output: list findings by severity with file references, then name missing tests. Do not summarize code that has no issue.
02

The prompt loop

Treat prompting as an iterative engineering process. Each turn should narrow uncertainty or produce evidence.

1. FrameDefine the outcome and why it matters.
2. GroundSupply focused context and references.
3. DirectSet constraints and the output shape.
4. InspectReview the result against evidence.
5. RefineCorrect the smallest missing signal.

Before you send

  • Can the goal be verified without reading my mind?
  • Did I identify the files, symbols, or examples that control the task?
  • Did I state what is out of scope?
  • Did I ask for a useful output shape rather than merely saying "help"?
  • Do I know which test, command, or review will disconfirm the answer?
03

Reliable prompt patterns

Patterns give repeated work a stable shape. Adapt them to the task instead of copying them mechanically.

Explore before editing

Ask for the owning code path, nearby tests, and one falsifiable hypothesis before making a change.

Plan a bounded change

Name the files, behavior, constraints, validation command, and explicit non-goals.

Implement from an anchor

Point to an existing implementation or test and ask for the smallest consistent edit.

Review for failure modes

Ask for bugs, regressions, security risks, missing tests, and file references first.

Teach with contrast

Request a good and bad example, then explain the decision boundary between them.

Compress the context

Prefer relevant excerpts, symbols, and decisions over dumping the entire repository into the conversation.

Task prompt template

Task: [one sentence describing the desired behavior] Anchor: [file, symbol, test, failing command, or nearby implementation] Context: [only the facts needed to control the decision] Constraints: [framework, API, compatibility, security, scope, and non-goals] Implementation: [what to change and what to preserve] Validation: [the narrow command or test that could disconfirm the change] Output: [files changed, concise summary, and validation result]
04

Prompting GitHub Copilot

Copilot works best when the repository itself carries stable instructions and each request supplies the local task context.

Inline completion

Use nearby code, names, types, and comments to express the immediate shape of an implementation.

Chat

Ask for explanation, alternatives, tests, or a small transformation while keeping the relevant files visible.

Agent mode

Define the outcome, scope, allowed tools, checkpoints, and validation. Ask it to inspect before it edits.

Instructions and skills

Move durable repository conventions out of one-off prompts so every task starts with the same baseline.

Context is a budget: more text is not automatically more signal. Include information that changes the decision, and identify untrusted or merely illustrative material.

Agent task example

Add a retry policy for transient payment-provider failures. First inspect the payment client, its callers, existing error types, and nearby tests. State one hypothesis about where retry ownership belongs and name the narrow test that could disconfirm it. Keep the public API unchanged. Retry only documented transient failures with bounded exponential backoff. Do not retry validation, authentication, or declined-payment errors. Implement the smallest change, add focused tests for retry and no-retry cases, then run the payment test suite. Report files changed and any assumptions.
05

Common failures

When a response misses, diagnose the missing signal before adding more words.

FailureWhat it looks likeRepair the prompt
Vague goalA polished answer that solves the wrong problem.Name the user, behavior, and observable outcome.
Context dumpThe response repeats background but misses the controlling file.Point to the owning symbol and remove unrelated material.
Hidden constraintsThe change works locally but breaks compatibility or conventions.State APIs, versions, security rules, and non-goals explicitly.
No proof requestCode is generated without tests, checks, or assumptions.Specify the validation command and edge cases to cover.
Too many asksSeveral partially complete changes are difficult to review.Split discovery, implementation, and verification into focused turns.
Leading questionThe tool agrees with a solution before examining the problem.Ask it to inspect alternatives and state a falsifiable hypothesis.
06

Evaluation gates

A prompt is only successful when its output survives the checks that matter for the task.

Correctness

Does the behavior match the stated requirements and edge cases?

Fit

Does the change follow local architecture, APIs, style, and ownership boundaries?

Risk

Did the review consider security, privacy, accessibility, performance, and failure handling?

Human judgment remains in the loop: generated code can be plausible and still be wrong. Read the diff, run the focused check, and verify the result against the user need.

Review prompt

Review the current diff as a skeptical maintainer. Prioritize: correctness bugs, behavior regressions, security and privacy risks, missing error handling, and missing tests. Use the repository's existing conventions and inspect the nearest tests before judging style. Report findings first, ordered by severity, with file references. If there are no findings, say so and list residual test gaps.
07

Team playbook

Teams get more value when prompt quality becomes a shared practice rather than an individual trick.

Capture durable rules

Put coding standards, test commands, architecture boundaries, and review expectations in repository instructions.

Keep examples current

Store successful prompts near the workflow they support and remove examples that no longer match the codebase.

Measure the loop

Track rework, escaped defects, review findings, and time to a validated result rather than prompt length.

Bridge to specifications

When the prototype stabilizes, turn decisions, requirements, and acceptance criteria into durable project artifacts.

Prompt engineering maturity: start with clearer individual requests, then build shared context, reusable patterns, automated evaluation, and specifications that make good work repeatable.
