AI-Assisted Engineering &
Spec Driven Dev

Six progressive exercises: start with pure AI-assisted development, then level up to testable acceptance criteria, spec-first discipline, controlled comparison, and quality gates.

⏱ ~75 min total
🧪 6 Exercises
🟢 Beginner → Intermediate
EX 01
Pure AI-Assisted Engineering — Build a Feature Quickly
⏱ 15 min
▼
🎯 Goal
Experience the speed and fluidity of AI-assisted development — iterate rapidly with Copilot without planning upfront.
  1. 1
    Pick a small, contained idea
    Choose something you can build in under 20 minutes. Example: a CLI tool that fetches the weather for a city, a date-diff calculator, or a markdown table formatter.
  2. 2
    Open Copilot Chat and describe your idea conversationally
    Don't plan — just start talking. Try: "Build me a CLI tool that takes a city name and returns today's weather using a free API. Use Node.js."
  3. 3
    Iterate in real time
    Accept code, run it, notice what's missing, and ask Copilot to fix it conversationally. Keep your prompts informal and exploratory.
  4. 4
    Reflect: what was hard?
    Note 3 things that needed repetitive re-prompting. These are signals that a spec would have helped.
Tip: AI-Assisted Engineering is not sloppy coding — stay alert to security defaults (never hardcode keys), even in exploratory mode.
✅ Success Criteria
  • Working prototype in under 20 minutes
  • At least 3 vibe iterations (prompt → run → adjust)
  • List of 3 "friction points" noted for Exercise 2
EX 02
Vibe → Spec Conversion
⏱ 20 min
▼
🎯 Goal
Take the vibe-coded feature from Exercise 1 and retroactively write a spec.md that captures intent and requirements.
  1. 1
    Ask Copilot to extract requirements from your vibe session
    Use: "Review the code we just wrote. List the functional requirements it satisfies as REQ-001, REQ-002, etc. with acceptance criteria."
  2. 2
    Create spec.md
    Create a new file spec.md. Ask Copilot: "Generate a spec.md for this feature using the requirements list. Include title, summary, requirements, non-goals, and open questions."
  3. 3
    Identify gaps
    Review the spec. Find at least 2 things the code does that aren't in the spec, and 2 things in the spec that the code doesn't yet do.
  4. 4
    Fill the open questions section
    Answer the open questions yourself and update spec.md. Now you have a living document.
Tip: Retroactive specs are common in real projects. Getting comfortable writing them after exploration is a key skill.
✅ Success Criteria
  • spec.md with at least 4 REQ-IDs and acceptance criteria
  • Non-goals section present
  • Gap analysis: 2 undocumented behaviours + 2 missing implementations identified
EX 03
Spec-First Feature Development
⏱ 25 min
▼
🎯 Goal
Write a spec.md before writing any code, then implement strictly against it. Feel the difference in clarity and control.
  1. 1
    Choose a new feature idea
    Pick something slightly more complex: an API endpoint with validation and error handling, or a configuration file parser, or a notification email template builder.
  2. 2
    Write spec.md first — no code yet
    Use Copilot to help draft it: "I want to build [feature]. Help me write a spec.md with requirements, acceptance criteria, and non-goals. Don't write any code."
  3. 3
    Generate plan.md from spec
    Ask: "From this spec.md, create a plan.md with numbered tasks, each under 4 hours. Map each task to its REQ-IDs."
  4. 4
    Implement Task 1 only
    Ask Copilot to implement just the first task. After it completes, verify the acceptance criteria are met before moving to Task 2.
  5. 5
    Compare the experience
    Write a 3-sentence reflection comparing the spec-first experience to Exercise 1's vibe session.
✅ Success Criteria
  • spec.md written before any code
  • plan.md with 3+ tasks, each with REQ traceability
  • Task 1 implemented and verified against acceptance criteria
  • Written reflection comparing vibe vs spec approaches
EX 04
Run Quality Gates
⏱ 15 min
▼
🎯 Goal
Apply the four quality gates to your spec and plan from Exercise 3. Learn to self-audit your specs.
  1. 1
    Gate 1 — Spec quality
    Ask Copilot: "Review my spec.md and check: do all requirements have Given/When/Then acceptance criteria? Are non-goals listed? Are open questions answered?" Fix any issues.
  2. 2
    Gate 2 — Spec → Plan coverage
    Ask: "Check that every REQ-ID in spec.md appears in at least one task in plan.md. List any orphaned requirements."
  3. 3
    Gate 3 — Plan → Code traceability
    For your implemented Task 1, verify the code comment or commit message references the task and REQ-ID. Update if missing.
  4. 4
    Gate 4 — Completeness check
    Ask: "Based on spec.md and plan.md, what percentage of requirements are now implemented? List what's remaining."
Tip: Quality gates are most valuable when automated. In Module 5 (GitHub Spec Kit), you'll see how SpecKit automates all four gates.
✅ Success Criteria
  • All 4 gates run and findings documented
  • At least one spec gap found and fixed
  • Code traceability comment added to Task 1 implementation
  • Completeness report showing % done
EX 05
Acceptance-Test Matrix
⏱ 15 min
▼
🎯 Goal
Turn the feature from Exercise 3 into a measurable acceptance-test matrix before adding more code.
  1. 1
    List each requirement
    Copy every REQ-ID from spec.md into a table with Given, When, Then, test type, and current status columns.
  2. 2
    Challenge the happy path
    Add at least one invalid input, boundary value, and failure scenario for each user-facing requirement.
  3. 3
    Trace the evidence
    Link each row to a test name or manual verification step and mark any uncovered requirement.
✅ Success Criteria
  • Every REQ-ID has a testable Given/When/Then row
  • Boundary and failure cases are included
  • Uncovered requirements are clearly marked
EX 06
Controlled Vibe vs Spec Experiment
⏱ 15 min
▼
🎯 Goal
Compare both development styles using the same feature, evidence, and evaluation criteria.
  1. 1
    Choose a small feature
    Use a feature that can be prototyped in 10 minutes and has at least three acceptance criteria.
  2. 2
    Run two fresh sessions
    Build it once with a conversational prompt and once from a short spec. Keep the runtime, model, and starting code constant.
  3. 3
    Score the outcomes
    Compare time, rework, acceptance-criteria coverage, test quality, and confidence. Record where each approach helped or hurt.
✅ Success Criteria
  • Both approaches used the same starting conditions
  • At least five comparison measures recorded
  • Recommendation includes the context that led to it
